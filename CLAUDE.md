# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`interop-tools` (formerly `hl7-tools`, renamed as scope expanded beyond HL7v2) is a Python/FastAPI web app for converting healthcare messages/documents to FHIR R4 Bundles. The long-term goal (see README.md) covers transformation, validation, deduplication, test-data generation, and mapping across HL7v2/FHIR/CDA/C-CDA, with EDI planned next. Currently implemented:
- ADT — **A01 Admit, A02 Transfer, A03 Discharge, A04 Register, A05 Pre-admit, A08 Update, A11 Cancel Admit, A13 Cancel Discharge, A38 Cancel Pre-Admit** — each converting to a FHIR Bundle (Patient + Encounter).
- SIU — **S12 New booking, S13 Reschedule, S14 Modify, S15 Cancel, S17 Delete, S26 Patient No-Show** — each converting to a FHIR Bundle (Patient + Appointment + real Practitioner/Location/Device resources for the appointment's AIP/AIL/AIG participants, referenced by `urn:uuid`, not left as display-only text).
- ORU — **R01 Observation result, R30/R31/R32/R40 point-of-care result** — each converting to a FHIR Bundle (Patient + optional Encounter + one DiagnosticReport per OBR + one Observation per OBX, correctly grouped so each report only references its own results).
- MDM — **T02 New document, T04 Document status update, T06 Document addendum, T08 Document edit, T10 Document replacement, T11 Document cancel** — each converting to a FHIR Bundle (Patient + optional Encounter + DocumentReference + Binary for the document's OBX-carried text content), TXA → DocumentReference per the v2-to-FHIR IG.
- A synthetic HL7 message generator (`app/generators/`) covering all 26 combinations above, with realistic field-level randomization, selectable from a UI dropdown or `/api/generate`.
- A message **validator** - independent of conversion, runs against any message/document and returns a report of `error`/`warning`/`info` findings, each pointing at the offending location, covering both structural correctness and healthcare data-quality plausibility (a birth date in the future, a discharge before an admit, an appointment ending before it starts). Reachable via the **Validate** button in the UI or `/api/validate`, dispatched by input format via `app/pipeline.py::validate_any` - `app/validation/` for HL7v2, `app/cda/validation.py` for C-CDA.
- **C-CDA → FHIR** (`app/cda/`) - the app's first non-HL7v2 *input format* (XML, not pipe-delimited). Two document types: **CCD** (Continuity of Care Document) and **Discharge Summary**, both sharing the same header (Patient + optional Encounter) and section-dispatch infrastructure via `app/cda/common.py::build_sectioned_bundle` - four sections recognized on either document type: **Problems** → `Condition`, **Medications** → `MedicationRequest`, **Allergies** → `AllergyIntolerance`, and **Immunizations** → `Immunization` (administered/refused entries only - see the C-CDA subsection for the disclosed planned-immunization scope limit). Discharge Summary's own IG-required sections (Hospital Discharge Diagnosis, Discharge Medications, Hospital Course, Plan of Treatment) use entry shapes this app doesn't recognize yet and are silently skipped - see the C-CDA subsection for the full disclosed scope limit. Input format is auto-detected (`app/pipeline.py`) so the same **Convert to FHIR**/**Validate**/**Generate sample** UI and `/api/convert`/`/api/validate`/`/api/generate` endpoints handle either format - no separate route/UI. See the C-CDA subsection below for the full shape.

The previously-"remaining" HL7v2 trigger events for these four message types are now all implemented: ADT A38 (cancel pre-admit - the A05 sibling of A11/A13's cancel pattern), ORU R31/R32 (the remaining point-of-care variants alongside R30/R40), and MDM T08/T10/T11 (edit/replacement/cancel notifications) all shipped following the exact same patterns as their already-implemented siblings - see the per-type extension-point notes below for what (if anything) each one needed beyond a trigger-event string swap. Any future HL7v2 trigger event for one of these four types (there's no exhaustive list being tracked - add one if/when it's needed) can follow the same precedent. For C-CDA, Medications/Allergies/Immunizations now ship alongside Problems, and Discharge Summary now ships alongside CCD (see the C-CDA subsection below); H&P is a natural next document type on the same infrastructure. EDI support is planned after that.

## Architecture

**Request flow:** `app/routes/convert.py` (FastAPI routes for `/`, `/convert`, `/api/convert`, `/validate`, `/api/validate`, `/api/generate`, `/healthz`) calls `app/pipeline.py::convert_to_bundle(raw_text) -> Bundle` for conversion and `app/pipeline.py::validate_any(raw_text) -> ValidationReport` for validation. Both are thin format-sniffing dispatchers sitting above two independent, format-specific pipelines: `app/pipeline.py::is_xml(raw_text)` (does the text start with `<`, ignoring a possible leading BOM/whitespace) routes to `app/cda/pipeline.py`'s `convert_cda_to_bundle`/`validate_cda` for C-CDA XML or `app/hl7/pipeline.py`'s `convert_hl7_to_bundle`/`validate_hl7` for HL7v2 - neither format-specific pipeline knows the other format exists, and both raise the same exception shapes on each axis (`MissingSegmentError`/`MappingError`/`pydantic.ValidationError` for conversion, plus a format-specific parse error for both) so `app/routes/convert.py` needs only one dispatch table per axis, not a parallel one per format. `convert_hl7_to_bundle` parses via `app/hl7/parser.py`, reads MSH-9 for the message type/trigger event, looks up a mapper in `app/mappings/registry.py`, and calls `mapper.to_bundle(message)`; `validate_hl7` parses the same way and delegates to `app/validation/engine.py::validate_message()` (see the validation extension point below). The CDA side mirrors this exactly - `convert_cda_to_bundle`/`validate_cda` in `app/cda/pipeline.py` both parse via `app/cda/parser.py::parse_document` then delegate to `get_document_builder(...).build_bundle(...)`/`app/cda/validation.py::validate_document()` respectively (see the C-CDA subsection below). `/api/generate?message_type=&trigger_event=&seed=` runs the mirror-image path through `app/generators/registry.py::generate()` and returns raw text instead of a Bundle (HL7v2 or C-CDA, both registered in the same flat registry - see the C-CDA subsection) - the UI's message-type dropdown (populated from `app/generators/registry.py::list_supported_types()`) and "Generate sample" button call it to fill the textarea. The **Convert to FHIR** and **Validate** buttons are two `type="submit"` buttons sharing one `<form>`, distinguished via `formaction` (`/api/convert` vs `/api/validate`, or their `/convert`/`/validate` no-JS form-post fallbacks) - `app/static/app.js` branches on the standard `event.submitter` property to know which one triggered the submit.

**Extension point for new message types:** `app/mappings/base.py` defines the `MessageMapper` interface (`to_bundle(message) -> Bundle`). Each HL7 message *type* gets its own module (`app/mappings/adt.py`, `app/mappings/siu.py`, `app/mappings/oru.py`, `app/mappings/mdm.py`) implementing that interface, registered in `app/mappings/registry.py` as `{(message_type, trigger_event): mapper_instance}` — no changes to routes, the parser, or templates. Cross-message-type shared logic lives in `app/mappings/common.py`:
- `build_patient(pid) -> Patient` — PID is mapped identically no matter the message type.
- `assemble_bundle(msh, patient, *resources) -> Bundle` — MSH-derived Bundle metadata + entries, generic over however many additional resources a message type produces.
- `resolve_encounter_class(pv1) -> Coding` / `build_visit_identifier(pv1) -> Identifier | None` — PV1-2 (patient class) → `Encounter.class` and PV1-19 (visit number) → an `Identifier`, used by `adt.py`'s `build_encounter_core` and `common.py`'s own `build_minimal_encounter` below. `adt.py` and `oru.py` independently hand-rolled the same `{"I":"IMP","O":"AMB",...}` mapping before it was extracted here - if you're building a third PV1-derived Encounter somewhere, use these rather than a third copy.
- `build_minimal_encounter(pv1, patient_id) -> Encounter` — a minimal, status-`"unknown"` Encounter for message types whose PV1 (when present) gives context rather than an admit/discharge lifecycle event. Used by both `oru.py`'s optional result-reporting encounter and `mdm.py`'s optional document-context encounter. This was independently duplicated byte-for-byte between `oru.py` and `mdm.py` before being extracted here - caught by code review, not the original test suite.
- `location_display(segment, field_num)` / `person_display(segment, field_num)` — PL/XCN-shaped **display-string** formatting, for when a field only needs to read as text (e.g. `Encounter.location`/`Encounter.participant` display in `adt.py`, which doesn't materialize separate Location/Practitioner resources). `person_display` falls back to the XCN id (component 1) when family/given are both empty — it must stay in sync with `build_practitioner_from_xcn`'s presence check ("id or family or given") below, since anywhere both are paired into one `Reference` (as `siu.py`'s AIP participants and `mdm.py`'s TXA-9/TXA-10 do), a field with only an id and no name would otherwise materialize a real Practitioner but produce `Reference(display="")`, which FHIR rejects (`display` must be a non-empty string when present). This exact crash shipped once (an id-only AIP, e.g. `AIP|1||5678||||`) and was caught by code review, not the original test suite — see `tests/test_siu_s12_mapping.py::test_aip_with_id_only_materializes_with_id_as_display`.
- `build_reference_with_optional_display(resource_id, display) -> Reference` — the defensive counterpart to the crash above: a `Reference` to a materialized resource with `display` omitted entirely (rather than passed as `""`) whenever the display text couldn't be resolved, so any *future* caller pairing an XCN/PL-sourced resource with a display string fails safe instead of crashing. First written inline in `siu.py`'s `add_participant`, independently re-derived in `mdm.py` for TXA-9/TXA-10, then extracted here once both existed - both now call this shared helper.
- `build_location_from_pl(segment, field_num) -> Location | None` / `build_practitioner_from_xcn(segment, field_num) -> Practitioner | None` — the same PL/XCN field shapes, but building a **real, separately-referenceable resource** instead of just a string. Used by `siu.py` (AIL→Location, AIP→Practitioner), `oru.py` (OBX-16→Practitioner performer), and `mdm.py` (TXA-9/TXA-10→Practitioner originator/authenticator). Prefer these over the display-only pair whenever the target field is an `actor`/`performer`/similar `Reference` rather than a plain string, since a real resource is more useful to any downstream consumer (they can look up the practitioner's identifier, not just read a name). These are PL/XCN-scoped specifically - don't reuse them for a differently-shaped field (e.g. CWE) just because two of its components happen to look similar; build that shape's resource directly instead (see the AIG note below for a case where this was gotten wrong once).

Generic, reusable *field-level* FHIR-fragment builders (name/address/datetime/gender parsing, `build_codeable_concept_from_cwe` for CWE-typed fields) live in `app/fhir_models/builders.py`, shared across all message types; message-type-specific field logic stays in that type's module.

**Extension point for trigger events within one message type:** `app/mappings/adt.py` and `app/mappings/siu.py` follow the same shape — a `Base*Mapper(MessageMapper)` whose `to_bundle()` does the parts identical across every trigger event for that message type (require the message type's core segments, read any optional repeating segments, build the Patient via the shared `build_patient`, delegate to an abstract per-trigger build method, assemble the Bundle via the shared `assemble_bundle`), with concrete trigger subclasses implementing only the part that actually varies:
- `app/mappings/adt.py`: `BaseAdtMapper.build_encounter(pv1, evn, patient_id) -> Encounter`. Most subclasses (`AdtA01Mapper`, `AdtA04Mapper`, `AdtA05Mapper`) just call the shared `build_encounter_core(pv1, evn, patient_id, status=...)` (`A05` pre-admit uses `status="planned"`); `AdtA02Mapper` additionally layers in PV1-6 prior-location history; `AdtA03Mapper` requires a resolvable discharge time (PV1-45 or EVN-2 fallback) and maps PV1-36 discharge disposition; `AdtA08Mapper` infers status from whether a discharge time is present. `AdtA11Mapper` (cancel admit), `AdtA13Mapper` (cancel discharge), and `AdtA38Mapper` (cancel pre-admit) all set `status="entered-in-error"` — a deliberate choice, not IG-mandated (the v2-to-FHIR IG's own A11 guidance applies no special cancel handling at all, which would make an A11-derived Encounter indistinguishable from a plain A01 one in the output) — and all three call the shared `_drop_evn2_period_start_fallback(encounter, pv1)` after `build_encounter_core`, since `build_encounter_core`'s EVN-2 fallback for `period.start` is correct for admission-lifecycle triggers (EVN-2 genuinely is the encounter's own event time for A01/A02/A04/A05/A08) but wrong for these three: EVN-2 on a cancel-trigger message is when the *cancel notification itself* was recorded, not any real admission start. Getting this wrong (only guarding `period.end` against the same hazard, which `AdtA13Mapper` did at first, while leaving `period.start` unguarded) silently mislabels the cancel-event's own timestamp as an admission start — this exact bug shipped once and was caught by code review, not the original test suite (see `tests/test_adt_a11_mapping.py::test_cancel_admit_without_pv1_44_does_not_leak_evn2_as_period_start` and the equivalent A13/A38 tests). `AdtA38Mapper` is A05's cancel-pattern sibling the same way `AdtA11Mapper` is A01/A04's and `AdtA13Mapper` is A03's — unlike A13, it does *not* map PV1-36 discharge disposition, since a pre-admission was never discharged.
- `app/mappings/siu.py`: `BaseSiuMapper.build_appointment(sch, tq1_segments, nte_segments, ais_segments, participants) -> Appointment`. `participants` is built once by `to_bundle` (via `_build_participants`, which also returns the Practitioner/Location/Device resources materialized for AIP/AIL/AIG so `to_bundle` can add them to the Bundle) since it's identical regardless of trigger event - only `status`/`start`/`end` vary, so those are the only things each subclass supplies. Two private base classes each expose a `status` class attribute overridden per subclass, rather than hardcoding status in the shared build method: `_BookedSiuMapper` (`status="booked"` by default) resolves timing via `resolve_appointment_timing()` and requires a start time (raises `MappingError` otherwise) — `SiuS12Mapper`/`SiuS13Mapper`/`SiuS14Mapper` inherit it unchanged (deliberately identical apart from which `trigger_event` string ends up in the `Appointment.extension` marker, since this converter has no persisted state to make a "new booking" vs. "reschedule" vs. "modify" distinguishable in the output), while `SiuS26Mapper` (patient no-show) overrides `status="noshow"` - a no-show necessarily refers to a specific already-scheduled time, so it shares the timing-required behavior. `_UntimedSiuMapper` (`status="cancelled"` by default) resolves timing but does not require it — `SiuS15Mapper` inherits it unchanged, while `SiuS17Mapper` (delete) overrides `status="entered-in-error"`: the HL7 standard draws an explicit, deliberate distinction between S17 "removing an error" and S15 "cancelling a valid request," and FHIR's `entered-in-error` ("should not have been part of the record") is a closer semantic match to S17 than reusing S15's `cancelled`.
- `app/mappings/oru.py`: **not** trigger-polymorphic — `BaseOruMapper` handles R01/R30/R31/R32/R40 identically (they differ only in upstream ordering-workflow semantics this converter doesn't model — R30 places a new order, R31 searches for an existing one, R32 assumes one was already pre-ordered, R40 places none — none of which this stateless converter models), so the five concrete classes are just `trigger_event = "R01"/"R30"/"R31"/"R32"/"R40"` with no overrides. This is the degenerate case of the same pattern, not a different one.
- `app/mappings/mdm.py`: same degenerate, non-trigger-polymorphic pattern as `oru.py` — `BaseMdmMapper` handles T02/T04/T06/T08/T10/T11 identically, since the official v2-to-FHIR IG ships exactly one MDM ConceptMap (`MDM_T02` → `Bundle`) and treats the TXA segment map as trigger-agnostic. The six concrete classes are just `trigger_event = "T02"/"T04"/"T06"/"T08"/"T10"/"T11"` with no overrides. T10 (replace) and T11 (cancel) look like they should warrant trigger-specific `DocumentReference.status` handling the way A11/A13/A38 deliberately override ADT's cancel-trigger status — but here the decision went the other way: the segment-txa-to-documentreference ConceptMap has no trigger-event-specific guidance at all, and TXA-13 (the field that would carry T10's "replaces" pointer) has no mapped FHIR target in it, so — per an explicit instruction to treat the IG as the authoritative source when weighing this exact tradeoff — status stays 100% TXA-19-driven and TXA-13 stays unmapped for every trigger, same as T02/T04/T06. See the module docstring for the full reasoning.

When adding a new trigger event for an already-supported message type, add a subclass in that type's module rather than a new file — only add a new file for a genuinely different HL7 message type.

**Extension point for repeating leader/member segment groups:** `app/hl7/parser.py::group_segments_by_leader(message, leader_name, member_names)` walks a message's segments in order and associates each run of member segments with the leader segment that immediately precedes it (e.g. ORU's `OBR` leading its `OBX` results). Use this - not the flat `optional_segments()` - whenever which-segment-belongs-to-which matters for correctness, not just presence/absence. It's deliberately generic (any leader/member name pair), so a future message type with a similar repeating-group shape (e.g. an order message's `ORC` leading `OBR`) can reuse it directly rather than re-deriving the same positional-walk logic.

**Synthetic message generation (`app/generators/`)** is the mirror image of `app/mappings/` - HL7 text out instead of in. `app/generators/registry.py::generate(message_type, trigger_event, seed=None) -> str` looks up a plain generator function per `(message_type, trigger_event)` (not a class hierarchy like the mappers - generation doesn't need per-trigger polymorphism, just per-trigger field-population rules) and threads a `random.Random(seed)` instance through it; same seed always reproduces the same message byte-for-byte, `seed=None` gives real randomness for the UI's "fresh one" use case. `("CDA", "CCD"): (app.cda.generator.generate_ccd, "CDA^CCD - Continuity of Care Document")` is registered in this exact same flat dict (see the C-CDA subsection below) - "CCD" stands in for `trigger_event` even though C-CDA has no real trigger-event concept, chosen because it costs zero UI/route changes versus a genuine third registry axis for one entry. `app/generators/base.py` holds shared primitives every generator uses: `maybe(rng, p=0.6) -> bool` (the one place "should this optional field be included" is decided), small pools of obviously-synthetic sample data (names/addresses/reason codes/lab tests/etc.), `generate_msh_segment()`, `generate_pid_segment()` (used by all three message types' generators), `build_minimal_pv1_fields(rng, patient_class) -> dict` (used by `adt.py`, `oru.py`, and `mdm.py` - the message types whose generators build a PV1; this exists because ADT and ORU independently duplicated the same PV1-1/2/7/19 field logic once, and had already silently diverged - ORU's copy was missing the physician field ADT's had - before being unified here), and shape-level helpers (`random_location_field()` for PL-shaped fields, `random_physician_xcn()` for XCN-shaped fields) reused across `adt.py`/`siu.py`/`oru.py`/`mdm.py` as needed.

Required/optional policy (the field-level randomization rule the generators implement): a field is treated as required - always populated - when either the HL7 standard calls it required, *or* this app's own mapper needs it to avoid raising `MappingError`/`MissingSegmentError` for that specific trigger (e.g. `PV1-6` prior location is required only for A02; `PV1-44`/`PV1-45` are both required only for A03, since `AdtA03Mapper` raises without a discharge time; SIU S12/S13/S14 always get resolvable timing - via a randomized ~75/25 split between `TQ1` and legacy `SCH-11`, deliberately exercising both of `resolve_appointment_timing()`'s paths - while S15 leaves timing fully optional). Every other field is optional at a fixed ~50-60% inclusion rate via `maybe()`. The one deliberate exception is A08's discharge time, held at exactly 50% *by design* (not just "the general optional rate") specifically to exercise `AdtA08Mapper`'s finished-vs-in-progress status inference in both directions. This policy guarantees every generated message converts successfully through the existing pipeline - the generator's test suite leans on this heavily (see Testing below). **When both admit and discharge are generated, they must come from the same `random_time_range()` call**, not two independent ones - `generate_adt_a03`/`generate_adt_a13` already did this correctly, but `generate_adt_a08` originally drew them from two separate calls, which could (and, once `app/validation/` existed to notice, did) produce a discharge time before the admit time. Fixed once `app/validation/adt.py`'s `discharge-before-admit` rule caught it in the generator's own fuzz output - not a validation-rule bug, a real pre-existing generator gap the validator was the first thing to actually notice.

**Extension point for validation rules (`app/validation/`)** is a third, independent pillar alongside `app/mappings/` (HL7→FHIR) and `app/generators/` (FHIR-shaped→HL7 text) - it takes a parsed message and returns a `ValidationReport` (`app/validation/models.py`: `ValidationFinding{severity: error|warning|info, rule_id, segment, field, message}` + `ValidationReport{message_type, trigger_event, is_valid, findings}`), never a Bundle, and never raises for anything a real HL7 sender could plausibly produce. Same per-message-type module shape as mappings/generators, but two deliberate structural differences:
- `app/validation/registry.py` is keyed by **message type only** (`{message_type: validate_fn}`), not `(message_type, trigger_event)` like `app/mappings/registry.py` - rule *sets* are type-scoped; trigger-specific nuance (e.g. `adt.py`'s A02-only prior-location rule) lives inside the relevant rule function via an `if trigger_event == "...":` check, not via a second registry dimension.
- Each module (`generic.py` for every message type, `adt.py`/`siu.py`/`oru.py`/`mdm.py` per type) exposes one `validate(message, trigger_event) -> list[ValidationFinding]`, but internally composes small private `_rule_*` functions by concatenation rather than one large function - each rule is independently testable and a future contributor knows exactly where to add the next one, mirroring `build_encounter_core`'s small-named-step style more than a single do-everything function.

`app/validation/engine.py::validate_message()` runs `generic.validate()`, then the type-specific validator if one is registered, then `_check_convertibility()` - the load-bearing design decision here: rather than re-deriving a second, parallel "which segments does trigger X require" table (a real duplication-and-drift risk this project has already been bitten by once, see `build_minimal_pv1_fields`/`build_minimal_encounter` above), it actually calls `get_mapper(...).to_bundle(message)` and turns whatever it raises into a finding, so structural completeness can never drift from what the mappers actually enforce. Two gotchas that shipped wrong on the first pass and were caught by manual smoke-testing before the test suite was even written, not by code review this time:
- **`MappingError` is raised from two different places with two different meanings**, and both must be handled, not just one: `get_mapper(message_type, trigger_event)` raises it when the type/trigger isn't registered at all (→ an `info` finding, "no converter registered" - not a defect in the message), but several mappers (`AdtA03Mapper`, `SiuS12Mapper`/`S13`/`S14`/`S26`) *also* raise `MappingError` directly from inside `to_bundle()` for business-rule violations (missing discharge time, unresolvable appointment timing) once a mapper instance was already successfully obtained. The first version of `_check_convertibility()` only caught `(MissingSegmentError, ValidationError)` around the `to_bundle()` call, so every one of those legitimate, well-documented mapper errors fell through into the bare `except Exception` safety net and got logged as an "unexpected internal error" - technically not a crash, but a misleading severity/message for a completely ordinary outcome. Fixed by adding `MappingError` to that inner except tuple too.
- **PID-7 (date of birth) is very commonly date-only** (`YYYYMMDD`, 8 digits, no time component) - `app/fhir_models/builders.py::parse_hl7_datetime` requires 12+ digits (it's built for timestamps, not bare dates) and returns `None` for an 8-digit value, which `app/validation/common.py::parse_comparable_datetime` originally treated as "unparseable," flagging every ordinary date-only birth date as a warning. Fixed by falling back to `parse_hl7_date` (exactly 8 digits) and treating a date-only result as UTC midnight - this is also why `parse_comparable_datetime` exists as its own helper rather than every rule calling `parse_hl7_datetime` directly, so this fallback only had to be written once.

A follow-up multi-agent code review (adversarially verified - findings had to be reproduced by actually running code, not just argued for) caught four more, real ones the manual smoke-testing above missed:
- **The date-only-as-midnight fallback above has its own downstream consequence**: comparing a date-only value against a same-calendar-day *timestamped* value (e.g. `PV1-44` admit `...T08:30:00Z` vs. a date-only `PV1-45` discharge on the same day) made the synthetic midnight sort before the real time-of-day, producing a false `adt.discharge-before-admit`/`adt.admit-before-birth` **error** on a perfectly plausible message. `app/validation/common.py::has_time_precision()` now exposes whether a value actually carried a time component; `app/validation/adt.py::_is_before()` falls back to date-granularity comparison (`.date() <`) whenever either side lacks it, and only compares exact datetimes when both have full precision.
- **`parse_hl7_date`/`parse_hl7_datetime` only validate digit *shape*, not calendar validity** - a numerically well-formed but nonsensical date like `20260231` (Feb 31) made `datetime.fromisoformat()` raise an uncaught `ValueError` from inside `parse_comparable_datetime`'s date-only fallback branch (its sibling `_parse_fhir_datetime`, for the timestamp path, already guarded this correctly). Since this ran during the *generic rules* phase - before `_check_convertibility()`'s own `except Exception` safety net ever executes - it wasn't caught anywhere, and turned `/api/validate` into a raw HTTP 500 on exactly the kind of fat-fingered input a validator exists to catch. Fixed by wrapping that branch in the same `try/except ValueError` its sibling already had.
- **A registered *type* with an unmapped *trigger*** (e.g. `ADT^A38`, one of the "remaining trigger events" this file lists) already runs its type-specific rules before `_check_convertibility()` ever discovers the trigger isn't mapped - so the resulting `engine.unsupported-message-type` finding's message text (`"...only generic checks were run"`) was flatly false whenever type-specific findings sat right next to it in the same report. `_check_convertibility()` now takes a `ran_type_specific_checks` flag from `validate_message()` and adjusts the wording accordingly.
- **Two other, lower-stakes issues in the same pass**: `app/validation/oru.py::_resolve_reference_range` accepted a syntactically valid but semantically transposed range like `"100-70"` (low > high) as if it were normal, producing an inverted (wrong) in/out-of-range determination instead of being skipped like every other malformed `OBX-7` shape - fixed by rejecting `low > high` the same way. `app/validation/adt.py::_rule_a02_missing_prior_location` compared `trigger_event` with a bare `== "A02"`, unlike every other type/trigger dispatch point in this codebase (`get_mapper`, `get_type_validator`), which normalize with `.strip().upper()` first - a lowercase `ADT^a02` silently skipped the check. Both `adt.py` and `mdm.py`'s "is this in the future" rules were also independently hand-rolling the exact logic `common.py::not_in_future()` already existed to centralize (dead code, not a behavior bug) - now both call it.

`app/validation/adt.py`'s `_is_before(earlier_raw, earlier_dt, later_raw, later_dt)` (the date-only-aware ordering comparison behind `discharge-before-admit`/`admit-before-birth`) was promoted to `app/validation/common.py::is_before()` (public) once `app/cda/validation.py` needed the exact same logic for its own encounter/problem-ordering rules - the same "extract once a second real consumer exists" pattern already used for `build_minimal_pv1_fields`/`build_minimal_encounter` above, not a speculative abstraction.

Route/API shape (`app/routes/convert.py`): `_run_validation()`/`ValidationResult` mirror `_run_conversion()`/`ConvertResult` exactly, but `/api/validate` **always returns HTTP 200** for a report, even when `is_valid: false` - a report concluding "this message has an error" is itself a *successful* analysis, not an API-level failure. Only the two exceptions `validate_hl7()` can still raise (`Hl7ParseError`, and `MissingSegmentError` specifically for MSH itself being absent - there's nothing left to validate without it) map to a 4xx, via a narrower `_VALIDATION_ERROR_STATUS` table that deliberately excludes `MappingError`/`pydantic.ValidationError` (validate_hl7 never raises either).

**Error taxonomy:** three custom exceptions in `app/hl7/errors.py` — `Hl7ParseError` (unparseable text), `MissingSegmentError` (required segment absent), `MappingError` (no mapper registered for a message type) — plus `pydantic.ValidationError` from FHIR resource construction. `app/cda/errors.py` adds exactly one more, `CdaParseError` (unparseable XML, or a well-formed document whose root isn't `ClinicalDocument`) - `MissingSegmentError`/`MappingError` are reused as-is for C-CDA rather than duplicated, since their meaning ("a required structural piece is absent" / "no builder registered for this recognized-but-unhandled type") is format-agnostic. `app/routes/convert.py` translates each to an HTTP status + category label, and both the JSON API and the server-rendered form path route through the same `_run_conversion()` helper so error handling only lives in one place. The UI never shows a raw traceback.

### C-CDA support (`app/cda/`)

C-CDA is a genuinely different input *format* from HL7v2 (XML, not pipe-delimited), so it's a sibling package to `app/hl7/`/`app/mappings/`, not folded into either — the field-access primitives are fundamentally different even though the FHIR-building spirit is the same. Built entirely on stdlib `xml.etree.ElementTree` (verified sufficient for this scope: template-id-driven section/entry lookup at fixed nesting depths, no need for XPath 1.0 axes or XSD validation) — no new dependency.

- **`app/cda/parser.py`** — the `app/hl7/parser.py` equivalent: `parse_document(raw_xml) -> Element` (raises `CdaParseError`), `has_template_id(element, root_oid) -> bool`, `find_child`/`find_all` (path navigation), `xsi_type`, `coded_value`, `ts_value`, `ivl_ts_bounds`. Two real `ElementTree` gotchas these primitives are built to make structurally impossible to hit by accident: (1) a multi-segment relative path missing the namespace prefix on **any** segment fails **silently** (`[]`, not an error) — `find_all` auto-prefixes every `/`-separated segment itself, so a caller can't under-prefix a path; (2) every C-CDA templateId is emitted **twice** per element (a bare `<templateId root="...">` and a versioned sibling with `root`+`extension`), as sibling elements in no guaranteed order — `has_template_id` checks all direct children for a matching `@root`, never assumes `find()`'s first hit is the bare one, and (deliberately) only checks **direct** children, not descendants, so checking a section for its own templateId can't false-match a nested entry's templateId several levels down.
- **`app/cda/common.py`** — the `app/mappings/common.py` equivalent, shared across C-CDA document types (not CCD-specific, since header structure and coded-value shape are standardized across the whole C-CDA family): `build_codeable_concept_from_cd(element) -> CodeableConcept | None` (CD-shaped `<code>`/`<value xsi:type="CD">`, via a disclosed OID→FHIR-system table - SNOMED CT, LOINC, RxNorm, ICD-10-CM, falling back to `urn:oid:<oid>`), `parse_partial_ts(raw) -> str | None` (tries a full HL7 TS timestamp, falls back to date-only — CDA's `@value` digit shape is identical to HL7v2's TS fields, so `app/fhir_models/builders.py::parse_hl7_date`/`parse_hl7_datetime` are reused directly, not reimplemented), `build_patient_from_header(document) -> Patient` (raises `MissingSegmentError` if `recordTarget/patientRole/patient` is absent), `build_encounter_from_header(document, patient_id) -> Encounter | None` (from `componentOf/encompassingEncounter`, `None` when absent since a CCD is a summary document not necessarily bound to one encounter; status always `"unknown"` — same rationale as ORU/MDM's minimal PV1-derived Encounters, no reliable lifecycle signal to infer from), `assemble_bundle(document, patient, *resources) -> Bundle` (`Bundle.identifier`/`.timestamp` from `ClinicalDocument/id`/`effectiveTime`, `Bundle.type = "collection"` matching every existing HL7v2 pipeline's output shape — a proper FHIR-Document-shaped `Bundle(type="document")` + `Composition` is out of scope, since `fhir.resources.R4B.Composition` requires `author` (1..*), which this slice never materializes), and `build_sectioned_bundle(document) -> Bundle` (header + walk every `structuredBody` section through `SECTION_BUILDERS` - the full `build_bundle()` implementation for any document type whose conversion is exactly that shape; extracted here once `app/cda/discharge_summary.py` became a second real consumer of logic `ccd.py` had originally implemented inline, the same "extract once a second real consumer exists" pattern already used for `build_minimal_pv1_fields`/`build_minimal_encounter`, `is_before`, etc. — see that function's own docstring for why a document type with genuinely different structure should implement `build_bundle()` directly instead of being forced through it). CDA's `AdministrativeGender` codeSystem uses `F`/`M`/`UN`, a genuinely different vocabulary from HL7v2 PID-8's `M`/`F`/`O` — its own `_GENDER_MAP`, not a reuse of `app/fhir_models/builders.py`'s HL7v2 gender map. Three bugs caught by a follow-up multi-agent code review (adversarially verified by actually reproducing each with real code, not just argued for), all fixed before any fixture exercised them:
  - **`Bundle.timestamp` is FHIR `instant`, which has no date-only form** (unlike `Condition.onset(Date)Time`, a plain `dateTime` that does) - `assemble_bundle` originally fed it through `parse_partial_ts`, whose whole purpose is a date-only fallback. A `ClinicalDocument/effectiveTime` with no time component (a common, legitimate real-world shape) produced a value the `instant` regex rejects, crashing resource construction with `pydantic.ValidationError` on an otherwise perfectly convertible document - reproduced directly via `Bundle(timestamp="2026-08-12")`. Fixed by calling `parse_hl7_datetime` directly (returns `None` rather than a date-only string) instead of `parse_partial_ts`, matching `app/mappings/common.py::assemble_bundle`'s own deliberate no-date-only-fallback choice for this exact field.
  - **A root-only `<id>` (no `@extension`) was silently treated as "no identifier"** - `_build_identifier` returned `None` whenever `@extension` was absent, even though an II with only a `root` is still a complete identifier per the HL7 datatype spec (the root itself IS the identifier value). Reproduced: a root-only `patientRole/id` produced `Patient.identifier = None` instead of an identifier. Fixed by falling back to `Identifier(system="urn:ietf:rfc:3986", value=f"urn:oid:{root}")` when `@extension` is absent but `@root` is present, matching FHIR's own CDA-on-FHIR convention for representing a bare root.
  - **`build_encounter_from_header` only ever captured the first `<id>`** (`find_child`, not `find_all`), unlike `_build_patient_identifiers` which correctly collects every one - an `encompassingEncounter` with two ids (e.g. local + national encounter number) silently lost the second. Fixed by extracting a shared `_build_identifiers(id_elements, fallback_system) -> list[Identifier]` helper, used by both the patient and encounter paths now.
- **`app/cda/base.py`** / **`app/cda/registry.py`** — `CdaDocumentBuilder(ABC)` (`build_bundle(document) -> Bundle`) is the `MessageMapper` equivalent: document types are a "different shape dispatched via registry" situation, same as HL7v2 message types. `registry.py` holds two tables: `_DOCUMENT_BUILDERS` (`{CCD_TEMPLATE_ID: CcdBuilder(), DISCHARGE_SUMMARY_TEMPLATE_ID: DischargeSummaryBuilder()}`) and `SECTION_BUILDERS` (`{PROBLEMS_SECTION_TEMPLATE_ID: build_conditions, MEDICATIONS_SECTION_TEMPLATE_ID: build_medication_requests, allergies.SECTION_TEMPLATE_ID: build_allergy_intolerances, allergies.SECTION_TEMPLATE_ID_ENTRIES_OPTIONAL: build_allergy_intolerances, IMMUNIZATIONS_SECTION_TEMPLATE_ID: build_immunizations}`, plain functions since every section builder shares one signature — the generator-registry precedent, not the mapper one; the Allergies section is registered under **two** templateIds - the "entries required" one this app originally targeted and the "entries optional" sibling variant, both wrapping the identical entry shape, just a different section-level cardinality constraint - a real gap found by fetching a real Discharge Summary example while researching that document type (see the `discharge_summary.py` bullet below), not something CCD's own fixtures had exercised. **Registering the conversion-side dict entry alone was itself an incomplete fix, caught by a follow-up code review**: `app/cda/validation.py` has its own independent `_find_allergies_section(document)` helper (used to decide which section to run `_rule_allergies` against), and it originally checked only the "entries required" templateId - so a document using the "entries optional" variant converted correctly (via `SECTION_BUILDERS`) but silently ran *zero* allergy validation findings against it, reproduced directly (an entries-optional section with an unresolvable allergen produced no `cda.allergy-missing-allergen` finding, while the identical content under the "entries required" templateId correctly did). Fixed by extracting a shared `_find_section(document, *template_ids)` helper in `validation.py` that every `_find_*_section` function now calls, so a section type registered under more than one templateId can't have this drift between its conversion-side and validation-side dispatch again; `app/cda/generator.py`'s `_random_allergies_section` was also updated to emit the "entries optional" templateId ~25% of the time (it previously always emitted "entries required"), since that gap was exactly why the 1000+-seed fuzz suite never caught it in the first place). `SECTION_BUILDERS` lives in `registry.py` rather than inline in `ccd.py` since section templateIds are standardized across C-CDA document types generally - both `CcdBuilder` and `DischargeSummaryBuilder` reuse this exact table via `app/cda/common.py::build_sectioned_bundle`. **Import-direction note:** `registry.py` imports each concrete document builder class at module load time (same as `app/mappings/registry.py` imports each HL7v2 mapper class), but `build_sectioned_bundle()` also needs `SECTION_BUILDERS` to dispatch each section it walks — a top-level circular import if `common.py` imported `registry.py` back at its own module level. Solved with a function-local (not module-level) import inside `build_sectioned_bundle()`: `from app.cda.registry import SECTION_BUILDERS` runs only when the function executes, by which time `registry.py` has already finished loading.
- **`app/cda/ccd.py`** — `CcdBuilder` (`CCD_TEMPLATE_ID = "2.16.840.1.113883.10.20.22.1.2"`): `build_bundle()` is now just `return build_sectioned_bundle(document)` (see the `common.py` bullet above) - CCD is the "header + generic sections" shape that helper was extracted from. **An unrecognized section is silently skipped** — deliberate and disclosed, not a bug: this slice's section coverage is intentionally partial (Problems, Medications, Allergies, and Immunizations; other sections like Procedures/Results/Vital Signs are deferred to a later slice, following this project's own established "one thing per slice" precedent — verified via git history that ADT^A01 shipped alone before A02/A03/A04/A08 arrived together in the next commit).
- **`app/cda/problems.py`** — `build_conditions(section, patient_id) -> list[Condition]`, per the official "C-CDA on FHIR" IG (`build.fhir.org/ig/HL7/ccda-on-fhir/`, current v2.0.0 continuous build). Entry shape: `entry/act[templateId=...4.3]/entryRelationship[typeCode=SUBJ]/observation[templateId=...4.4]/value[xsi:type=CD]`. Both the Concern Act and Problem Observation templateIds are checked via `has_template_id` before use, not assumed from position alone — a real gap caught by re-checking a draft against the approved plan before any test ran against it. `negationInd="true"` on the Problem Observation ("no known problem" pattern) makes the entry skipped entirely, not mapped as if the coded value were asserted — a disclosed limitation, not modeled as its own resource this slice. **`clinicalStatus` is resolved from two separate vocabularies that must not be merged into one lookup table**: a nested Problem Status Observation (LOINC `33999-4`)'s SNOMED CT value, checked first and taking priority when present, falls back to the Concern Act's own act-lifecycle `statusCode` (`active`/`suspended`/`aborted`/`completed`) only when no status observation resolves - see `_resolve_clinical_status`. `effectiveTime` low/high → `onsetDateTime`/`abatementDateTime`, resolved via `ivl_ts_bounds` which itself handles all three legal `IVL_TS` shapes (bare `@value` point-in-time, `<low>`/`<high>` children, or `nullFlavor` for fully unknown). **`entryRelationship/@typeCode` was originally never checked**, only the nested element's templateId - despite CLAUDE.md's own entry-shape description above always having specified `typeCode=SUBJ`. A `<entryRelationship typeCode="REFR">` (or any non-`SUBJ` code) whose nested `<observation>` happened to carry the Problem Observation templateId was incorrectly mapped as an asserted problem; the same gap existed for the Status Observation lookup (should require `typeCode="REFR"` per the IG pattern, not just match on the nested code alone). Caught by a follow-up multi-agent code review and reproduced directly (a `REFR`-wrapped Problem Observation produced a `Condition` it shouldn't have) - fixed by checking `relationship.get("typeCode")` against the expected code (`"SUBJ"` for the act-level loop, `"REFR"` for the status-observation loop) before descending into the nested element in both `build_conditions` and `_resolve_clinical_status`.
- **`app/cda/medications.py`** — `build_medication_requests(section, patient_id) -> list[MedicationRequest]`, per the official "C-CDA on FHIR" IG's `CF-medications.html` guidance and its underlying `CCDA-FHIR MedicationRequest.csv` mapping table (`github.com/HL7/ccda-on-fhir/blob/master/mappings/CF/`), verified by fetching both directly rather than assumed from field-name similarity to Problems. Entry shape: `entry/substanceAdministration[templateId=...4.16]` (a Medication Activity is a `substanceAdministration` directly - no wrapping Act, unlike Problems' Concern Act). Two published ConceptMaps, kept as separate dicts since they're genuinely different vocabularies: `STATUS_MAP` (`statusCode`, HL7 `ActStatus` → `MedicationRequest.status` - `active`→`active`, `suspended`→`on-hold`, `aborted`→`stopped`, `completed`→`completed`, `nullified`→`entered-in-error`; unrecognized/absent falls back to `"unknown"`) and `_MOOD_TO_INTENT` (`moodCode` → `MedicationRequest.intent` - `INT`→`"order"`, `EVN`→`"plan"`; this reads backwards at first glance but is the IG's own mapping, both rows marked "maps loosely to" since CDA mood codes are broader than FHIR intent codes). **`intent` turned out to be FHIR-required despite not showing up via `model_fields` introspection** - confirmed by constructing `MedicationRequest` directly (`status` too; only `subject` appears as `is_required()` in the model's own field metadata, the same "don't trust the library's declared cardinality" lesson `Appointment.status` already taught, but this time in the *stricter*-than-declared direction rather than the looser one) - an unrecognized/absent `moodCode` falls back to `"order"` rather than leaving a required field unset. Structured dosing (`routeCode`→`Dosage.route`, `doseQuantity`/`rateQuantity`→`Dosage.doseAndRate`, `effectiveTime` low/high→`Dosage.timing.repeat.boundsPeriod`) and free-text SIG (a nested `entryRelationship[typeCode=COMP]/substanceAdministration[templateId=...4.147]` "Medication Free Text Sig" whose `<text>` → `Dosage.patientInstruction`) are alternatives in real C-CDA, not both always present - `_build_dosage` returns `None` (omitting `dosageInstruction` entirely) only when neither is present, matching `Dosage` having no required fields itself. `doseQuantity`/`rateQuantity` are read as simple PQ (`@value`/`@unit` directly on the element) only - an `IVL_PQ` range shape (`<low>`/`<high>` children instead) is left unmapped rather than guessing which bound to report as a fixed dose, since the IG's own CSV doesn't disambiguate which shape governs this target field (noted `"Is SXPR used?"` in its own comments column). `negationInd="true"` (this specific administration/order did NOT happen) skips the entry entirely, mirroring Problems' negation philosophy. `consumable/manufacturedProduct/manufacturedMaterial/code` with no resolvable coded value also skips the entry - `medicationCodeableConcept` (or `medicationReference`, not produced by this converter) is required by `fhir.resources.R4B.MedicationRequest`, confirmed by construction the same way `intent`/`status` were. **Deliberately not mapped, per the CSV's own disclosed gaps** (each row explicitly marked "not supported" or "best pattern unclear" in the source table, not silently dropped): `entryRelationship[indication]` (target field genuinely undecided in the IG itself), performer/requester Practitioner references (would need a CDA-side XCN-equivalent practitioner-builder this slice doesn't add), Supply Order / Medication Dispense / Reaction Observation / Drug Monitoring entry relationships.
- **`app/cda/allergies.py`** — `build_allergy_intolerances(section, patient_id) -> list[AllergyIntolerance]`, per the IG's `CF-allergies.html` guidance and `CCDA-FHIR Allergy.csv`. Entry shape mirrors Problems' Concern-Act wrapper (`entry/act[templateId=...4.30]/entryRelationship[SUBJ]/observation[templateId=...4.7]`), but the observation itself nests notably more sub-structure, each gated by its own `typeCode` per the same "check the relationship type, not just the nested templateId" discipline `_find_nested_observation` centralizes: a Status Observation (`entryRelationship[REFR]`, templateId `...4.28`, LOINC `33999-4`) for `clinicalStatus`, a Criticality Observation (`entryRelationship[SUBJ, inversionInd=true]`, templateId `...4.145`, LOINC `82606-5`) for `criticality`, and any number of Reaction Observations (`entryRelationship[MFST, inversionInd=true]`, templateId `...4.9`) each optionally carrying its own nested Severity Observation (`entryRelationship[SUBJ, inversionInd=true]`, templateId `...4.8`) for `reaction.severity` - the allergen itself lives at `participant[@typeCode=CSM]/participantRole/playingEntity/code`, a shape neither Problems nor Medications has (verified against a real HL7 C-CDA-Examples allergy entry, not assumed from the CSV alone). Four small ConceptMaps, each its own dict since they're independently-keyed vocabularies: `_TYPE_MAP`/`_CATEGORY_MAP` (both keyed off the *same* Allergy-Intolerance Observation `<value>` SNOMED code, but targeting `type`/`category` respectively - a code can be type-mapped without being category-mapped, e.g. "Allergy to substance" `419199007`, an intentional fuzz case), `CLINICAL_STATUS_MAP` (public, reused by the generator; the *values* are identical to `app.cda.problems.STATUS_OBSERVATION_VALUE_TO_CLINICAL_STATUS` since both sections share the one generic Status Observation template, but kept a separate dict/CodeableConcept construction since `AllergyIntolerance.clinicalStatus` binds to a different terminology system, `allergyintolerance-clinical`, than `Condition.clinicalStatus`'s `condition-clinical`), `CRITICALITY_MAP` (local `HL7ObservationValue` codes `CRITH`/`CRITL`/`CRITU`, not SNOMED), `SEVERITY_MAP` (SNOMED). **A real, disclosed divergence from Problems' negation handling**: Problems skips a `negationInd="true"` entry entirely, but the IG's own `CCDA-FHIR Allergy.csv` gives negated Allergy Observations a real target - a "no known allergy" `AllergyIntolerance` - so this module builds one rather than skipping, via `_resolve_allergen_code`'s two negation-only text fallbacks (a still-resolvable allergen → `code.text = "No known allergy to <display>"`; unresolvable/absent → the IG's exact `"No known allergies"` wording). The IG's *fully coded* negation crosswalk (`CF_AllergyIntoleranceAbsentCode`, mapping specific negated allergens to their own "no known allergy to X" SNOMED codes) was not found published in a verified, fetchable form - disclosed and left unimplemented rather than guessed at, same "don't guess at an unverified crosswalk" philosophy as MDM's TXA-17. `AllergyIntolerance.patient` (not `.subject`, unlike every other resource this app builds) and `.recordedDate` (not `.recorded`) were both confirmed by inspecting `model_fields` directly rather than assumed from naming-convention pattern-matching to `Condition`/`MedicationRequest`. `type`/`category`/`criticality` are bare `code` strings (not `CodeableConcept`, unlike `clinicalStatus`/`code`) - also confirmed by inspecting `model_fields` annotations before writing the constructor calls, per this project's established "always inspect, never guess" `fhir.resources` policy.
- **`app/cda/immunizations.py`** — `build_immunizations(section, patient_id) -> list[Immunization]`, per the IG's `CF-immunizations.html` guidance and `CCDA-FHIR Immunization.csv`. **The IG's own CSV splits Immunization Activity into two target resources by `moodCode`**: `EVN` (already administered/refused) → `Immunization`, `INT` (ordered/planned, not yet given) → `MedicationRequest`, with a mostly-disjoint field set on the `INT` side (`protocolApplied`/`doNotPerform`/`requester`). This module deliberately handles only `EVN` → `Immunization` - the section's own purpose ("history of vaccinations given") makes `EVN` the dominant real-world case, and a second, mostly-parallel `INT` → `MedicationRequest` path would roughly double this slice's scope for a rarely-populated shape; `INT`-mood entries are silently skipped (`build_immunizations`'s own mood filter), same disclosed-scope-limit treatment as an unrecognized section, not surfaced as a validation finding. Entry shape has no wrapping Act (`entry/substanceAdministration[templateId=...4.52]` directly, like Medications) - `consumable/manufacturedProduct/manufacturedMaterial/code` → `vaccineCode` (CVX-coded in practice) and `.../lotNumberText` → `lotNumber`, `routeCode`/`doseQuantity` map the same way Medications' structured dosing does. `STATUS_MAP` (public, reused by the generator) is the `CF_ImmunizationStatus` ConceptMap - but `negationInd="true"` overrides it unconditionally to `"not-done"` regardless of `statusCode` (per the ConceptMap's own comment that `completed`→`not-done` applies "only... when CDA negation is present and true" - every other source status already maps to `not-done` on its own, so checking negation first is equivalent and simpler than consulting the table for every code). `Immunization.status` has no `"unknown"` value (unlike most other status maps in this app - only `completed`/`entered-in-error`/`not-done` exist), so an unrecognized/absent non-negated `statusCode` defaults to `"completed"` rather than an artificial unknown, matching the same "default to the most common real value" judgment already made for Medications' `moodCode` fallback. **Two more required-but-not-`is_required()` surprises, both confirmed by constructing `Immunization` directly rather than trusting `model_fields`** (same lesson `MedicationRequest.intent` already taught): `status` is eagerly required despite not appearing in `model_fields`'s own required list, and `occurrence[x]` (`occurrenceDateTime`/`occurrenceString`) is a required one-of choice enforced *at construction*, not settable via attribute assignment afterward (like `Encounter.class_fhir`) - when `effectiveTime` doesn't resolve, this falls back to `occurrenceString = "Unknown"`, FHIR's own conventional representation for "administered, exact date unrecorded" (e.g. US Core's Immunization guidance), not a local guess. `primarySource` (the CSV's `_primarySource → Fixed value: "unknown"` row) is left unmapped entirely - `primarySource` is a plain FHIR `boolean`, and `"unknown"` isn't a valid boolean value, so passing the IG's own stated fixed value through would be invalid; disclosed and skipped rather than guessing at what was actually intended. Performer materialization (the CSV's `performer.actor → Reference`) is also disclosed-and-skipped, matching Medications' equivalent omission - this app has no CDA-side `assignedEntity → Practitioner` builder yet (the C-CDA equivalent of `app/mappings/common.py::build_practitioner_from_xcn` for HL7v2's XCN fields).
- **`app/cda/discharge_summary.py`** — `DischargeSummaryBuilder` (`DISCHARGE_SUMMARY_TEMPLATE_ID = "2.16.840.1.113883.10.20.22.1.8"`): the second document type, and the first real proof that `build_sectioned_bundle` generalizes - `build_bundle()` is, like `CcdBuilder`'s, just `return build_sectioned_bundle(document)`. Confirmed structurally identical to CCD at the header level (`recordTarget`, `componentOf/encompassingEncounter`) by fetching a real HL7 C-CDA-Examples Discharge Summary and comparing directly, not assumed from the document-type name alone. **A real, disclosed scope limit, not a redesign**: Discharge Summary's own IG-required sections (Hospital Discharge Diagnosis, Hospital Course, Plan of Treatment, Discharge Medications) each use entry templates genuinely different from what this app's existing section builders recognize - Hospital Discharge Diagnosis Section (templateId `...2.24`) wraps its Problem Observation in a **Hospital Discharge Diagnosis Act** (templateId `...4.33`), not Problems' Concern Act (`...4.3`); Discharge Medications Section (templateId `...2.11.1`) wraps its medication entry in a **Discharge Medication Act** (templateId `...4.35`), not a bare `substanceAdministration`; Hospital Course is narrative-only (no structured entries without a proper FHIR Composition, already an out-of-scope item); Plan of Treatment's entry shape is too heterogeneous for one resource type. Verified directly against a real Discharge Summary example (not assumed): alongside these discharge-specific sections, it also carried a plain Problem List section and a plain Immunizations section using the exact templateIds this app already recognizes - so a real Discharge Summary does convert to something useful (header + whatever already-recognized sections it also happens to carry) even without the discharge-specific ones, which are silently skipped, the same "unrecognized section" treatment `build_sectioned_bundle` already gives any section without a registered builder. The same real example also surfaced the Allergies "entries optional" section-templateId gap fixed in the `registry.py` bullet above.
- **Format auto-detection (`app/pipeline.py`)** — `is_xml(raw_text)` strips a leading BOM **before** whitespace (not after: the BOM character isn't itself whitespace, so a leading BOM stops a whitespace-only `lstrip()` before it ever reaches the whitespace that follows it — this exact ordering bug was caught by direct testing before shipping), then checks for a leading `<`. `convert_to_bundle`/`validate_any` dispatch to `convert_cda_to_bundle`/`convert_hl7_to_bundle` and `validate_cda`/`validate_hl7` accordingly. This keeps the single unified "paste anything, click Convert/Validate" UX every prior HL7v2 message type has used — never a new route/UI branch per input format.
- **`app/cda/generator.py`** — `generate_ccd(rng)`/`generate_discharge_summary(rng) -> str`, the C-CDA mirror of `app/generators/{adt,siu,oru,mdm}.py`, but living inside `app/cda/` rather than `app/generators/`: there are only two document types so far, so a separate `app/generators/cda.py` with its own sub-registry would be premature relative to HL7v2's real 4-type/20-trigger registry need. Both generator functions are thin wrappers around a shared `_generate_sectioned_document(rng, document_template_id, doc_code, doc_code_display, title, force_encounter=False)` - the generator-side mirror of `build_sectioned_bundle` above, extracted the same "second real consumer" way once `generate_discharge_summary` existed. `force_encounter=True` for Discharge Summary (unlike CCD, where `componentOf/encompassingEncounter` is genuinely optional and stays a 50/50 `maybe()`) - a real discharge summary is inherently tied to one hospitalization, so `_random_encounter` gained a `force: bool` parameter to skip its own presence check when set. Reuses `app/generators/base.py`'s format-agnostic primitives directly (`maybe()`, `random_person_name()`, `random_address()`, `random_phone()`, `random_sex()`, `random_identifier()`, `random_datetime_near_now()`/`format_hl7_datetime()` - the latter's `YYYYMMDDHHMMSS` output is exactly CDA's own `@value` TS digit shape) rather than re-deriving name/address pools; net-new is only a small SNOMED problem-code pool, an RxNorm medication-code pool (plus a small route-code and free-text-SIG pool for the Medications section), and the XML field builders. Built via f-string templates (same style as the hand-authored `ccd_*.xml` fixtures), not `ElementTree` tree-building, and self-checked via `parse_document()` before returning (mirrors `_assemble()`'s `parse_message()` self-check in the HL7v2 generators) - full-conversion-success verification is left to `tests/test_generate_cda.py`, matching the HL7v2 precedent. **Every random value is drawn from the passed-in `rng`, never `uuid.uuid4()`** - `uuid4()` uses its own unseeded internal randomness and would silently break the "same seed → same output byte-for-byte" guarantee every generator in this project must uphold; `_random_uuid_like(rng)` builds a UUID-shaped root string entirely from `rng.choice()` calls instead. Field-population policy deliberately exercises both branches of everything the review-caught `common.py`/`problems.py` bugs above involved (root-only vs. root+extension `id`s, date-only vs. full-timestamp `effectiveTime`, recognized vs. unrecognized encounter class, Concern-Act-only vs. nested-Status-Observation `clinicalStatus`), while keeping onset/birth date ranges constrained so no combination can ever trip an error-severity validation rule (see the file's own comments for the exact day-count bounds and why) - the same "guarantee convertibility/validity by construction" contract the HL7v2 generators already keep. `_random_medication_entry` follows the identical philosophy for the Medications section: `moodCode` splits ~50/50 INT/EVN, `statusCode` is mostly a recognized `STATUS_MAP` key (~85%) with an occasional unrecognized one (`new`/`held`, exercising the `"unknown"`-fallback validation finding), and dosing representation splits ~45/35/20 across structured-only/free-text-only/neither - direct fuzz coverage of `_build_dosage`'s three branches, mirroring how the Problems entry generator exercises `_resolve_clinical_status`'s two branches. `_random_allergy_entry` covers the Allergies section's larger branch space the same way: ~10% `negationInd`, and within that ~30% still carrying a resolvable allergen vs. a `nullFlavor` one (both `_resolve_allergen_code` negation paths); the Status Observation (~50%), Criticality Observation (~40%), and Reaction Observation with its own optional nested Severity Observation (~50%/~60%) are each independently `maybe()`-gated, so every nesting depth this section supports gets exercised in some combination across seeds. `_random_immunization_entry` splits `moodCode` ~80/20 EVN/INT (direct fuzz coverage of `build_immunizations()`'s mood-based skip - the INT branch must produce zero `Immunization` resources from that entry), and within EVN further splits ~15% negated; `statusCode` is mostly a recognized `STATUS_MAP` key with an occasional unrecognized one (`"draft"`, exercising the `"completed"`-fallback validation finding); dosing (`routeCode`+`doseQuantity`) and `lotNumberText` are each independently `maybe()`-gated. Registered in the *existing* `app/generators/registry.py::_GENERATORS` flat dict as `("CDA", "CCD")`/`("CDA", "DISCHARGESUMMARY")` (see above) rather than a parallel CDA-specific registry - `DISCHARGESUMMARY` is uppercase (unlike the human-readable `"DischargeSummary"` label) to match `generate()`'s own `.upper()`-normalized lookup, which requires its dict keys to already be uppercase, same as every HL7v2 trigger value.
- **`app/cda/validation.py`** — `validate_document(document) -> ValidationReport`, the C-CDA mirror of `app/validation/{generic,adt,engine}.py`, composed the same small-`_rule_*`-functions-by-concatenation way. Still no `get_type_validator`-style dispatch-by-document-type registry even with two document types now - every section-level rule (Problems/Medications/Allergies/Immunizations) walks the document generically (`component/structuredBody/component/section`, exactly what `build_sectioned_bundle` walks too) rather than branching on which document type it's in, so a CCD and a Discharge Summary carrying the same recognized section get the same findings for free; only `_resolve_trigger_event(document)` needs to know about both document types by name (checks `CCD_TEMPLATE_ID` then `DISCHARGE_SUMMARY_TEMPLATE_ID`, returning `"CCD"`/`"DISCHARGESUMMARY"`/`None` - uppercase to match every other trigger-event string in this app and `app/generators/registry.py::generate()`'s own normalized lookup). Reuses `app.validation.models.ValidationFinding`/`ValidationReport` as-is (a CDA finding uses a path-like string for `segment`, e.g. `"recordTarget/patientRole/patient/administrativeGenderCode"`, `field` left `None`) and `app.validation.common.parse_comparable_datetime`/`not_in_future`/`is_before` directly, since CDA's `@value` uses the identical HL7-TS digit shape. Rules mirror `adt.py`'s explicit "surface what the mapper already silently defaults/skips" philosophy: a Problem Observation with no resolvable coded value is an `info` finding ("the converter will silently skip this entry") even though `build_conditions()` itself never raises for it; an unrecognized encounter class code is `info` ("will silently default to AMB"), reusing `app.cda.common.RECOGNIZED_ENCOUNTER_CLASSES` directly rather than a re-derived copy. The Medications section follows the same pattern via `_iter_medication_activities` (walking entries the identical way `build_medication_requests()` does, so validation can never see a different entry set than conversion) and three rules: `cda.medication-missing-code` (`info` - mirrors the Problem Observation missing-value rule exactly, skipped for negated entries since the converter itself never evaluates those), `cda.medication-status-unrecognized` (`info` - reuses `app.cda.medications.STATUS_MAP` directly, same "will silently default to X" wording as the encounter-class rule), and `cda.medication-period-end-before-start` (`error` - dosing `effectiveTime` high before low, reusing `is_before` the same way the Problems abatement-before-onset and Encounter period-end-before-start rules already do). Allergies gets the same treatment via `_iter_allergy_observations` and four rules: `cda.allergy-missing-allergen` (`info` - skipped for negated entries, since `_resolve_allergen_code` gives those a real text-only fallback rather than skipping them, unlike every other "missing code" rule in this file), `cda.allergy-onset-in-future` (`warning`) and `cda.allergy-onset-before-birth` (`error`) mirroring Problems' onset rules exactly, and `cda.allergy-reaction-missing-manifestation` (`info` - a Reaction Observation with no resolvable `<value>`, surfacing `_build_reaction`'s own skip-the-reaction behavior). Immunizations gets three rules via `_iter_evn_immunization_activities` (which, like the mapper's own walk, excludes `INT`-mood entries entirely rather than flagging them - a scope limit, not a data-quality issue): `cda.immunization-missing-vaccine-code` (`info`), `cda.immunization-status-unrecognized` (`info` - only evaluated for non-negated entries, since `negationInd="true"` overrides `status` unconditionally in the mapper regardless of `statusCode`'s value), and `cda.immunization-occurrence-in-future` (`warning`). Convertibility is checked last, mirroring `app/validation/engine.py::_check_convertibility()` exactly: call `get_document_builder(document)` (unregistered → `info` finding), then `.build_bundle(document)` (`MappingError`/`MissingSegmentError`/`pydantic.ValidationError` → `error` finding; anything else → logged + `error` finding) - the same load-bearing "never re-derive a second required-fields table, just run the real builder" decision already made for HL7v2. `app/cda/pipeline.py::validate_cda(raw_xml)` parses then delegates, mirroring `convert_cda_to_bundle`'s exact shape - it raises only `CdaParseError` (unlike `validate_hl7`, there's no second raise-worthy case: HL7v2's "MSH itself absent" maps to a malformed/wrong-root document here, already `CdaParseError` from `parse_document`). **`_rule_encounter`'s period-timing checks originally lived entirely inside `if low:`**, so an `IVL_TS` with only `@high` (known end, unknown start - a legal shape `ivl_ts_bounds()` returns as `(None, high)`) silently produced *zero* encounter findings even when the known end date was implausibly in the future - caught by a follow-up multi-agent code review, reproduced directly. Fixed by computing `low_dt`/`high_dt` independently up front and adding a dedicated `cda.encounter-period-end-in-future` check for the no-`low`/future-`high` case, rather than nesting everything under `low`'s truthiness.
- **Known, disclosed scope limits for this slice**: two document types (CCD, Discharge Summary), four sections (Problems, Medications, Allergies, Immunizations) recognized on either, Discharge Summary's own required sections (Hospital Discharge Diagnosis, Discharge Medications, Hospital Course, Plan of Treatment) not yet recognized (see `discharge_summary.py`), no proper FHIR-Document `Bundle(type="document")`/`Composition` (author/custodian would become load-bearing), no narrative-`<text>`/`originalText` resolution when `displayName` is absent (falls back to code-only). All are natural, already-scoped follow-ups on the infrastructure above, not redesigns.

### `hl7` library gotcha (important)

The `hl7` package (PyPI: `hl7`, i.e. python-hl7) is used for HL7v2 parsing:
- `hl7.parse()` **always** splits segments on `\r`, regardless of input. `app/hl7/parser.py::parse_message()` normalizes `\n`/`\r\n` input (e.g. from a browser textarea or an uploaded file) to `\r` before calling it, and drops blank lines.
- When a field/repetition has no component separator (`^`), the library collapses it to a bare Python `str` instead of a nested `[component]` list. Naively indexing a second level (`field[0][0]`) on such a field does **character** indexing, not component indexing, and silently returns the wrong (truncated) value. `app/hl7/parser.py::component_str()` guards against this and is the only sanctioned way to pull a component out of a field/repetition — always use it (or `field_str()`, which wraps it) instead of raw indexing when adding a new mapper.
- The library splits on `^` **purely syntactically, with no awareness of HL7 data types** — it splits a field the same way whether the field is genuinely composite (XCN, CWE, PL, ...) or an unstructured free-text type (`ST`/`FT`/`TX`) where a literal `^` is just a character a user typed, not a component separator. `field_str()`'s `component=1` default is correct for the former but silently **truncates** the latter at the first `^`. `app/hl7/parser.py::raw_field_str(segment, field_num, repetition=0)` returns the field's full original text in both cases (it's a bare string already when the library didn't split it, and gets rejoined with `^` via `str()` when it did) — use this, not `field_str()`, for any `ST`/`FT`/`TX`-typed field (e.g. `OBX-5` when `OBX-2` is one of those types, `NTE-3`, `TXA-25`). This exact truncation bug shipped once in both `app/mappings/oru.py`'s `_build_observation_value` and `app/mappings/mdm.py`'s `_build_binary_from_obx` (both read free-text `OBX-5` via `field_str`) and was caught by code review, not the original test suite — see `tests/test_hl7_parser.py::test_raw_field_str_preserves_a_caret_that_field_str_would_truncate` and the matching regression tests in `test_oru_mapping.py`/`test_mdm_mapping.py`.

### `fhir.resources` library notes

- Resources are imported from the `R4B` subpackage (`fhir.resources.R4B.*`), not the root package — as of `fhir.resources` v7+, the root package defaults to FHIR R5. R4B did not change `Patient`/`Encounter`/`Bundle`/`Appointment`/`Practitioner`/`Location`/`Device`/`DiagnosticReport`/`Observation`, so it's a safe practical stand-in for R4 here.
- `Encounter.class` is a required field exposed as the Python attribute `class_fhir` (since `class` is a reserved word) — it must be passed as a constructor kwarg (`Encounter(..., class_fhir=Coding(...))`), not set as an attribute after construction, because required fields are validated eagerly on `__init__`. `Appointment` has no such reserved-word field and can be built incrementally (construct with just `id`/`status`/`participant`/`extension`, then set the rest via attribute assignment).
- Bundles use `Bundle.type = "collection"` (not `"transaction"`) since there's no FHIR-server interaction in this app.
- Before using a resource sub-object you haven't used before (e.g. `EncounterHospitalization`, `AppointmentParticipant`, `DeviceDeviceName`, `ObservationReferenceRange`), inspect its real `model_fields` rather than guessing field names/shapes — this was done for `dischargeDisposition` when adding A03 discharge mapping, for `Appointment`/`AppointmentParticipant` when adding SIU, and for `Practitioner`/`Location`/`Device`/`DiagnosticReport`/`Observation` when adding resource materialization and ORU. Also don't assume the library enforces FHIR's own cardinality/binding rules: `fhir.resources.R4B.Appointment` doesn't actually require `status` at construction time (only `participant`) even though the FHIR spec calls status 1..1, and it does **not** validate that status/participant-status strings are real codes from the spec's value sets — getting the *values* right (not just the field names) is entirely on the mapper. Confirm real code values against the FHIR spec pages (e.g. `valueset-appointmentstatus.html`), not memory. `Practitioner`/`Location`/`Device` have **no required fields at all** (unlike `Encounter`/`Appointment`/`DiagnosticReport`/`Observation`, which each require at least one) - they can be built incrementally with nothing but an `id`.
- `Quantity.value` (used for `Observation.valueQuantity`, e.g. from OBX-5/6) deserializes as `decimal.Decimal`, not `float` - `Decimal('7.2') == 7.2` is `False` in Python, so comparisons in tests need `float(obs.valueQuantity.value) == 7.2` or a `Decimal` literal, not a bare float equality check.

### HL7 SCH/SIU-shaped facts worth remembering

- The `TQ` composite data type (used in the legacy `SCH-11` field) has **component 4 = start date/time, component 5 = end date/time** — not components 1/2 as might be assumed from a generic "timing" field. `TQ1` (the segment that superseded embedding TQ in SCH-11) is much simpler: TQ1-7 = start, TQ1-8 = end, both plain `DTM` fields. `app/mappings/siu.py::resolve_appointment_timing()` prefers TQ1, falls back to SCH-11 — resolved **per-field** (start and end independently), not all-or-nothing: a TQ1 segment that supplies only a start (no end) still lets a usable SCH-11 end value through, rather than leaving `Appointment.end` blank just because TQ1 supplied *something*. Get this wrong (checking `if start or end` instead of resolving each independently) and a partially-populated TQ1 silently blocks a complete SCH-11 fallback — this exact bug shipped once and was caught by code review, not by the original test suite (see `tests/test_siu_s12_mapping.py::test_partial_tq1_falls_back_to_sch11_per_field`).
- `_resolve_minutes_duration` prefers **TQ1-6 over SCH-9/10** (matching `resolve_appointment_timing`'s TQ1-over-SCH11 preference) specifically so a reschedule (S13) with a stale SCH-9 duration but a fresh TQ1-derived start/end doesn't produce a self-contradictory Appointment where `minutesDuration` doesn't match `end - start`. The SCH-10 unit check is lenient (`startswith("MIN")`) rather than an exact match, to tolerate spellings like `"MINUTES"`.
- `parse_hl7_datetime` (`app/fhir_models/builders.py`) preserves a trailing HL7 timezone offset (`+/-ZZZZ`) rather than dropping it and mislabeling the result `Z` (UTC) — silently wrong-by-hours timing is a real scheduling error, not a cosmetic issue, once this helper feeds `Appointment.start`/`end`/`created`.
- `RGS` (Resource Group Segment) is purely structural (sequencing/action-code only, no clinical content) — SIU's `AIS`/`AIG`/`AIL`/`AIP` segments are read directly via `optional_segments()` without tracking which `RGS` group they belong to, since FHIR's `Appointment.participant` is a flat list with no group-nesting concept to preserve anyway.
- `Appointment.participant.type`'s recommended value set (`encounter-participant-type`, Extensible binding) has no code for "patient" or for a location/equipment role — only practitioner-ish roles like `ATND`. Don't force a non-fitting code in just to fill the field; omit `type` when nothing in the binding actually fits (see `app/mappings/siu.py::_build_participants`).
- **AIP/AIL/AIG participants are materialized as real resources, not display text** - and each participant `Reference` carries both `reference` (the real resource, by `urn:uuid`) *and* `display` (human-readable text), per FHIR's own guidance that `display` SHOULD be populated even when `reference` is present, for consumers that render a participant list without resolving the whole Bundle. Per the official v2-to-FHIR ConceptMaps, `AIP-3` → `Appointment.participant.actor` = `Reference(Practitioner)` and `AIL-3` → `Reference(Location)` are fixed targets; both use the shared `build_practitioner_from_xcn`/`build_location_from_pl` from `common.py` for the resource, and `person_display`/`location_display` for the matching `Reference.display` text. `AIG` ("general resource") has **no single fixed target** in the official mapping - the real resource type depends on what `AIG-4` (Resource Type, a local/user-defined table) says the resource actually is. `app/mappings/siu.py::_build_aig_resource` branches on it: a location-ish `AIG-4` code (`LOCATION`/`ROOM`) builds a `Location`, anything else (the common case) builds a `Device` whose `.type` preserves the AIG-4 category (not just used to pick the branch and then discarded). Unlike AIP/AIL, this is built **directly** from AIG-3/4's components rather than routed through `build_location_from_pl` - AIG-3/4 is CWE-shaped, not PL, and the two only coincidentally look similar (both have two leading components); reusing the PL-scoped helper here worked by accident the first time this was written, not by design, and was fixed once caught by review. This is a disclosed interpretation, not something the spec hands you directly - if a real-world sender uses a different `AIG-4` vocabulary, `_AIG_LOCATION_TYPE_CODES` is the place to extend it.
- **`Appointment.comment` concatenates every `NTE` in the message**, not just the first one (`build_appointment_core` in `app/mappings/siu.py`). This replaced an earlier, buggier version that took only `nte_segments[0]` regardless of which segment it actually trailed, which could pick an AIS/AIG/AIL/AIP-scoped note over a more relevant SCH-level one just because it happened to appear first. **Known, disclosed limitation that remains:** every NTE is treated as appointment-scoped and folded into one comment (joined with `\n`) with no group-scoping - an SCH-level note and an AIP-scoped personnel note end up indistinguishable in the output, since `Appointment.comment` is a single field with no place to preserve which segment each note trailed, and no separate field exists for per-participant notes. Fixing *that* properly would require positionally tracking which segment each NTE follows (the same kind of group-tracking `app/hl7/parser.py::group_segments_by_leader` provides for ORU's OBR/OBX) and then deciding what to do with a non-SCH-scoped note, which has no home in FHIR's `Appointment` shape - a real scope decision, not a one-line fix. NTE-3 is read via `raw_field_str`, not `field_str` (see the `hl7` library gotcha above) - it's an `FT` free-text field, so a literal `^` in a clinical note must not get truncated at component 1. The join separator is `\n` rather than `"; "` specifically because a semicolon is a much more plausible substring of real clinical-note text than a newline, though neither separator fully eliminates the ambiguity of folding multiple notes into one field with no boundary markers.

### HL7 ORU/OBR/OBX facts worth remembering

- **OBR/OBX grouping is not optional, unlike SIU's RGS.** An ORU message can carry multiple `OBR` (one per ordered panel/report), each followed by its own run of `OBX` result segments. Which `OBX` belongs to which `OBR` is semantically load-bearing: `DiagnosticReport.result` must reference only the `Observation`s built from *its own* group's `OBX` segments, not every `OBX` in the message. This is exactly what `group_segments_by_leader(message, "OBR", ["OBX"])` is for - see `app/mappings/oru.py::BaseOruMapper.to_bundle`.
- **OBX-2 (Value Type) drives which `Observation.value[x]` choice is populated from OBX-5**: `NM` → `valueQuantity` (with OBX-6 as `.unit`), `ST`/`FT`/`TX` → `valueString`, `CE`/`CWE`/`CNE`/`IS` → `valueCodeableConcept`, `DT`/`DTM` → `valueDateTime`. Other value types (`SN`, `NA`, `ED`, ...) are left unset rather than guessed at - see `app/mappings/oru.py::_build_observation_value`.
- **OBX-11 (Result Status) / OBR-25 (Result Status) → `Observation.status` / `DiagnosticReport.status`** both draw from the same core HL7 status codes (table 0085/0123): `F`→`final`, `P`→`preliminary`, `C`→`corrected`, `A`→`amended`, `X`→`cancelled`, `D`/`W`→`entered-in-error`. Codes with no FHIR equivalent (`B`, `I`, `N`, `O`, `R`, `S`, `U`, `V`, ...) fall back to `"unknown"` (a real `Observation`/`DiagnosticReport` status code) rather than raising or guessing - see `app/mappings/oru.py::_RESULT_STATUS_MAP`.
- **`Encounter.status` for ORU's optional PV1-derived Encounter is honestly `"unknown"`**, not inferred the way ADT's `AdtA08Mapper` infers it - ORU's PV1 gives result-reporting context, not an admit/discharge lifecycle trigger, so there's no signal to infer a real status from.
- **OBX-16 (Responsible Observer) Practitioners are deduped within a message**, keyed by the XCN's id component (component 1), via a `performer_cache: dict[str, Practitioner]` created once per `to_bundle()` call and threaded through every `build_observation()` call for that message (see `app/mappings/oru.py::_resolve_performer`). A report panel commonly has every result verified by the same physician; without this, an N-result panel would produce N near-identical `Practitioner` resources referencing one real person instead of one resource referenced N times. An OBX-16 with no id component (family/given only) still gets its own fresh `Practitioner` each time, since there's no reliable key to dedupe on.
- **OBR-4 → `DiagnosticReport.code` and OBX-3 → `Observation.code` are both FHIR-required** (`fhir.resources.R4B` enforces this at construction). If either is genuinely empty in malformed input, resource construction raises `pydantic.ValidationError` naturally - already handled by the existing "FHIR validation error" (422) category in `app/routes/convert.py`, no special-casing needed.
- **ORU's free-text `OBX-5` values (`ST`/`FT`/`TX`) are read via `raw_field_str`, not `field_str`** — see the `hl7` library gotcha above.

### HL7 MDM/TXA facts worth remembering

- **The v2-to-FHIR IG ships exactly one MDM ConceptMap** (`MDM_T02` → `Bundle`) and treats the `TXA` segment map as trigger-agnostic — confirmed via `build.fhir.org/ig/HL7/v2-to-fhir`'s `artifacts.html`. There's no IG-published guidance distinguishing T02/T04/T06/T08/T10/T11's field-level handling, which is why `app/mappings/mdm.py::BaseMdmMapper` is non-trigger-polymorphic like ORU, not like ADT/SIU.
- **TXA → DocumentReference field map** (verified against the real IG ConceptMap page, not memory): TXA-2 Document Type → `type`, TXA-3 Content Presentation → `content.attachment.contentType` (1..1 in the IG), TXA-6 Origination Date/Time → `date`, TXA-9 Originator → `author` (Practitioner), TXA-10 Assigned Authenticator → `authenticator` (Practitioner), TXA-12 Unique Document Number → `masterIdentifier`, TXA-16 Unique Document File Name → `identifier`, TXA-18 Confidentiality Status → `securityLabel`, TXA-19 Availability Status → `status`, TXA-25 Document Title → `description`. TXA-17 (Completion Status → `docStatus`) is deliberately **not** mapped — no verified code crosswalk from TXA-17's table values to FHIR's 4-code `CompositionStatus` value set was found, and passing an unverified raw code through risked emitting a non-compliant value; omitted rather than guessed, same philosophy as ORU's OBX-11 status map falling back to `"unknown"` rather than inventing a mapping.
- **TXA-19 → `DocumentReference.status` only has one verified mapping** (`"AV"` → `"current"`); every other/absent value also defaults to `"current"` (matching the IG's own stated default) rather than guessing at a fuller crosswalk - see `app/mappings/mdm.py::_resolve_status`.
- **Document *content* is carried by `OBX` segments following `TXA`, not by `TXA` itself** — the IG doesn't show a worked content-transfer example, so this app's approach (every `TX`/`FT`-typed `OBX-5` value concatenated into a single plaintext body, base64-encoded into a separate `Binary` resource referenced via `DocumentReference.content.attachment.url = urn:uuid:...`) is a disclosed extension of the IG's intent, not something the IG hands you directly. A message with no usable OBX content still converts successfully - it just gets no `Binary` and an `Attachment` with no `url` (valid FHIR - `Attachment` has no required fields). OBX-5 is read via `raw_field_str`, not `field_str` - see the `hl7` library gotcha above.
- **TXA-3 (Content Presentation, HL7 table 0191) → a real MIME type has no IG-published crosswalk** - `app/mappings/mdm.py::_CONTENT_PRESENTATION_TO_MIME_TYPE` is a disclosed, local judgment call (same category as SIU's `_AIG_LOCATION_TYPE_CODES`) covering the most common real-world codes (`TEXT`/`FORMATTED`/`HTML`/`XML`/`RTF`/`PDF`/`JPEG`); anything unrecognized falls back to `text/plain` rather than leaving `contentType` unset, since it's a required-by-the-IG 1..1 target field.
- **TXA-9 (Originator) and TXA-10 (Assigned Authenticator) are deduped when they identify the same real person** (matching XCN id component), reusing one materialized `Practitioner` referenced from both `DocumentReference.author` and `.authenticator` rather than building two near-identical resources - same rationale as ORU's OBX-16 `performer_cache`, see `app/mappings/mdm.py::build_document_reference`.
- **`fhir.resources.R4B.DocumentReference` requires `content` at construction** (unlike `Appointment`, which doesn't enforce its spec-required `status`) - confirmed by inspecting `model_fields` and constructing directly, not assumed. `Attachment` and `Binary` have **no required fields at all** (same "no required fields" pattern as `Practitioner`/`Location`/`Device`). `Binary.data` and `Attachment.data` both accept a base64-encoded `str` at construction and store it decoded as raw `bytes` (`pydantic`'s `Base64Binary` type handles the encode/decode automatically) - don't re-`base64.b64decode()` a constructed instance's `.data`, it's already raw bytes.

## Testing

`tests/fixtures/*.hl7` are synthetic, non-PHI HL7v2 messages. They were generated by building each segment as a list of positional fields joined with the correct field index (see git history of `tests/fixtures/` if regenerating) rather than hand-typing pipe-delimited strings — it's easy to miscount field positions (e.g. PV1-19 vs PV1-18) by hand. If adding a new fixture, verify field positions by parsing it back with `hl7.parse()` and checking each field you intend to rely on.

`tests/test_generate_adt.py` / `tests/test_generate_siu.py` / `tests/test_generate_oru.py` / `tests/test_generate_mdm.py` are property-based/fuzz tests over the generators (fixed seed ranges, so failures are reproducible) - they check: the message parses and carries the right MSH-9 trigger; fields documented as "required" above are non-empty across many seeds; fields documented as "optional" are genuinely both present *and* absent across enough seeds (this is the test that would catch a `maybe()` call accidentally hardcoded to always-true/always-false); and, most valuably, that `convert_hl7_to_bundle()` succeeds on every generated message across 20+ fixed seeds per trigger - this is real fuzz coverage of the mappers using far more field-value combinations than the static fixtures alone exercise, and is exactly why the required/optional policy above guarantees convertibility rather than leaving it to chance. `test_generate_oru.py` additionally fuzzes the OBR/OBX grouping guarantee itself (every `DiagnosticReport.result` reference resolves to a real `Observation`, and every generated `Observation` is referenced by exactly one report) - the kind of correctness property that's easy to get right on a hand-built fixture and wrong on a differently-shaped one. `test_generate_mdm.py` similarly fuzzes whether OBX document content varies both present and absent, exercising the with-`Binary`/without-`Binary` mapper paths. Each of the four files also has a `test_generated_message_has_no_validation_errors` case - `validate_hl7()` must report `is_valid=True` (zero **error**-severity findings, not zero findings of any severity) across the same seed ranges; `test_generate_oru.py`'s version is the one place this distinction actually matters, since the ORU generator deliberately produces `OBX-5` values outside their `OBX-7` reference range ~30% of the time, which is a legitimate `info`-severity finding, not a bug.

`tests/test_hl7_parser.py` has direct (non-fuzz) unit tests for `group_segments_by_leader` itself - correct grouping, no-leader-present, and members-before-the-first-leader-are-dropped - independent of any specific mapper, since it's meant to be reused by future message types. It also has direct unit tests for `raw_field_str` (see the `hl7` library gotcha above) confirming it preserves a `^`-containing free-text value that `field_str` would truncate, and matches `field_str` when no component separator is present; and for `optional_segment` (present/absent).

`tests/test_validation_generic.py` / `_adt.py` / `_siu.py` / `_oru.py` / `_mdm.py` are direct (non-fuzz) unit tests, one per rule, each against a small fixture built the same programmatic, field-position-verified way as every other fixture - deliberately not reusing generator output for these (a generator's random field values aren't a reliable way to hit one specific rule condition on demand). `tests/test_validation_common.py` directly unit-tests `parse_comparable_datetime`/`has_time_precision`/`not_in_future`/`parse_comparable_fhir_datetime` in isolation (full timestamp, date-only, empty, garbage, and calendar-invalid input) rather than only indirectly through a rule. `tests/test_validation_engine.py` covers the orchestrator: `is_valid` computed correctly from mixed severities, the unsupported-message-type path (including the registered-type-unmapped-trigger wording fix above), the `MappingError`-from-`to_bundle` gotcha above, and (via `monkeypatch`ing `app.validation.engine.get_mapper`) that a genuinely unexpected mapper crash is absorbed into a finding rather than propagating - a validator must never 500 on the exact malformed input it exists to flag. The four review-caught bugs above each have a dedicated regression test/fixture (`validation_adt_same_day_date_only_discharge.hl7` and `_birth.hl7`, `validation_generic_pid7_invalid_calendar_date.hl7`, `validation_oru_reversed_reference_range.hl7`, `validation_adt_a02_lowercase_trigger.hl7`, `validation_adt_unmapped_trigger_with_type_specific_issue.hl7`).

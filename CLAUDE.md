# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`interop-tools` (formerly `hl7-tools`, renamed as scope expanded beyond HL7v2) is a Python/FastAPI web app for converting healthcare messages/documents to FHIR R4 Bundles. The long-term goal (see README.md) covers transformation, validation, deduplication, test-data generation, and mapping across HL7v2/FHIR/CDA/C-CDA/EDI. Currently implemented:
- ADT — **A01 Admit, A02 Transfer, A03 Discharge, A04 Register, A05 Pre-admit, A08 Update, A11 Cancel Admit, A13 Cancel Discharge, A38 Cancel Pre-Admit** — each converting to a FHIR Bundle (Patient + Encounter).
- SIU — **S12 New booking, S13 Reschedule, S14 Modify, S15 Cancel, S17 Delete, S26 Patient No-Show** — each converting to a FHIR Bundle (Patient + Appointment + real Practitioner/Location/Device resources for the appointment's AIP/AIL/AIG participants, referenced by `urn:uuid`, not left as display-only text).
- ORU — **R01 Observation result, R30/R31/R32/R40 point-of-care result** — each converting to a FHIR Bundle (Patient + optional Encounter + one DiagnosticReport per OBR + one Observation per OBX, correctly grouped so each report only references its own results).
- MDM — **T02 New document, T04 Document status update, T06 Document addendum, T08 Document edit, T10 Document replacement, T11 Document cancel** — each converting to a FHIR Bundle (Patient + optional Encounter + DocumentReference + Binary for the document's OBX-carried text content), TXA → DocumentReference per the v2-to-FHIR IG.
- A synthetic HL7 message generator (`app/generators/`) covering all 26 combinations above, with realistic field-level randomization, selectable from a UI dropdown or `/api/generate`.
- A message **validator** - independent of conversion, runs against any message/document and returns a report of `error`/`warning`/`info` findings, each pointing at the offending location, covering both structural correctness and healthcare data-quality plausibility (a birth date in the future, a discharge before an admit, an appointment ending before it starts). Reachable via the **Validate** button in the UI or `/api/validate`, dispatched by input format via `app/pipeline.py::validate_any` - `app/validation/` for HL7v2, `app/cda/validation.py` for C-CDA.
- **C-CDA → FHIR** (`app/cda/`) - the app's first non-HL7v2 *input format* (XML, not pipe-delimited). Three document types: **CCD** (Continuity of Care Document), **Discharge Summary**, and **History and Physical Note**, all sharing the same header (Patient + optional Encounter) and section-dispatch infrastructure via `app/cda/common.py::build_sectioned_bundle` - seven sections recognized on any of the three document types: **Problems** → `Condition`, **Medications** → `MedicationRequest`, **Allergies** → `AllergyIntolerance`, **Immunizations** → `Immunization` (administered/refused entries only - see the C-CDA subsection for the disclosed planned-immunization scope limit), **Vital Signs** → an `Observation` panel (`.hasMember`) wrapping one `Observation` per vital sign, **Results** → `DiagnosticReport` (`.result`) wrapping one `Observation` per result, and **Procedures** → `Procedure` - each of the last three registered under both its "entries required" and "entries optional" templateId variants (see the C-CDA subsection's `procedures.py` bullet for the real, evidenced gap this closed). Discharge Summary's own IG-required sections (Hospital Discharge Diagnosis, Discharge Medications, Hospital Course, Plan of Treatment) and History and Physical's own IG-required narrative sections (Reason for Visit, History of Present Illness, Physical Exam, Assessment, Plan of Care, Review of Systems, Social History, Family History, General Status) each use entry shapes this app doesn't recognize yet, or are narrative-only, and are silently skipped - see the C-CDA subsection for the full disclosed scope limit. Input format is auto-detected (`app/pipeline.py`) so the same **Convert to FHIR**/**Validate**/**Generate sample** UI and `/api/convert`/`/api/validate`/`/api/generate` endpoints handle any of the three formats - no separate route/UI. See the C-CDA subsection below for the full shape.
- **X12 EDI → FHIR** (`app/edi/`) - the app's second non-HL7v2 *input format* (delimited text with self-describing delimiters, not pipe-delimited or XML). Phase 1: **270** (Eligibility Inquiry) → `CoverageEligibilityRequest`, **271** (Eligibility Response) → `CoverageEligibilityResponse`, both alongside a `Coverage` + payer `Organization` + subscriber (and optional dependent) `Patient` + provider `Organization`/`Practitioner`. Phase 2: **276** (Claim Status Request) / **277** (Claim Status Response) → `Task` (base FHIR R4 has no purpose-built claim-status-inquiry resource - see the EDI subsection below), one `Task` per claim-status entry, alongside payer/receiver/provider `Organization`/`Practitioner` and subscriber (and optional dependent) `Patient`. Phase 3: **278** (Health Care Services Review - Prior Authorization) → `Claim` (`use="preauthorization"`) always, plus a `ClaimResponse` referencing that same `Claim` when the message is a certification decision - **the one EDI pair sharing a single `ST01="278"`** for both directions (distinguished by `BHT02`, not `ST01`, unlike every other EDI family here), verified against real X12.org-published examples and, for the target FHIR shape specifically, against the official Da Vinci PAS IG. Phase 4: **835** (Health Care Claim Payment/Advice - Electronic Remittance Advice) → `PaymentReconciliation`, one `.detail[]` entry per claim payment - **the one EDI family with no `HL` hierarchy and no `BHT` segment at all**, a genuine structural break from every other family here (confirmed directly, not assumed). Phase 5: **837P** (Health Care Claim - Professional) → `Claim` (`use="claim"`, `type="professional"`) - the deepest, most cross-referential loop shape of any EDI phase here (a claim-level `HI` diagnosis list cross-referenced by position from each service line's own diagnosis-pointer composite). Phase 6: **837I** (Health Care Claim - Institutional) → `Claim` (`use="claim"`, `type="institutional"`) - **the one EDI trio in this app sharing a single `ST01="837"` with no `BHT02`-style field inside the transaction set to distinguish the variants** (unlike 278's own request/response split), disambiguated instead by `ST03` (verified as the officially authoritative field for exactly this - see the EDI subsection). Phase 7: **837D** (Health Care Claim - Dental) → `Claim` (`use="claim"`, `type="oral"`) - the third member of that same `ST01="837"` trio (also disambiguated by `ST03`), with its own genuinely different service-line segment (`SV3`, CDT procedure codes) and a dedicated `TOO` (Tooth Information) segment mapping tooth number/surfaces to real ADA canonical systems - completing the full "big five" HIPAA X12 transaction-set suite this app set out to cover. Same auto-detected, third branch of the format sniff in `app/pipeline.py` - no separate route/UI. See the EDI subsection below for the full shape and its disclosed verification-source gap (no official, free X12-to-FHIR ConceptMap IG exists in general, unlike HL7v2's v2-to-FHIR or C-CDA's C-CDA on FHIR - 278 is a real, disclosed exception to that gap via Da Vinci PAS's target-shape verification, even though its own X12-segment crosswalk still isn't published).

The previously-"remaining" HL7v2 trigger events for these four message types are now all implemented: ADT A38 (cancel pre-admit - the A05 sibling of A11/A13's cancel pattern), ORU R31/R32 (the remaining point-of-care variants alongside R30/R40), and MDM T08/T10/T11 (edit/replacement/cancel notifications) all shipped following the exact same patterns as their already-implemented siblings - see the per-type extension-point notes below for what (if anything) each one needed beyond a trigger-event string swap. Any future HL7v2 trigger event for one of these four types (there's no exhaustive list being tracked - add one if/when it's needed) can follow the same precedent. For C-CDA, Medications/Allergies/Immunizations now ship alongside Problems, Discharge Summary and History and Physical Note now ship alongside CCD, and Vital Signs/Results/Procedures now ship alongside all three document types (see the C-CDA subsection below); Discharge Summary's and History and Physical's own remaining IG-required sections (Hospital Discharge Diagnosis/Discharge Medications/Hospital Course/Plan of Treatment for the former, Reason for Visit/History of Present Illness/Physical Exam/Assessment/etc. for the latter) are a natural next slice, following the exact same "header + whatever already-recognized sections it also carries" precedent both document types already established. EDI support now spans all five "big five" HIPAA transaction-set families - 270/271, 276/277, 278, 835, and 837 in all three of its Professional/Institutional/Dental variants - see the EDI subsection below.

## Architecture

**Request flow:** `app/routes/convert.py` (FastAPI routes for `/`, `/convert`, `/api/convert`, `/validate`, `/api/validate`, `/api/generate`, `/healthz`) calls `app/pipeline.py::convert_to_bundle(raw_text) -> Bundle` for conversion and `app/pipeline.py::validate_any(raw_text) -> ValidationReport` for validation. Both are thin format-sniffing dispatchers sitting above three independent, format-specific pipelines, checked in this order since the three signatures are mutually exclusive by construction and X12's check is the cheapest: `app/pipeline.py::is_x12(raw_text)` (does the text start with the literal `"ISA"`, ignoring a possible leading BOM/whitespace - deliberately not `"ISA*"`, since the element separator is discovered dynamically, not spec-guaranteed to be `*`) routes to `app/edi/pipeline.py`'s `convert_edi_to_bundle`/`validate_edi` for X12 EDI; else `app/pipeline.py::is_xml(raw_text)` (does the text start with `<`) routes to `app/cda/pipeline.py`'s `convert_cda_to_bundle`/`validate_cda` for C-CDA XML; else `app/hl7/pipeline.py`'s `convert_hl7_to_bundle`/`validate_hl7` handles HL7v2 - none of the three format-specific pipelines knows another format exists, and all three raise the same exception shapes on each axis (`MissingSegmentError`/`MappingError`/`pydantic.ValidationError` for conversion, plus a format-specific parse error for each) so `app/routes/convert.py` needs only one dispatch table per axis, not a parallel one per format. `convert_hl7_to_bundle` parses via `app/hl7/parser.py`, reads MSH-9 for the message type/trigger event, looks up a mapper in `app/mappings/registry.py`, and calls `mapper.to_bundle(message)`; `validate_hl7` parses the same way and delegates to `app/validation/engine.py::validate_message()` (see the validation extension point below). The CDA side mirrors this exactly - `convert_cda_to_bundle`/`validate_cda` in `app/cda/pipeline.py` both parse via `app/cda/parser.py::parse_document` then delegate to `get_document_builder(...).build_bundle(...)`/`app/cda/validation.py::validate_document()` respectively (see the C-CDA subsection below). The EDI side mirrors it again one level further out - `convert_edi_to_bundle`/`validate_edi` in `app/edi/pipeline.py` parse via `app/edi/parser.py::parse_interchange` then take the interchange's `first_transaction_set()` and delegate to `get_transaction_builder(st01).build_bundle(transaction_set, interchange.delimiters)`/`app/edi/validation.py::validate_interchange()` respectively (see the EDI subsection below - `delimiters` is threaded through the builder interface, not just the parser, once a real consumer needed it). `/api/generate?message_type=&trigger_event=&seed=` runs the mirror-image path through `app/generators/registry.py::generate()` and returns raw text instead of a Bundle (HL7v2, C-CDA, or EDI, all registered in the same flat registry - see the C-CDA/EDI subsections) - the UI's message-type dropdown (populated from `app/generators/registry.py::list_supported_types()`) and "Generate sample" button call it to fill the textarea. The **Convert to FHIR** and **Validate** buttons are two `type="submit"` buttons sharing one `<form>`, distinguished via `formaction` (`/api/convert` vs `/api/validate`, or their `/convert`/`/validate` no-JS form-post fallbacks) - `app/static/app.js` branches on the standard `event.submitter` property to know which one triggered the submit.

**Extension point for new message types:** `app/mappings/base.py` defines the `MessageMapper` interface (`to_bundle(message) -> Bundle`). Each HL7 message *type* gets its own module (`app/mappings/adt.py`, `app/mappings/siu.py`, `app/mappings/oru.py`, `app/mappings/mdm.py`) implementing that interface, registered in `app/mappings/registry.py` as `{(message_type, trigger_event): mapper_instance}` — no changes to routes, the parser, or templates. Cross-message-type shared logic lives in `app/mappings/common.py`:
- `build_patient(pid) -> Patient` — PID is mapped identically no matter the message type.
- `assemble_bundle(msh, patient, *resources) -> Bundle` — MSH-derived Bundle metadata + entries, generic over however many additional resources a message type produces.
- `resolve_encounter_class(pv1) -> Coding` / `build_visit_identifier(pv1) -> Identifier | None` — PV1-2 (patient class) → `Encounter.class` and PV1-19 (visit number) → an `Identifier`, used by `adt.py`'s `build_encounter_core` and `common.py`'s own `build_minimal_encounter` below. `adt.py` and `oru.py` independently hand-rolled the same `{"I":"IMP","O":"AMB",...}` mapping before it was extracted here - if you're building a third PV1-derived Encounter somewhere, use these rather than a third copy.
- `build_minimal_encounter(pv1, patient_id) -> Encounter` — a minimal, status-`"unknown"` Encounter for message types whose PV1 (when present) gives context rather than an admit/discharge lifecycle event. Used by both `oru.py`'s optional result-reporting encounter and `mdm.py`'s optional document-context encounter. This was independently duplicated byte-for-byte between `oru.py` and `mdm.py` before being extracted here - caught by code review, not the original test suite.
- `location_display(segment, field_num)` / `person_display(segment, field_num)` — PL/XCN-shaped **display-string** formatting, for when a field only needs to read as text (e.g. `Encounter.location`/`Encounter.participant` display in `adt.py`, which doesn't materialize separate Location/Practitioner resources). `person_display` falls back to the XCN id (component 1) when family/given are both empty — it must stay in sync with `build_practitioner_from_xcn`'s presence check ("id or family or given") below, since anywhere both are paired into one `Reference` (as `siu.py`'s AIP participants and `mdm.py`'s TXA-9/TXA-10 do), a field with only an id and no name would otherwise materialize a real Practitioner but produce `Reference(display="")`, which FHIR rejects (`display` must be a non-empty string when present). This exact crash shipped once (an id-only AIP, e.g. `AIP|1||5678||||`) and was caught by code review, not the original test suite — see `tests/test_siu_s12_mapping.py::test_aip_with_id_only_materializes_with_id_as_display`.
- `build_reference_with_optional_display(resource_id, display) -> Reference` — the defensive counterpart to the crash above: a `Reference` to a materialized resource with `display` omitted entirely (rather than passed as `""`) whenever the display text couldn't be resolved, so any *future* caller pairing an XCN/PL-sourced resource with a display string fails safe instead of crashing. First written inline in `siu.py`'s `add_participant`, independently re-derived in `mdm.py` for TXA-9/TXA-10, then extracted here once both existed - both now call this shared helper.
- `build_location_from_pl(segment, field_num) -> Location | None` / `build_practitioner_from_xcn(segment, field_num) -> Practitioner | None` — the same PL/XCN field shapes, but building a **real, separately-referenceable resource** instead of just a string. Used by `siu.py` (AIL→Location, AIP→Practitioner), `oru.py` (OBX-16→Practitioner performer), and `mdm.py` (TXA-9/TXA-10→Practitioner originator/authenticator). Prefer these over the display-only pair whenever the target field is an `actor`/`performer`/similar `Reference` rather than a plain string, since a real resource is more useful to any downstream consumer (they can look up the practitioner's identifier, not just read a name). These are PL/XCN-scoped specifically - don't reuse them for a differently-shaped field (e.g. CWE) just because two of its components happen to look similar; build that shape's resource directly instead (see the AIG note below for a case where this was gotten wrong once).

Generic, reusable *field-level* FHIR-fragment builders (name/address/datetime/gender parsing, `build_codeable_concept_from_cwe` for CWE-typed fields) live in `app/fhir_models/builders.py`, shared across all message types; message-type-specific field logic stays in that type's module.

**Extension point for trigger events within one message type:** `app/mappings/adt.py` and `app/mappings/siu.py` follow the same shape — a `Base*Mapper(MessageMapper)` whose `to_bundle()` does the parts identical across every trigger event for that message type (require the message type's core segments, read any optional repeating segments, build the Patient via the shared `build_patient`, delegate to an abstract per-trigger build method, assemble the Bundle via the shared `assemble_bundle`), with concrete trigger subclasses implementing only the part that actually varies:
- `app/mappings/adt.py`: `BaseAdtMapper.build_encounter(pv1, evn, patient_id) -> Encounter`. Most subclasses (`AdtA01Mapper`, `AdtA04Mapper`, `AdtA05Mapper`) just call the shared `build_encounter_core(pv1, evn, patient_id, status=...)` (`A05` pre-admit uses `status="planned"`); `AdtA02Mapper` additionally layers in PV1-6 prior-location history; `AdtA03Mapper` requires a resolvable discharge time (PV1-45 or EVN-2 fallback) and maps PV1-36 discharge disposition; `AdtA08Mapper` infers status from whether a discharge time is present. `AdtA11Mapper` (cancel admit), `AdtA13Mapper` (cancel discharge), and `AdtA38Mapper` (cancel pre-admit) all set `status="entered-in-error"` — a deliberate choice, not IG-mandated (the v2-to-FHIR IG's own A11 guidance applies no special cancel handling at all, which would make an A11-derived Encounter indistinguishable from a plain A01 one in the output) — and all three call the shared `_drop_evn2_period_start_fallback(encounter, pv1)` after `build_encounter_core`, since `build_encounter_core`'s EVN-2 fallback for `period.start` is correct for admission-lifecycle triggers (EVN-2 genuinely is the encounter's own event time for A01/A02/A04/A05/A08) but wrong for these three: EVN-2 on a cancel-trigger message is when the *cancel notification itself* was recorded, not any real admission start. Getting this wrong (only guarding `period.end` against the same hazard, which `AdtA13Mapper` did at first, while leaving `period.start` unguarded) silently mislabels the cancel-event's own timestamp as an admission start — this exact bug shipped once and was caught by code review, not the original test suite (see `tests/test_adt_a11_mapping.py::test_cancel_admit_without_pv1_44_does_not_leak_evn2_as_period_start` and the equivalent A13/A38 tests). `AdtA38Mapper` is A05's cancel-pattern sibling the same way `AdtA11Mapper` is A01/A04's and `AdtA13Mapper` is A03's — unlike A13, it does *not* map PV1-36 discharge disposition, since a pre-admission was never discharged.
- `app/mappings/siu.py`: `BaseSiuMapper.build_appointment(sch, tq1_segments, nte_segments, ais_segments, participants) -> Appointment`. `participants` is built once by `to_bundle` (via `_build_participants`, which also returns the Practitioner/Location/Device resources materialized for AIP/AIL/AIG so `to_bundle` can add them to the Bundle) since it's identical regardless of trigger event - only `status`/`start`/`end` vary, so those are the only things each subclass supplies. Two private base classes each expose a `status` class attribute overridden per subclass, rather than hardcoding status in the shared build method: `_BookedSiuMapper` (`status="booked"` by default) resolves timing via `resolve_appointment_timing()` and requires a start time (raises `MappingError` otherwise) — `SiuS12Mapper`/`SiuS13Mapper`/`SiuS14Mapper` inherit it unchanged (deliberately identical apart from which `trigger_event` string ends up in the `Appointment.extension` marker, since this converter has no persisted state to make a "new booking" vs. "reschedule" vs. "modify" distinguishable in the output), while `SiuS26Mapper` (patient no-show) overrides `status="noshow"` - a no-show necessarily refers to a specific already-scheduled time, so it shares the timing-required behavior. `_UntimedSiuMapper` (`status="cancelled"` by default) resolves timing but does not require it — `SiuS15Mapper` inherits it unchanged, while `SiuS17Mapper` (delete) overrides `status="entered-in-error"`: the HL7 standard draws an explicit, deliberate distinction between S17 "removing an error" and S15 "cancelling a valid request," and FHIR's `entered-in-error` ("should not have been part of the record") is a closer semantic match to S17 than reusing S15's `cancelled`.
- `app/mappings/oru.py`: **not** trigger-polymorphic — `BaseOruMapper` handles R01/R30/R31/R32/R40 identically (they differ only in upstream ordering-workflow semantics this converter doesn't model — R30 places a new order, R31 searches for an existing one, R32 assumes one was already pre-ordered, R40 places none — none of which this stateless converter models), so the five concrete classes are just `trigger_event = "R01"/"R30"/"R31"/"R32"/"R40"` with no overrides. This is the degenerate case of the same pattern, not a different one.
- `app/mappings/mdm.py`: same degenerate, non-trigger-polymorphic pattern as `oru.py` — `BaseMdmMapper` handles T02/T04/T06/T08/T10/T11 identically, since the official v2-to-FHIR IG ships exactly one MDM ConceptMap (`MDM_T02` → `Bundle`) and treats the TXA segment map as trigger-agnostic. The six concrete classes are just `trigger_event = "T02"/"T04"/"T06"/"T08"/"T10"/"T11"` with no overrides. T10 (replace) and T11 (cancel) look like they should warrant trigger-specific `DocumentReference.status` handling the way A11/A13/A38 deliberately override ADT's cancel-trigger status — but here the decision went the other way: the segment-txa-to-documentreference ConceptMap has no trigger-event-specific guidance at all, and TXA-13 (the field that would carry T10's "replaces" pointer) has no mapped FHIR target in it, so — per an explicit instruction to treat the IG as the authoritative source when weighing this exact tradeoff — status stays 100% TXA-19-driven and TXA-13 stays unmapped for every trigger, same as T02/T04/T06. See the module docstring for the full reasoning.

When adding a new trigger event for an already-supported message type, add a subclass in that type's module rather than a new file — only add a new file for a genuinely different HL7 message type.

**Extension point for repeating leader/member segment groups:** `app/hl7/parser.py::group_segments_by_leader(message, leader_name, member_names)` walks a message's segments in order and associates each run of member segments with the leader segment that immediately precedes it (e.g. ORU's `OBR` leading its `OBX` results). Use this - not the flat `optional_segments()` - whenever which-segment-belongs-to-which matters for correctness, not just presence/absence. It's deliberately generic (any leader/member name pair), so a future message type with a similar repeating-group shape (e.g. an order message's `ORC` leading `OBR`) can reuse it directly rather than re-deriving the same positional-walk logic.

**Synthetic message generation (`app/generators/`)** is the mirror image of `app/mappings/` - HL7 text out instead of in. `app/generators/registry.py::generate(message_type, trigger_event, seed=None) -> str` looks up a plain generator function per `(message_type, trigger_event)` (not a class hierarchy like the mappers - generation doesn't need per-trigger polymorphism, just per-trigger field-population rules) and threads a `random.Random(seed)` instance through it; same seed always reproduces the same message byte-for-byte, `seed=None` gives real randomness for the UI's "fresh one" use case. `("CDA", "CCD"): (app.cda.generator.generate_ccd, "CDA^CCD - Continuity of Care Document")` is registered in this exact same flat dict (see the C-CDA subsection below) - "CCD" stands in for `trigger_event` even though C-CDA has no real trigger-event concept, chosen because it costs zero UI/route changes versus a genuine third registry axis for one entry. `app/generators/base.py` holds shared primitives every generator uses: `maybe(rng, p=0.6) -> bool` (the one place "should this optional field be included" is decided), small pools of obviously-synthetic sample data (names/addresses/reason codes/lab tests/etc.), `generate_msh_segment()`, `generate_pid_segment()` (used by all three message types' generators), `build_minimal_pv1_fields(rng, patient_class) -> dict` (used by `adt.py`, `oru.py`, and `mdm.py` - the message types whose generators build a PV1; this exists because ADT and ORU independently duplicated the same PV1-1/2/7/19 field logic once, and had already silently diverged - ORU's copy was missing the physician field ADT's had - before being unified here), and shape-level helpers (`random_location_field()` for PL-shaped fields, `random_physician_xcn()` for XCN-shaped fields) reused across `adt.py`/`siu.py`/`oru.py`/`mdm.py` as needed.

Required/optional policy (the field-level randomization rule the generators implement): a field is treated as required - always populated - when either the HL7 standard calls it required, *or* this app's own mapper needs it to avoid raising `MappingError`/`MissingSegmentError` for that specific trigger (e.g. `PV1-6` prior location is required only for A02; `PV1-44`/`PV1-45` are both required only for A03, since `AdtA03Mapper` raises without a discharge time; SIU S12/S13/S14 always get resolvable timing - via a randomized ~75/25 split between `TQ1` and legacy `SCH-11`, deliberately exercising both of `resolve_appointment_timing()`'s paths - while S15 leaves timing fully optional). Every other field is optional at a fixed ~50-60% inclusion rate via `maybe()`. The one deliberate exception is A08's discharge time, held at exactly 50% *by design* (not just "the general optional rate") specifically to exercise `AdtA08Mapper`'s finished-vs-in-progress status inference in both directions. This policy guarantees every generated message converts successfully through the existing pipeline - the generator's test suite leans on this heavily (see Testing below). **When both admit and discharge are generated, they must come from the same `random_time_range()` call**, not two independent ones - `generate_adt_a03`/`generate_adt_a13` already did this correctly, but `generate_adt_a08` originally drew them from two separate calls, which could (and, once `app/validation/` existed to notice, did) produce a discharge time before the admit time. Fixed once `app/validation/adt.py`'s `discharge-before-admit` rule caught it in the generator's own fuzz output - not a validation-rule bug, a real pre-existing generator gap the validator was the first thing to actually notice.

**Extension point for validation rules (`app/validation/`)** is a third, independent pillar alongside `app/mappings/` (HL7→FHIR) and `app/generators/` (FHIR-shaped→HL7 text) - it takes a parsed message and returns a `ValidationReport` (`app/validation/models.py`: `ValidationFinding{severity: error|warning|info, rule_id, segment, field, message}` + `ValidationReport{message_type, trigger_event, is_valid, findings}`), never a Bundle, and never raises for anything a real HL7 sender could plausibly produce. Same per-message-type module shape as mappings/generators, but two deliberate structural differences:
- `app/validation/registry.py` is keyed by **message type only** (`{message_type: validate_fn}`), not `(message_type, trigger_event)` like `app/mappings/registry.py` - rule *sets* are type-scoped; trigger-specific nuance (e.g. `adt.py`'s A02-only prior-location rule) lives inside the relevant rule function via an `if trigger_event == "...":` check, not via a second registry dimension.
- Each module (`generic.py` for every message type, `adt.py`/`siu.py`/`oru.py`/`mdm.py` per type) exposes one `validate(message, trigger_event) -> list[ValidationFinding]`, but internally composes small private `_rule_*` functions by concatenation rather than one large function - each rule is independently testable and a future contributor knows exactly where to add the next one, mirroring `build_encounter_core`'s small-named-step style more than a single do-everything function.

`app/validation/engine.py::validate_message()` runs `generic.validate()`, then the type-specific validator if one is registered, then `_check_convertibility()` - the load-bearing design decision here: rather than re-deriving a second, parallel "which segments does trigger X require" table (a real duplication-and-drift risk this project has already been bitten by once, see `build_minimal_pv1_fields`/`build_minimal_encounter` above), it actually calls `get_mapper(...).to_bundle(message)` and turns whatever it raises into a finding, so structural completeness can never drift from what the mappers actually enforce. Two gotchas that shipped wrong on the first pass and were caught by manual smoke-testing before the test suite was even written, not by code review this time:
- **`MappingError` is raised from two different places with two different meanings**, and both must be handled, not just one: `get_mapper(message_type, trigger_event)` raises it when the type/trigger isn't registered at all (→ an `info` finding, "no converter registered" - not a defect in the message), but several mappers (`AdtA03Mapper`, `SiuS12Mapper`/`S13`/`S14`/`S26`) *also* raise `MappingError` directly from inside `to_bundle()` for business-rule violations (missing discharge time, unresolvable appointment timing) once a mapper instance was already successfully obtained. The first version of `_check_convertibility()` only caught `(MissingSegmentError, ValidationError)` around the `to_bundle()` call, so every one of those legitimate, well-documented mapper errors fell through into the bare `except Exception` safety net and got logged as an "unexpected internal error" - technically not a crash, but a misleading severity/message for a completely ordinary outcome. Fixed by adding `MappingError` to that inner except tuple too.
- **PID-7 (date of birth) is very commonly date-only** (`YYYYMMDD`, 8 digits, no time component) - `app/fhir_models/builders.py::parse_hl7_datetime` requires 12+ digits (it's built for timestamps, not bare dates) and returns `None` for an 8-digit value, which `app/validation/common.py::parse_comparable_datetime` originally treated as "unparseable," flagging every ordinary date-only birth date as a warning. Fixed by falling back to `parse_hl7_date` (exactly 8 digits) and treating a date-only result as UTC midnight - this is also why `parse_comparable_datetime` exists as its own helper rather than every rule calling `parse_hl7_datetime` directly, so this fallback only had to be written once.

A follow-up multi-agent code review (adversarially verified - findings had to be reproduced by actually running code, not just argued for) caught four more, real ones the manual smoke-testing above missed:
- **The date-only-as-midnight fallback above has its own downstream consequence**: comparing a date-only value against a same-calendar-day *timestamped* value (e.g. `PV1-44` admit `...T08:30:00Z` vs. a date-only `PV1-45` discharge on the same day) made the synthetic midnight sort before the real time-of-day, producing a false `adt.discharge-before-admit`/`adt.admit-before-birth` **error** on a perfectly plausible message. `app/validation/common.py::has_time_precision()` now exposes whether a value actually carried a time component; `app/validation/adt.py::_is_before()` falls back to date-granularity comparison (`.date() <`) whenever either side lacks it, and only compares exact datetimes when both have full precision.
- **`parse_hl7_date`/`parse_hl7_datetime` only validate digit *shape*, not calendar validity** - a numerically well-formed but nonsensical date like `20260231` (Feb 31) made `datetime.fromisoformat()` raise an uncaught `ValueError` from inside `parse_comparable_datetime`'s date-only fallback branch (its sibling `_parse_fhir_datetime`, for the timestamp path, already guarded this correctly). Since this ran during the *generic rules* phase - before `_check_convertibility()`'s own `except Exception` safety net ever executes - it wasn't caught anywhere, and turned `/api/validate` into a raw HTTP 500 on exactly the kind of fat-fingered input a validator exists to catch. Fixed by wrapping that branch in the same `try/except ValueError` its sibling already had.
- **A registered *type* with an unmapped *trigger*** (e.g. `ADT^A38`, one of the "remaining trigger events" this file lists) already runs its type-specific rules before `_check_convertibility()` ever discovers the trigger isn't mapped - so the resulting `engine.unsupported-message-type` finding's message text (`"...only generic checks were run"`) was flatly false whenever type-specific findings sat right next to it in the same report. `_check_convertibility()` now takes a `ran_type_specific_checks` flag from `validate_message()` and adjusts the wording accordingly.
- **Two other, lower-stakes issues in the same pass**: `app/validation/oru.py::_resolve_reference_range` accepted a syntactically valid but semantically transposed range like `"100-70"` (low > high) as if it were normal, producing an inverted (wrong) in/out-of-range determination instead of being skipped like every other malformed `OBX-7` shape - fixed by rejecting `low > high` the same way. `app/validation/adt.py::_rule_a02_missing_prior_location` compared `trigger_event` with a bare `== "A02"`, unlike every other type/trigger dispatch point in this codebase (`get_mapper`, `get_type_validator`), which normalize with `.strip().upper()` first - a lowercase `ADT^a02` silently skipped the check. Both `adt.py` and `mdm.py`'s "is this in the future" rules were also independently hand-rolling the exact logic `common.py::not_in_future()` already existed to centralize (dead code, not a behavior bug) - now both call it.

`app/validation/adt.py`'s `_is_before(earlier_raw, earlier_dt, later_raw, later_dt)` (the date-only-aware ordering comparison behind `discharge-before-admit`/`admit-before-birth`) was promoted to `app/validation/common.py::is_before()` (public) once `app/cda/validation.py` needed the exact same logic for its own encounter/problem-ordering rules - the same "extract once a second real consumer exists" pattern already used for `build_minimal_pv1_fields`/`build_minimal_encounter` above, not a speculative abstraction.

Route/API shape (`app/routes/convert.py`): `_run_validation()`/`ValidationResult` mirror `_run_conversion()`/`ConvertResult` exactly, but `/api/validate` **always returns HTTP 200** for a report, even when `is_valid: false` - a report concluding "this message has an error" is itself a *successful* analysis, not an API-level failure. Only the two exceptions `validate_hl7()` can still raise (`Hl7ParseError`, and `MissingSegmentError` specifically for MSH itself being absent - there's nothing left to validate without it) map to a 4xx, via a narrower `_VALIDATION_ERROR_STATUS` table that deliberately excludes `MappingError`/`pydantic.ValidationError` (validate_hl7 never raises either).

**Error taxonomy:** three custom exceptions in `app/hl7/errors.py` — `Hl7ParseError` (unparseable text), `MissingSegmentError` (required segment absent), `MappingError` (no mapper registered for a message type) — plus `pydantic.ValidationError` from FHIR resource construction. `app/cda/errors.py` adds exactly one more, `CdaParseError` (unparseable XML, or a well-formed document whose root isn't `ClinicalDocument`) - `MissingSegmentError`/`MappingError` are reused as-is for C-CDA rather than duplicated, since their meaning ("a required structural piece is absent" / "no builder registered for this recognized-but-unhandled type") is format-agnostic. `app/edi/errors.py` adds exactly one more the same way, `EdiParseError` (a genuinely broken envelope - missing/malformed ISA, unmatched ST/SE/GS/GE boundary segments - see the EDI subsection's parser notes for exactly which shapes raise it versus which become validation findings instead), again reusing `MissingSegmentError`/`MappingError` as-is. `app/routes/convert.py` translates each to an HTTP status + category label, and both the JSON API and the server-rendered form path route through the same `_run_conversion()` helper so error handling only lives in one place. The UI never shows a raw traceback.

### C-CDA support (`app/cda/`)

C-CDA is a genuinely different input *format* from HL7v2 (XML, not pipe-delimited), so it's a sibling package to `app/hl7/`/`app/mappings/`, not folded into either — the field-access primitives are fundamentally different even though the FHIR-building spirit is the same. Built entirely on stdlib `xml.etree.ElementTree` (verified sufficient for this scope: template-id-driven section/entry lookup at fixed nesting depths, no need for XPath 1.0 axes or XSD validation) — no new dependency.

- **`app/cda/parser.py`** — the `app/hl7/parser.py` equivalent: `parse_document(raw_xml) -> Element` (raises `CdaParseError`), `has_template_id(element, root_oid) -> bool`, `find_child`/`find_all` (path navigation), `xsi_type`, `coded_value`, `ts_value`, `ivl_ts_bounds`. Two real `ElementTree` gotchas these primitives are built to make structurally impossible to hit by accident: (1) a multi-segment relative path missing the namespace prefix on **any** segment fails **silently** (`[]`, not an error) — `find_all` auto-prefixes every `/`-separated segment itself, so a caller can't under-prefix a path; (2) every C-CDA templateId is emitted **twice** per element (a bare `<templateId root="...">` and a versioned sibling with `root`+`extension`), as sibling elements in no guaranteed order — `has_template_id` checks all direct children for a matching `@root`, never assumes `find()`'s first hit is the bare one, and (deliberately) only checks **direct** children, not descendants, so checking a section for its own templateId can't false-match a nested entry's templateId several levels down.
- **`app/cda/common.py`** — the `app/mappings/common.py` equivalent, shared across C-CDA document types (not CCD-specific, since header structure and coded-value shape are standardized across the whole C-CDA family): `build_codeable_concept_from_cd(element) -> CodeableConcept | None` (CD-shaped `<code>`/`<value xsi:type="CD">`, via a disclosed OID→FHIR-system table - SNOMED CT, LOINC, RxNorm, ICD-10-CM, falling back to `urn:oid:<oid>`), `parse_partial_ts(raw) -> str | None` (tries a full HL7 TS timestamp, falls back to date-only — CDA's `@value` digit shape is identical to HL7v2's TS fields, so `app/fhir_models/builders.py::parse_hl7_date`/`parse_hl7_datetime` are reused directly, not reimplemented), `build_patient_from_header(document) -> Patient` (raises `MissingSegmentError` if `recordTarget/patientRole/patient` is absent), `build_encounter_from_header(document, patient_id) -> Encounter | None` (from `componentOf/encompassingEncounter`, `None` when absent since a CCD is a summary document not necessarily bound to one encounter; status always `"unknown"` — same rationale as ORU/MDM's minimal PV1-derived Encounters, no reliable lifecycle signal to infer from), `assemble_bundle(document, patient, *resources) -> Bundle` (`Bundle.identifier`/`.timestamp` from `ClinicalDocument/id`/`effectiveTime`, `Bundle.type = "collection"` matching every existing HL7v2 pipeline's output shape — a proper FHIR-Document-shaped `Bundle(type="document")` + `Composition` is out of scope, since `fhir.resources.R4B.Composition` requires `author` (1..*), which this slice never materializes), and `build_sectioned_bundle(document) -> Bundle` (header + walk every `structuredBody` section through `SECTION_BUILDERS` - the full `build_bundle()` implementation for any document type whose conversion is exactly that shape; extracted here once `app/cda/discharge_summary.py` became a second real consumer of logic `ccd.py` had originally implemented inline, the same "extract once a second real consumer exists" pattern already used for `build_minimal_pv1_fields`/`build_minimal_encounter`, `is_before`, etc. — see that function's own docstring for why a document type with genuinely different structure should implement `build_bundle()` directly instead of being forced through it). CDA's `AdministrativeGender` codeSystem uses `F`/`M`/`UN`, a genuinely different vocabulary from HL7v2 PID-8's `M`/`F`/`O` — its own `_GENDER_MAP`, not a reuse of `app/fhir_models/builders.py`'s HL7v2 gender map. Three bugs caught by a follow-up multi-agent code review (adversarially verified by actually reproducing each with real code, not just argued for), all fixed before any fixture exercised them:
  - **`Bundle.timestamp` is FHIR `instant`, which has no date-only form** (unlike `Condition.onset(Date)Time`, a plain `dateTime` that does) - `assemble_bundle` originally fed it through `parse_partial_ts`, whose whole purpose is a date-only fallback. A `ClinicalDocument/effectiveTime` with no time component (a common, legitimate real-world shape) produced a value the `instant` regex rejects, crashing resource construction with `pydantic.ValidationError` on an otherwise perfectly convertible document - reproduced directly via `Bundle(timestamp="2026-08-12")`. Fixed by calling `parse_hl7_datetime` directly (returns `None` rather than a date-only string) instead of `parse_partial_ts`, matching `app/mappings/common.py::assemble_bundle`'s own deliberate no-date-only-fallback choice for this exact field.
  - **A root-only `<id>` (no `@extension`) was silently treated as "no identifier"** - `_build_identifier` returned `None` whenever `@extension` was absent, even though an II with only a `root` is still a complete identifier per the HL7 datatype spec (the root itself IS the identifier value). Reproduced: a root-only `patientRole/id` produced `Patient.identifier = None` instead of an identifier. Fixed by falling back to `Identifier(system="urn:ietf:rfc:3986", value=f"urn:oid:{root}")` when `@extension` is absent but `@root` is present, matching FHIR's own CDA-on-FHIR convention for representing a bare root.
  - **`build_encounter_from_header` only ever captured the first `<id>`** (`find_child`, not `find_all`), unlike `_build_patient_identifiers` which correctly collects every one - an `encompassingEncounter` with two ids (e.g. local + national encounter number) silently lost the second. Fixed by extracting a shared `_build_identifiers(id_elements, fallback_system) -> list[Identifier]` helper, used by both the patient and encounter paths now.
  - **`build_identifier`/`build_identifiers`** (promoted from `_build_identifier`/`_build_identifiers` - dropped the leading underscore - once `app/cda/procedures.py` became a second real consumer of the identical root/extension `<id>` resolution already used for patient/encounter/document ids) and **`build_quantity_from_pq(element) -> Quantity | None`** (a PQ-shaped element's `@value`/`@unit` → `Quantity`, value+unit only - no system/code, matching the IG's own worked examples for both Medications' `doseQuantity` and Vital Signs'/Results' own `value` - promoted here once `app/cda/medications.py`'s `_resolve_pq` and `app/cda/immunizations.py`'s `_resolve_dose_quantity` were found to be byte-for-byte identical, with `vitals.py`/`results.py` becoming a third and fourth real consumer of the same shape) are both now public, reused across four-plus section modules apiece.
- **`app/cda/base.py`** / **`app/cda/registry.py`** — `CdaDocumentBuilder(ABC)` (`build_bundle(document) -> Bundle`) is the `MessageMapper` equivalent: document types are a "different shape dispatched via registry" situation, same as HL7v2 message types. `registry.py` holds two tables: `_DOCUMENT_BUILDERS` (`{CCD_TEMPLATE_ID: CcdBuilder(), DISCHARGE_SUMMARY_TEMPLATE_ID: DischargeSummaryBuilder(), HISTORY_AND_PHYSICAL_TEMPLATE_ID: HistoryAndPhysicalBuilder()}`) and `SECTION_BUILDERS` (`{PROBLEMS_SECTION_TEMPLATE_ID: build_conditions, MEDICATIONS_SECTION_TEMPLATE_ID: build_medication_requests, allergies.SECTION_TEMPLATE_ID: build_allergy_intolerances, allergies.SECTION_TEMPLATE_ID_ENTRIES_OPTIONAL: build_allergy_intolerances, IMMUNIZATIONS_SECTION_TEMPLATE_ID: build_immunizations, vitals.SECTION_TEMPLATE_ID: build_vital_signs, vitals.SECTION_TEMPLATE_ID_ENTRIES_OPTIONAL: build_vital_signs, results.SECTION_TEMPLATE_ID: build_diagnostic_reports, results.SECTION_TEMPLATE_ID_ENTRIES_OPTIONAL: build_diagnostic_reports, procedures.SECTION_TEMPLATE_ID: build_procedures, procedures.SECTION_TEMPLATE_ID_ENTRIES_OPTIONAL: build_procedures}`, plain functions since every section builder shares one signature — the generator-registry precedent, not the mapper one; the Allergies section is registered under **two** templateIds - the "entries required" one this app originally targeted and the "entries optional" sibling variant, both wrapping the identical entry shape, just a different section-level cardinality constraint - a real gap found by fetching a real Discharge Summary example while researching that document type (see the `discharge_summary.py` bullet below), not something CCD's own fixtures had exercised. **Registering the conversion-side dict entry alone was itself an incomplete fix, caught by a follow-up code review**: `app/cda/validation.py` has its own independent `_find_allergies_section(document)` helper (used to decide which section to run `_rule_allergies` against), and it originally checked only the "entries required" templateId - so a document using the "entries optional" variant converted correctly (via `SECTION_BUILDERS`) but silently ran *zero* allergy validation findings against it, reproduced directly (an entries-optional section with an unresolvable allergen produced no `cda.allergy-missing-allergen` finding, while the identical content under the "entries required" templateId correctly did). Fixed by extracting a shared `_find_section(document, *template_ids)` helper in `validation.py` that every `_find_*_section` function now calls, so a section type registered under more than one templateId can't have this drift between its conversion-side and validation-side dispatch again; `app/cda/generator.py`'s `_random_allergies_section` was also updated to emit the "entries optional" templateId ~25% of the time (it previously always emitted "entries required"), since that gap was exactly why the 1000+-seed fuzz suite never caught it in the first place). `SECTION_BUILDERS` lives in `registry.py` rather than inline in `ccd.py` since section templateIds are standardized across C-CDA document types generally - both `CcdBuilder` and `DischargeSummaryBuilder` reuse this exact table via `app/cda/common.py::build_sectioned_bundle`. **Import-direction note:** `registry.py` imports each concrete document builder class at module load time (same as `app/mappings/registry.py` imports each HL7v2 mapper class), but `build_sectioned_bundle()` also needs `SECTION_BUILDERS` to dispatch each section it walks — a top-level circular import if `common.py` imported `registry.py` back at its own module level. Solved with a function-local (not module-level) import inside `build_sectioned_bundle()`: `from app.cda.registry import SECTION_BUILDERS` runs only when the function executes, by which time `registry.py` has already finished loading.
- **`app/cda/ccd.py`** — `CcdBuilder` (`CCD_TEMPLATE_ID = "2.16.840.1.113883.10.20.22.1.2"`): `build_bundle()` is now just `return build_sectioned_bundle(document)` (see the `common.py` bullet above) - CCD is the "header + generic sections" shape that helper was extracted from. **An unrecognized section is silently skipped** — deliberate and disclosed, not a bug: this slice's section coverage is intentionally partial (Problems, Medications, Allergies, Immunizations, Vital Signs, Results, and Procedures; other sections - e.g. Social History, Family History, Plan of Treatment - remain deferred to a later slice, following this project's own established "one thing per slice" precedent — verified via git history that ADT^A01 shipped alone before A02/A03/A04/A08 arrived together in the next commit).
- **`app/cda/problems.py`** — `build_conditions(section, patient_id) -> list[Condition]`, per the official "C-CDA on FHIR" IG (`build.fhir.org/ig/HL7/ccda-on-fhir/`, current v2.0.0 continuous build). Entry shape: `entry/act[templateId=...4.3]/entryRelationship[typeCode=SUBJ]/observation[templateId=...4.4]/value[xsi:type=CD]`. Both the Concern Act and Problem Observation templateIds are checked via `has_template_id` before use, not assumed from position alone — a real gap caught by re-checking a draft against the approved plan before any test ran against it. `negationInd="true"` on the Problem Observation ("no known problem" pattern) makes the entry skipped entirely, not mapped as if the coded value were asserted — a disclosed limitation, not modeled as its own resource this slice. **`clinicalStatus` is resolved from two separate vocabularies that must not be merged into one lookup table**: a nested Problem Status Observation (LOINC `33999-4`)'s SNOMED CT value, checked first and taking priority when present, falls back to the Concern Act's own act-lifecycle `statusCode` (`active`/`suspended`/`aborted`/`completed`) only when no status observation resolves - see `_resolve_clinical_status`. `effectiveTime` low/high → `onsetDateTime`/`abatementDateTime`, resolved via `ivl_ts_bounds` which itself handles all three legal `IVL_TS` shapes (bare `@value` point-in-time, `<low>`/`<high>` children, or `nullFlavor` for fully unknown). **`entryRelationship/@typeCode` was originally never checked**, only the nested element's templateId - despite CLAUDE.md's own entry-shape description above always having specified `typeCode=SUBJ`. A `<entryRelationship typeCode="REFR">` (or any non-`SUBJ` code) whose nested `<observation>` happened to carry the Problem Observation templateId was incorrectly mapped as an asserted problem; the same gap existed for the Status Observation lookup (should require `typeCode="REFR"` per the IG pattern, not just match on the nested code alone). Caught by a follow-up multi-agent code review and reproduced directly (a `REFR`-wrapped Problem Observation produced a `Condition` it shouldn't have) - fixed by checking `relationship.get("typeCode")` against the expected code (`"SUBJ"` for the act-level loop, `"REFR"` for the status-observation loop) before descending into the nested element in both `build_conditions` and `_resolve_clinical_status`.
- **`app/cda/medications.py`** — `build_medication_requests(section, patient_id) -> list[MedicationRequest]`, per the official "C-CDA on FHIR" IG's `CF-medications.html` guidance and its underlying `CCDA-FHIR MedicationRequest.csv` mapping table (`github.com/HL7/ccda-on-fhir/blob/master/mappings/CF/`), verified by fetching both directly rather than assumed from field-name similarity to Problems. Entry shape: `entry/substanceAdministration[templateId=...4.16]` (a Medication Activity is a `substanceAdministration` directly - no wrapping Act, unlike Problems' Concern Act). Two published ConceptMaps, kept as separate dicts since they're genuinely different vocabularies: `STATUS_MAP` (`statusCode`, HL7 `ActStatus` → `MedicationRequest.status` - `active`→`active`, `suspended`→`on-hold`, `aborted`→`stopped`, `completed`→`completed`, `nullified`→`entered-in-error`; unrecognized/absent falls back to `"unknown"`) and `_MOOD_TO_INTENT` (`moodCode` → `MedicationRequest.intent` - `INT`→`"order"`, `EVN`→`"plan"`; this reads backwards at first glance but is the IG's own mapping, both rows marked "maps loosely to" since CDA mood codes are broader than FHIR intent codes). **`intent` turned out to be FHIR-required despite not showing up via `model_fields` introspection** - confirmed by constructing `MedicationRequest` directly (`status` too; only `subject` appears as `is_required()` in the model's own field metadata, the same "don't trust the library's declared cardinality" lesson `Appointment.status` already taught, but this time in the *stricter*-than-declared direction rather than the looser one) - an unrecognized/absent `moodCode` falls back to `"order"` rather than leaving a required field unset. Structured dosing (`routeCode`→`Dosage.route`, `doseQuantity`/`rateQuantity`→`Dosage.doseAndRate`, `effectiveTime` low/high→`Dosage.timing.repeat.boundsPeriod`) and free-text SIG (a nested `entryRelationship[typeCode=COMP]/substanceAdministration[templateId=...4.147]` "Medication Free Text Sig" whose `<text>` → `Dosage.patientInstruction`) are alternatives in real C-CDA, not both always present - `_build_dosage` returns `None` (omitting `dosageInstruction` entirely) only when neither is present, matching `Dosage` having no required fields itself. `doseQuantity`/`rateQuantity` are read as simple PQ (`@value`/`@unit` directly on the element) only - an `IVL_PQ` range shape (`<low>`/`<high>` children instead) is left unmapped rather than guessing which bound to report as a fixed dose, since the IG's own CSV doesn't disambiguate which shape governs this target field (noted `"Is SXPR used?"` in its own comments column). `negationInd="true"` (this specific administration/order did NOT happen) skips the entry entirely, mirroring Problems' negation philosophy. `consumable/manufacturedProduct/manufacturedMaterial/code` with no resolvable coded value also skips the entry - `medicationCodeableConcept` (or `medicationReference`, not produced by this converter) is required by `fhir.resources.R4B.MedicationRequest`, confirmed by construction the same way `intent`/`status` were. **Deliberately not mapped, per the CSV's own disclosed gaps** (each row explicitly marked "not supported" or "best pattern unclear" in the source table, not silently dropped): `entryRelationship[indication]` (target field genuinely undecided in the IG itself), performer/requester Practitioner references (would need a CDA-side XCN-equivalent practitioner-builder this slice doesn't add), Supply Order / Medication Dispense / Reaction Observation / Drug Monitoring entry relationships.
- **`app/cda/allergies.py`** — `build_allergy_intolerances(section, patient_id) -> list[AllergyIntolerance]`, per the IG's `CF-allergies.html` guidance and `CCDA-FHIR Allergy.csv`. Entry shape mirrors Problems' Concern-Act wrapper (`entry/act[templateId=...4.30]/entryRelationship[SUBJ]/observation[templateId=...4.7]`), but the observation itself nests notably more sub-structure, each gated by its own `typeCode` per the same "check the relationship type, not just the nested templateId" discipline `app.cda.common.find_nested_observation` centralizes (promoted there from this module once `app/cda/problems.py`'s own `_resolve_clinical_status` became a second real consumer of the identical entryRelationship-walk shape - Problems matches its nested Status Observation by LOINC code rather than templateId, so the shared primitive is actually `iter_nested_observations(parent, type_code)`, with `find_nested_observation` as the templateId-matching convenience wrapper Allergies itself uses): a Status Observation (`entryRelationship[REFR]`, templateId `...4.28`, LOINC `33999-4`) for `clinicalStatus`, a Criticality Observation (`entryRelationship[SUBJ, inversionInd=true]`, templateId `...4.145`, LOINC `82606-5`) for `criticality`, and any number of Reaction Observations (`entryRelationship[MFST, inversionInd=true]`, templateId `...4.9`) each optionally carrying its own nested Severity Observation (`entryRelationship[SUBJ, inversionInd=true]`, templateId `...4.8`) for `reaction.severity` - the allergen itself lives at `participant[@typeCode=CSM]/participantRole/playingEntity/code`, a shape neither Problems nor Medications has (verified against a real HL7 C-CDA-Examples allergy entry, not assumed from the CSV alone). Four small ConceptMaps, each its own dict since they're independently-keyed vocabularies: `_TYPE_MAP`/`_CATEGORY_MAP` (both keyed off the *same* Allergy-Intolerance Observation `<value>` SNOMED code, but targeting `type`/`category` respectively - a code can be type-mapped without being category-mapped, e.g. "Allergy to substance" `419199007`, an intentional fuzz case), `CLINICAL_STATUS_MAP` (public, reused by the generator; the *values* are identical to `app.cda.problems.STATUS_OBSERVATION_VALUE_TO_CLINICAL_STATUS` since both sections share the one generic Status Observation template, but kept a separate dict/CodeableConcept construction since `AllergyIntolerance.clinicalStatus` binds to a different terminology system, `allergyintolerance-clinical`, than `Condition.clinicalStatus`'s `condition-clinical`), `CRITICALITY_MAP` (local `HL7ObservationValue` codes `CRITH`/`CRITL`/`CRITU`, not SNOMED), `SEVERITY_MAP` (SNOMED). **A real, disclosed divergence from Problems' negation handling**: Problems skips a `negationInd="true"` entry entirely, but the IG's own `CCDA-FHIR Allergy.csv` gives negated Allergy Observations a real target - a "no known allergy" `AllergyIntolerance` - so this module builds one rather than skipping, via `_resolve_allergen_code`'s two negation-only text fallbacks (a still-resolvable allergen → `code.text = "No known allergy to <display>"`; unresolvable/absent → the IG's exact `"No known allergies"` wording). The IG's *fully coded* negation crosswalk (`CF_AllergyIntoleranceAbsentCode`, mapping specific negated allergens to their own "no known allergy to X" SNOMED codes) was not found published in a verified, fetchable form - disclosed and left unimplemented rather than guessed at, same "don't guess at an unverified crosswalk" philosophy as MDM's TXA-17. `AllergyIntolerance.patient` (not `.subject`, unlike every other resource this app builds) and `.recordedDate` (not `.recorded`) were both confirmed by inspecting `model_fields` directly rather than assumed from naming-convention pattern-matching to `Condition`/`MedicationRequest`. `type`/`category`/`criticality` are bare `code` strings (not `CodeableConcept`, unlike `clinicalStatus`/`code`) - also confirmed by inspecting `model_fields` annotations before writing the constructor calls, per this project's established "always inspect, never guess" `fhir.resources` policy.
- **`app/cda/immunizations.py`** — `build_immunizations(section, patient_id) -> list[Immunization]`, per the IG's `CF-immunizations.html` guidance and `CCDA-FHIR Immunization.csv`. **The IG's own CSV splits Immunization Activity into two target resources by `moodCode`**: `EVN` (already administered/refused) → `Immunization`, `INT` (ordered/planned, not yet given) → `MedicationRequest`, with a mostly-disjoint field set on the `INT` side (`protocolApplied`/`doNotPerform`/`requester`). Entry shape has no wrapping Act (`entry/substanceAdministration[templateId=...4.52]` directly, like Medications) - `consumable/manufacturedProduct/manufacturedMaterial/code` → `vaccineCode` (CVX-coded in practice) and `.../lotNumberText` → `lotNumber`, `routeCode`/`doseQuantity` map the same way Medications' structured dosing does. `STATUS_MAP` (public, reused by the generator) is the `CF_ImmunizationStatus` ConceptMap - but `negationInd="true"` overrides it unconditionally to `"not-done"` regardless of `statusCode` (per the ConceptMap's own comment that `completed`→`not-done` applies "only... when CDA negation is present and true" - every other source status already maps to `not-done` on its own, so checking negation first is equivalent and simpler than consulting the table for every code). `Immunization.status` has no `"unknown"` value (unlike most other status maps in this app - only `completed`/`entered-in-error`/`not-done` exist), so an unrecognized/absent non-negated `statusCode` defaults to `"completed"` rather than an artificial unknown, matching the same "default to the most common real value" judgment already made for Medications' `moodCode` fallback. **Two more required-but-not-`is_required()` surprises, both confirmed by constructing `Immunization` directly rather than trusting `model_fields`** (same lesson `MedicationRequest.intent` already taught): `status` is eagerly required despite not appearing in `model_fields`'s own required list, and `occurrence[x]` (`occurrenceDateTime`/`occurrenceString`) is a required one-of choice enforced *at construction*, not settable via attribute assignment afterward (like `Encounter.class_fhir`) - `primarySource` is a plain FHIR `boolean`, and `"unknown"` isn't a valid boolean value, so passing the IG's own stated fixed value through would be invalid; disclosed and skipped rather than guessing at what was actually intended. Performer materialization (the CSV's `performer.actor → Reference`) is also disclosed-and-skipped, matching Medications' equivalent omission - this app has no CDA-side `assignedEntity → Practitioner` builder yet (the C-CDA equivalent of `app/mappings/common.py::build_practitioner_from_xcn` for HL7v2's XCN fields).

- **`app/cda/results.py`** — `build_diagnostic_reports(section, patient_id) -> list[Observation | DiagnosticReport]`, per the IG's `CF-results.html` guidance plus its two published ConceptMaps (`ConceptMap-CF-ResultReportStatus`, `ConceptMap-CF-ResultStatus`) - again no CSV mapping table is published for Results, so field mapping is drawn directly from the markdown page's tables and the two fetched ConceptMaps. **The two ConceptMaps are genuinely value-identical** (both map the same six CDA `ActStatus` codes to `registered`/`final`/`cancelled`), confirmed by fetching both directly rather than assumed from covering the same source vocabulary - kept as one shared `STATUS_MAP` dict here since they really are the same crosswalk, just feeding two different target fields (`DiagnosticReport.status` and `Observation.status` both happen to accept the exact codes this map produces); unrecognized/absent falls back to `"unknown"`. - **Format auto-detection (`app/pipeline.py`)** — `is_xml(raw_text)` strips a leading BOM **before** whitespace (not after: the BOM character isn't itself whitespace, so a leading BOM stops a whitespace-only `lstrip()` before it ever reaches the whitespace that follows it — this exact ordering bug was caught by direct testing before shipping), then checks for a leading `<`. `convert_to_bundle`/`validate_any` dispatch to `convert_cda_to_bundle`/`convert_hl7_to_bundle` and `validate_cda`/`validate_hl7` accordingly. This keeps the single unified "paste anything, click Convert/Validate" UX every prior HL7v2 message type has used — never a new route/UI branch per input format.
- **`app/cda/generator.py`** — `generate_ccd(rng)`/`generate_discharge_summary(rng) -> str`, the C-CDA mirror of `app/generators/{adt,siu,oru,mdm}.py`, but living inside `app/cda/` rather than `app/generators/`: there are only two document types so far, so a separate `app/generators/cda.py` with its own sub-registry would be premature relative to HL7v2's real 4-type/20-trigger registry need. Field-population policy deliberately exercises both branches of everything the review-caught `common.py`/`problems.py` bugs above involved (root-only vs. root+extension `id`s, date-only vs. full-timestamp `effectiveTime`, recognized vs. unrecognized encounter class, Concern-Act-only vs. nested-Status-Observation `clinicalStatus`), while keeping onset/birth date ranges constrained so no combination can ever trip an error-severity validation rule (see the file's own comments for the exact day-count bounds and why) - the same "guarantee convertibility/validity by construction" contract the HL7v2 generators already keep. `_random_medication_entry` follows the identical philosophy for the Medications section: `moodCode` splits ~50/50 INT/EVN, `statusCode` is mostly a recognized `STATUS_MAP` key (~85%) with an occasional unrecognized one (`new`/`held`, exercising the `"unknown"`-fallback validation finding), and dosing representation splits ~45/35/20 across structured-only/free-text-only/neither - direct fuzz coverage of `_build_dosage`'s three branches, mirroring how the Problems entry generator exercises `_resolve_clinical_status`'s two branches. `_random_allergy_entry` covers the Allergies section's larger branch space the same way: ~10% `negationInd`, and within that ~30% still carrying a resolvable allergen vs. a `nullFlavor` one (both `_resolve_allergen_code` negation paths); the Status Observation (~50%), Criticality Observation (~40%), and Reaction Observation with its own optional nested Severity Observation (~50%/~60%) are each independently `maybe()`-gated, so every nesting depth this section supports gets exercised in some combination across seeds. `_random_immunization_entry` splits `moodCode` ~80/20 EVN/INT (direct fuzz coverage of `build_immunizations()`'s mood-based skip - the INT branch must produce zero `Immunization` resources from that entry), and within EVN further splits ~15% negated; Registered in the *existing* `app/generators/registry.py::_GENERATORS` flat dict as `("CDA", "CCD")`/`("CDA", "DISCHARGESUMMARY")` (see above) rather than a parallel CDA-specific registry - `DISCHARGESUMMARY` is uppercase (unlike the human-readable `"DischargeSummary"` label) to match `generate()`'s own `.upper()`-normalized lookup, which requires its dict keys to already be uppercase, same as every HL7v2 trigger value.
- **`app/cda/validation.py`** — `validate_document(document) -> ValidationReport`, the C-CDA mirror of `app/validation/{generic,adt,engine}.py`, composed the same small-`_rule_*`-functions-by-concatenation way. The Medications section follows the same pattern via `_iter_medication_activities` (walking entries the identical way `build_medication_requests()` does, so validation can never see a different entry set than conversion) and three rules: `cda.medication-missing-code` (`info` - mirrors the Problem Observation missing-value rule exactly, skipped for negated entries since the converter itself never evaluates those), `cda.medication-status-unrecognized` (`info` - reuses `app.cda.medications.STATUS_MAP` directly, same "will silently default to X" wording as the encounter-class rule), and `cda.medication-period-end-before-start` (`error` - dosing `effectiveTime` high before low, reusing `is_before` the same way the Problems abatement-before-onset and Encounter period-end-before-start rules already do). Allergies gets the same treatment via `_iter_allergy_observations` and four rules: `cda.allergy-missing-allergen` (`info` - skipped for negated entries, since `_resolve_allergen_code` gives those a real text-only fallback rather than skipping them, unlike every other "missing code" rule in this file), `cda.allergy-onset-in-future` (`warning`) and `cda.allergy-onset-before-birth` (`error`) mirroring Problems' onset rules exactly, and `cda.allergy-reaction-missing-manifestation` (`info` - a Reaction Observation with no resolvable `<value>`, surfacing `_build_reaction`'s own skip-the-reaction behavior). Immunizations gets four rules via `_iter_evn_immunization_activities` (which, like the mapper's own walk, excludes `INT`-mood entries entirely rather than flagging them - a scope limit, not a data-quality issue): `cda.immunization-missing-vaccine-code` (`info`), `cda.immunization-status-unrecognized` (`info` - only evaluated for non-negated entries, since `negationInd="true"` overrides `status` unconditionally in the mapper regardless of `statusCode`'s value), `cda.immunization-occurrence-in-future` (`warning`), and `cda.immunization-occurrence-before-birth` (`error` - mirroring Problems'/Allergies' own onset-before-birth rules exactly; a follow-up review found `_rule_immunizations` was the one section-level rule of the three not threading `patient` through to its own call site at all, an omission rather than a structural limitation, since `patient` was already resolved and in scope in `validate_document` - see `tests/test_cda_validation.py::test_immunization_occurrence_before_birth_is_error`). Convertibility is checked last, mirroring `app/validation/engine.py::_check_convertibility()` exactly: call `get_document_builder(document)` (unregistered → `info` finding), then `.build_bundle(document)` (`MappingError`/`MissingSegmentError`/`pydantic.ValidationError` → `error` finding; anything else → logged + `error` finding) - the same load-bearing "never re-derive a second required-fields table, just run the real builder" decision already made for HL7v2. `app/cda/pipeline.py::validate_cda(raw_xml)` parses then delegates, mirroring `convert_cda_to_bundle`'s exact shape - it raises only `CdaParseError` (unlike `validate_hl7`, there's no second raise-worthy case: HL7v2's "MSH itself absent" maps to a malformed/wrong-root document here, already `CdaParseError` from `parse_document`). **`_rule_encounter`'s period-timing checks originally lived entirely inside `if low:`**, so an `IVL_TS` with only `@high` (known end, unknown start - a legal shape `ivl_ts_bounds()` returns as `(None, high)`) silently produced *zero* encounter findings even when the known end date was implausibly in the future - caught by a follow-up multi-agent code review, reproduced directly. Fixed by computing `low_dt`/`high_dt` independently up front and adding a dedicated `cda.encounter-period-end-in-future` check for the no-`low`/future-`high` case, rather than nesting everything under `low`'s truthiness.
- **Known, disclosed scope limits for this slice**: three document types (CCD, Discharge Summary, History and Physical Note), seven sections (Problems, Medications, Allergies, Immunizations, Vital Signs, Results, Procedures) recognized on any of them, Discharge Summary's own required sections (Hospital Discharge Diagnosis, Discharge Medications, Hospital Course, Plan of Treatment) not yet recognized (see `discharge_summary.py`), History and Physical's own required narrative sections (Reason for Visit, History of Present Illness, Physical Exam, Assessment, Plan of Care, Review of Systems, Social History, Family History, General Status) not yet recognized (see `history_and_physical.py`), Vital Signs' Blood Pressure/Pulse Oximetry component-grouping not yet implemented (see `vitals.py`), Results' `category`/`specimen`/`author`->Provenance and `IVL_PQ`/`ED`-typed values not yet mapped (see `results.py`), Procedures' `performer`/`participant`/`author`->Provenance and Indication/Comment Activity cross-references not yet mapped (see `procedures.py`), no proper FHIR-Document `Bundle(type="document")`/`Composition` (author/custodian would become load-bearing), no narrative-`<text>`/`originalText` resolution when `displayName` is absent (falls back to code-only). All are natural, already-scoped follow-ups on the infrastructure above, not redesigns.

### EDI/X12 support (`app/edi/`)

X12 EDI is the app's third input *format* and, unlike C-CDA (self-describing XML), a genuinely different parsing problem again: a delimited text format whose own delimiters aren't fixed by spec but are declared *by the file itself*, at fixed byte positions inside its own envelope header (`ISA`). Sibling package to `app/hl7/`/`app/cda/`, not folded into either. Phase 1 covers **270** (Eligibility Inquiry) and **271** (Eligibility Response) - chosen because they're structurally the simplest of the "big five" healthcare X12 transaction sets (no claim/service-line hierarchy) and map to FHIR's own base-spec `CoverageEligibilityRequest`/`CoverageEligibilityResponse` with no extension IG required.

**A disclosed gap versus the other two formats**: HL7v2 has the ballot-published `v2-to-FHIR` IG and C-CDA has `C-CDA on FHIR`, both with per-field ConceptMaps this project leans on for verification. **No equivalent official, free X12-to-FHIR ConceptMap IG exists** - X12's own authoritative TR3 Implementation Guides are paywalled. Every field mapping in `eligibility_270.py`/`eligibility_271.py` is instead checked against the base (free) FHIR resource definitions plus a hand-verified real 270/271 segment/loop shape (HL03 level codes, NM1/DMG/EQ/EB/DTP/AAA positions) - each module's own docstring says so explicitly, the same disclosure discipline as every MDM/TXA and CDA field-mapping decision above.

- **`app/edi/parser.py`** — the `app/hl7/parser.py`/`app/cda/parser.py` equivalent for X12. Two real gotchas its primitives are built to make structurally impossible to hit by accident: (1) **`ISA` is the only fixed-width segment** (106 bytes, spec-guaranteed) - `read_isa_delimiters(raw_text) -> Delimiters` reads the element separator (byte 3, immediately after the literal `"ISA"`), repetition separator (byte 82, ISA11 - captured but not interpreted this slice, no Phase-1 field needs it), component separator (byte 104, ISA16), and segment terminator (byte 105) purely by position, never by splitting on a guessed delimiter - and this byte-position trick must never be generalized to any other segment, including `ISA`'s own trailer `IEA`. (2) **Trailing omitted elements are normal, not malformed** (e.g. a segment ending `...**100*95~` with an empty element) - `element(segment, index)` (1-based, matching X12's own numbering where element 1 is `segment[1]`) and `component(value, delimiters, index)` (1-based sub-element access into a composite value) are both bounds-guarded to return `""` rather than raise, the same contract `app/hl7/parser.py::field_str` already provides for HL7 fields. `split_segments()` strips surrounding whitespace from each segment before splitting into elements - real-world files commonly emit a line break after the segment terminator despite the spec not calling for one, and without this the stray newline glues onto the next segment's first element and silently breaks every subsequent segment-ID match. `parse_interchange(raw_text) -> Interchange` walks segments by **matching on segment ID** (`ISA`/`GS`/`ST`/`SE`/`GE`/`IEA`) to reconstruct the envelope tree, deliberately **not** by trusting the trailer segments' own declared counts (`IEA02`/`GE01`/`SE01`) - a wrong count is a plausible real-world sender bug that shouldn't block parsing, so `EdiParseError` is raised only when the envelope's nesting is genuinely broken (a boundary segment with no matching opener, an opener never closed before its parent closes, a missing `IEA`) - count *mismatches* become `warning`-severity validation findings instead (see `validation.py` below), the X12 analogue of "never raise for something a real sender could plausibly produce." An interchange that's well-formed but contains zero transaction sets is not an error either - `first_transaction_set(interchange)` returns `None`, and `app/edi/pipeline.py::convert_edi_to_bundle` is what turns that into a `MissingSegmentError` (there's genuinely nothing to convert), mirroring how CDA's "root isn't `ClinicalDocument`" and HL7v2's "`MSH` itself absent" are each raised by the layer that actually needed the missing thing, not by the parser speculatively. Two loop-grouping primitives: `group_by_leader(segments, leader_id, member_ids)` is a direct `list[Segment]`-typed port of `app/hl7/parser.py::group_segments_by_leader`'s exact algorithm (used for 270's `EQ`/271's `EB` leading their `REF`/`DTP`/`MSG` members); `group_by_hl_hierarchy(segments) -> list[HlLoop]` is genuinely new - nothing in HL7v2 or C-CDA needs this shape, since X12's `HL` segments encode a tree via **sibling pointers** (`HL01` this loop's own id, `HL02` parent's id, `HL03` level code - e.g. `"20"`=Information Source/`"21"`=Information Receiver/`"22"`=Subscriber/`"23"`=Dependent for 270/271, `HL04` has-children flag) rather than XML's native nesting or a simple leader/member run. Two passes: build a flat `HlLoop` per `HL` segment (every following non-`HL` segment up to the next `HL` is that loop's `member_segments`), then link `.children` by matching `hl02` → some other loop's `hl01`; a loop whose `hl02` doesn't resolve to any `hl01` (including a genuinely root loop, whose `hl02` is simply absent) becomes a root rather than being dropped or raising - a safe, disclosed default for a malformed sibling pointer, surfaced separately as `edi.hl-parent-not-found` in validation instead. `find_child_loop(loop, hl03)` (in `common.py`, not `parser.py`, since it's 270/271-shape-specific) walks `.children` the same way `app/cda/parser.py::find_child` does for CDA. `parse_decimal(raw) -> Decimal | None` (added Phase 4, for 835's money fields) parses defensively via `try/except InvalidOperation` like every other numeric primitive here, plus one extra guard neither `_int_or_none` nor a naive `Decimal(raw)` call has: **`Decimal("NaN")`/`Decimal("Infinity")`/`Decimal("-Infinity")` do not raise `InvalidOperation`** - Python's own `decimal` module parses those literal strings successfully, so a malformed-but-decimal-shaped X12 money element (`CLP03`/`CLP04`/`BPR02`) could otherwise flow a non-finite value straight into a `>`/`==` comparison or a constructed `Money.value` uncaught. `parse_decimal` explicitly rejects a non-finite result via `.is_finite()` after parsing, returning `None` the same as any other unparseable input. `remittance_835.py::_parse_money` and every 835 validation rule in `validation.py` share this one implementation rather than each having its own `try/except Decimal` - a follow-up code review caught that the first version of `validation.py`'s three 835 rules had their own local `_decimal_or_none()` with no non-finite guard - `Decimal('NaN') > Decimal('1')` itself raises `InvalidOperation` (confirmed directly, not assumed), so `_rule_835_claim_paid_exceeds_charge`'s `paid > charge` comparison would have crashed uncaught for a `CLP03`/`CLP04` value spelled `"NaN"`, turning `/api/validate` into exactly the kind of raw 500 this project has explicitly disclosed and fixed before (see the "date-only PID-7" and "calendar-invalid date" entries in the validation extension-point section above) - fixed by switching all three rules to the shared `parse_decimal`, see `tests/test_remittance_validation.py::test_835_non_finite_clp_amounts_do_not_crash_validation`.
- **`app/edi/common.py`** — the `app/cda/common.py` equivalent: cross-transaction-set shared builders, since NM1/DMG shape and Bundle/date assembly are standardized across X12 healthcare transaction sets generally, not 270/271-specific (a future 276/277 builder reuses this directly). `parse_x12_datetime(date_str, time_str="") -> str | None` concatenates X12's separately-carried date (`CCYYMMDD`) and time (`HHMM[SS]`) elements and delegates straight to the existing `app.fhir_models.builders.parse_hl7_datetime`/`parse_hl7_date` - X12's digit shapes are byte-for-byte the same as HL7v2's TS fields, the same direct-reuse opportunity `app/cda/common.py::parse_partial_ts` already took for CDA; falls back to a date-only result when `time_str` is empty or the combined string doesn't parse as a full datetime, returning `None` only when `date_str` itself is empty/invalid. `build_organization_from_nm1`/`build_practitioner_from_nm1`/`build_patient_from_nm1_dmg` build the payer/provider/subscriber-or-dependent resources from an `NM1` (+ optional `DMG`) segment; `is_person_entity(nm1)` (NM102 `"1"`=Person vs `"2"`=Non-Person Entity) is what both eligibility builders use to decide whether the 2000B provider loop materializes a `Practitioner` or an `Organization`, since X12 allows either there. `assemble_bundle(bht, *resources) -> Bundle` is the X12-header equivalent of `app/cda/common.py::assemble_bundle` (which reads `ClinicalDocument` fields instead): `BHT03` → `Bundle.identifier`, `BHT04`+`BHT05` → `Bundle.timestamp`, `Bundle.type = "collection"` matching every existing pipeline's output shape. BHT (the transaction's own application-level reference) is used rather than the ISA envelope's `ISA13` interchange control number, since BHT03 is more meaningful to a consumer than an interchange-level control number. **The exact `Bundle.timestamp`-is-`instant`-has-no-date-only-form bug already disclosed for CDA above was proactively avoided here, not independently rediscovered**: `assemble_bundle` calls `parse_hl7_datetime` directly (no date-only fallback) for `Bundle.timestamp` rather than `parse_x12_datetime`, whose whole purpose is that fallback - using the latter would crash resource construction on an otherwise perfectly convertible transaction set whenever `BHT05` (time) is empty or unparseable, the identical failure mode CDA's `assemble_bundle` shipped once and fixed. Two disclosed local-system fallbacks, same category as CDA's `_OID_TO_FHIR_SYSTEM` and MDM's TXA-3 table: `SERVICE_TYPE_CODE_SYSTEM` (no FHIR-canonical URI exists for X12's own Service Type Code external code list, used by both 270's `EQ01` and 271's `EB03`) and `NM1_ID_QUALIFIER_SYSTEM` (public - NM108 Identification Code Qualifier → a canonical system where one is officially recognized - `XX`→NPI, `SY`→SSN - falling back to a disclosed local system keyed by the qualifier itself for anything else, e.g. `PI`/`MI`; NM108 is normalized `.strip().upper()` before this lookup, matching DMG03's own normalization three lines below in the same file - a lowercase qualifier shipped once without this and silently fell through to the disclosed per-qualifier fallback instead of the canonical NPI/SSN system, caught by a follow-up code review). The lookup-with-fallback logic itself is `resolve_id_qualifier_system(qualifier, fallback_system) -> str`, extracted once `remittance_835.py::_build_n1_identifier` became a second real consumer of the identical qualifier→system resolution `_build_nm1_identifier` already did inline (N103/N104 use the same Identification Code Qualifier list as NM108, just at a different segment position - see that module's own bullet) - both callers now share one implementation instead of two independently-drifting copies. `_DMG_GENDER_MAP` (X12 code list 1068, DMG03: `M`/`F`/`U`) is its own table, not a reuse of HL7v2 PID-8's `M`/`F`/`O` map - a genuinely different vocabulary, the same "different-but-similar-looking vocabulary needs its own table" situation CDA's `F`/`M`/`UN` gender vocabulary already was relative to HL7v2's. `BHT_REFERENCE_SYSTEM` is the one named constant behind every `Reference`-by-identifier back to BHT03 in this app (both `assemble_bundle`'s own `Bundle.identifier` and `eligibility_271.py`'s `.request` fallback - see that module's bullet below) - promoted here after the two uses were found independently re-typing the same literal string, risking silent drift if one were ever changed without the other. **`resolve_eligibility_parties(segments, transaction_set_id) -> ResolvedEligibilityParties`** is the single real implementation of "walk 2000A→2000B→2000C→2000D and decide which NM1/DMG pair is the patient" - both `eligibility_270.py` and `eligibility_271.py`'s `build_bundle()` call it instead of each independently re-deriving the ~40-line walk, and `app/edi/eligibility_validation.py`'s own 270/271 plausibility rules call it too (wrapped in a `try/except MissingSegmentError` there, since validation must never raise). This was extracted after a follow-up multi-agent code review caught that the two builders' copies had already drifted apart from a third, independent copy inside `validation.py` - the validator's own version used a loose whole-tree search for the subscriber loop (instead of the strict 2000A→2000B→2000C parent chain `find_child_loop` enforces) and treated any present 2000D loop as "the patient" without checking its NM1 actually resolved, so a malformed-but-plausible dependent loop (HL03="23" present, no NM1) could make validation inspect a completely different, and empty, segment set than what conversion actually used - see `tests/test_eligibility_271_mapping.py::test_dependent_loop_without_nm1_falls_back_to_subscriber` and `tests/test_edi_validation.py::test_271_no_service_type_rule_follows_dependent_only_when_nm1_resolves` for the paired regression tests proving both sides now agree. **`build_coverage(patient, payer, subscriber) -> Coverage`** is a minimal, always-`"active"` `Coverage` linking beneficiary/payor/subscriber - independently hand-written the identical way three separate times (`eligibility_270.py`, `eligibility_271.py`, `prior_auth.py`) before being promoted here once `claim_837p.py` became a fourth real consumer of the exact same six-line shape; all four builders now call this instead. **`build_diagnosis_codeable_concepts(hi, delimiters) -> list[CodeableConcept]`** and its `HI_QUALIFIER_SYSTEM` table parse `HI`'s repeating diagnosis-code composites (`HI*ABK:J209*ABF:E119~` = two diagnoses, not two segments) - promoted from `prior_auth.py`'s own Phase 3 `_build_diagnoses`/`_HI_QUALIFIER_SYSTEM` once `claim_837p.py` needed the identical parsing loop a second time. **This promotion caught a real, pre-existing factual error, not just a duplication**: Phase 3's original table mapped qualifier `"BF"` itself to `http://hl7.org/fhir/sid/icd-10-cm` - verified directly (not assumed) against X12 code list 1270 that this is wrong: `"BF"`/`"BK"` are the legacy **ICD-9-CM** other/principal-diagnosis qualifiers, while `"ABF"`/`"ABK"` are the 5010 **ICD-10-CM** ones. The corrected `HI_QUALIFIER_SYSTEM` maps `"ABK"`/`"ABF"` to `http://hl7.org/fhir/sid/icd-10-cm` and `"BK"`/`"BF"` to the real (also verified) `http://hl7.org/fhir/sid/icd-9-cm`, rather than guessing either was interchangeable with the other - see `tests/test_edi_common.py` (direct unit tests for the corrected table) and `tests/test_prior_auth_mapping.py`'s updated assertion (the existing `edi_278_request_basic.x12` fixture happens to use the legacy `"BF"` qualifier, so its diagnosis now correctly resolves to ICD-9-CM, not ICD-10-CM as the pre-fix test wrongly asserted).
- **`app/edi/base.py`** / **`app/edi/registry.py`** — `EdiTransactionBuilder(ABC)` (`build_bundle(transaction_set, delimiters) -> Bundle`) is the `MessageMapper`/`CdaDocumentBuilder` equivalent: transaction sets (270/271/276/277/278/835/837) are a "different shape dispatched via registry" situation, same as HL7v2 message types and C-CDA document types. **`delimiters` was added to the interface in Phase 2**, alongside `transaction_set` rather than folded into it, since it's an interchange-level concern shared by every transaction set in the interchange - `claim_status.py` was the first builder needing it, to split STC01's composite category/status sub-parts via `app.edi.parser::component()`, which requires the interchange's own self-declared component separator (270/271 never needed it, since every field either eligibility builder reads is a simple element, not a composite). `app/edi/pipeline.py::convert_edi_to_bundle` passes `interchange.delimiters`; so does `app/edi/validation.py::_check_convertibility`, which needed the same one-parameter addition. `Edi270Builder`/`Edi271Builder`/`Edi835Builder` all accept the parameter but don't use it (835 has no composite element to parse either), purely to satisfy the shared interface; `Edi837pBuilder`/`Edi837iBuilder` are the third and fourth builders (after `claim_status.py`/`prior_auth.py`) that genuinely need it, to split `CLM05`/`SV1-01`/`SV1-07` (837P) and `CLM05`/`SV2-02` (837I)'s own composite sub-parts. `registry.py`'s `_TRANSACTION_BUILDERS` is keyed by `ST01` (`"270"`/`"271"`/`"276"`/`"277"`/`"278"`/`"835"`) - X12's own transaction-set-code axis is already the CDA-templateId-equivalent single dimension, no second axis needed the way HL7v2's `(message_type, trigger_event)` pair is, **with two real exceptions, each resolved a different way**: `"278"` is a single registry *entry* for both 278 request and response, since they share one `ST01` and the request/response branch happens inside `Edi278Builder.build_bundle()` itself by reading `BHT02` (see `prior_auth.py`'s own module docstring); `"837"` isn't in the dict *at all* - unlike 278, there's no field inside the transaction set itself to branch on, so `get_transaction_builder(st01: str, st03: str = "")` intercepts `"837"` before the dict is ever consulted and dispatches on `st03` instead (see `claim_837i.py`'s own bullet above for the full research and reasoning behind choosing `ST03` over `GS08` for this). `get_transaction_builder` raises `MappingError` if `st01` isn't registered at all, mirroring `get_document_builder`/`get_mapper` exactly (including the `.strip().upper()` key normalization, currently inert since every registered `ST01` is purely numeric, but kept consistent with the sibling registries rather than silently diverging).
- **Why 270 and 271 are two sibling builder files, not a `Base*` + subclass pair**: unlike ADT/SIU trigger events or CCD/DischargeSummary (which share nearly everything down to one literal `build_sectioned_bundle` call), 270 and 271 are a genuine request/response pair with a different leader segment (`EQ` vs `EB`) and an entirely different target FHIR resource - the "genuinely different structure, don't force it through one shared helper" case CDA's own `build_sectioned_bundle` docstring already warns about. What's actually shared - envelope parsing, the full 2000A→2000B→2000C→2000D HL-hierarchy walk and patient-precedence resolution (`common.py::resolve_eligibility_parties`), NM1/DMG builders, `Bundle` assembly - lives in `parser.py`/`common.py`; both builder modules call it directly rather than one subclassing the other. Only the patient-loop leader (`EQ`/`EB`) and the target resource construction that follows are genuinely per-transaction-set and stay in each builder's own file.
- **`app/edi/eligibility_270.py`** — `Edi270Builder` → `CoverageEligibilityRequest`. Loop shape (all HL03-keyed): 2000A (`"20"`, `NM1*PR`) → payer `Organization`; 2000B (`"21"`, `NM1*1P`/`41`) → provider `Organization`/`Practitioner` (branches on `is_person_entity`); 2000C (`"22"`, `NM1*IL`+`DMG`) → subscriber `Patient`; 2000D (`"23"`, `NM1*QC`+`DMG`, optional) → dependent `Patient`. **Named precedence rule, not left implicit**: `.patient` = the 2000D dependent when present *and its own NM1 resolves*, else the 2000C subscriber themselves - enforced once, by `common.py::resolve_eligibility_parties`, not re-derived per builder (documented in the module docstring the same way ADT/SIU's own field-precedence rules are). The nested 2110C/2110D loop leader `EQ` (`EQ01` Service Type Code) → `CoverageEligibilityRequest.item[].category` (via the shared `build_service_type_category`); its `DTP` (qualifier `"D8"` only - a plain `CCYYMMDD` date; the range qualifier `"RD8"` is deferred, disclosed rather than guessed at) → `servicedDate`, a single top-level field (confirmed by inspecting `model_fields` directly, not assumed) that takes the first resolvable date found across every `EQ` group - a disclosed simplification for the common case where one 270 carries one uniform service date. `.purpose` (FHIR-required - see the `fhir.resources` gotcha list above) has no source field at all in 270/271 ("why are we asking" isn't a data element X12 carries here) - defaults to `DEFAULT_PURPOSE = "benefits"` (the dominant real-world use), the same "default to the most common real value when no unknown option exists" judgment already made for Medications' `moodCode`/Immunizations' `statusCode` fallbacks. `.created` (also FHIR-required) is a real business-rule requirement, not just a default: resolved from `BHT04`(+`05`) via `parse_x12_datetime`, and `Edi270Builder` raises `MappingError` if it doesn't resolve - the same "require the one field with no safe default" precedent `AdtA03Mapper` already set for discharge time.
- **`app/edi/eligibility_271.py`** — `Edi271Builder` → `CoverageEligibilityResponse`. Same envelope/HL/NM1/DMG walk and dependent-precedence rule as 270, via the same shared `common.py::resolve_eligibility_parties` (`BHT02="11"` distinguishes a 271 from 270's `BHT02="13"`); diverges where 271's own segments differ: the 2110C/2110D leader is `EB` (Eligibility/Benefit Information), not `EQ` - `EB03` → `item.category` (same shared `build_service_type_category`), `EB01` (normalized `.strip().upper()` before lookup, matching `EB12`'s own normalization a few lines below - a lowercase EB01 shipped once without this and silently left `.excluded` unset/`.inforce` stuck `False`, caught by a follow-up code review, see `tests/test_eligibility_271_mapping.py::test_lowercase_eb01_still_resolves_excluded`) → `item.excluded` via a disclosed subset (`_EB01_EXCLUDED_MAP`: `"1"`→Active/`False`, `"6"`→Inactive/`True`, `"I"`→Non-Covered/`True`; unrecognized codes leave `.excluded` unset rather than guessed at) and also drives `insurance.inforce` (`True` if any `EB01="1"` was seen across the patient's `EB` groups), `EB05` → `item.description` (free text), `EB12` (Y/N/U) → `item.network` as disclosed free text via `_EB12_NETWORK_TEXT` (no official FHIR CodeSystem exists for this indicator - `network` is itself a `CodeableConcept`, confirmed by inspecting `model_fields`, so text-only is a legitimate, disclosed choice, the same treatment Allergies' "no known allergy" text fallback already established). `AAA` (Request Validation) segments are scanned across the **whole transaction set**, not loop-scoped (a disclosed Phase-1 simplification) - any `AAA01="N"` → `.outcome = "error"`, **unconditionally on whether `AAA03` itself resolved** (an earlier version required a non-empty `AAA03` before treating the rejection as real, silently reporting `"complete"` for a genuinely rejected request whose reason code just didn't resolve - caught by a follow-up code review, see `tests/test_eligibility_271_mapping.py::test_aaa_rejection_with_empty_reason_code_still_sets_error_outcome`) - and `.disposition` = free text built from whichever `AAA03` reject-reason codes did resolve (no verified FHIR CodeSystem crosswalk exists for `AAA03`, so it's carried as text rather than guessed at, the same treatment MDM's TXA-17 already gets), left unset only when none did; otherwise `.outcome = "complete"`, the common-case default matching `Immunization.status`'s own "default to the most common real value" precedent. `.request` (FHIR-required) has no real originating `CoverageEligibilityRequest` resource to point at, since this converter processes a standalone 271 with no linked 270 Bundle - built as `Reference(identifier=Identifier(system=BHT_REFERENCE_SYSTEM, value=bht03))` rather than a resolvable `urn:uuid`, a disclosed, deliberate use of FHIR's own reference-by-identifier shape for exactly this "the referenced resource isn't actually in this Bundle" situation, not a workaround.

### `hl7` library gotcha (important)

The `hl7` package (PyPI: `hl7`, i.e. python-hl7) is used for HL7v2 parsing:
- `hl7.parse()` **always** splits segments on `\r`, regardless of input. `app/hl7/parser.py::parse_message()` normalizes `\n`/`\r\n` input (e.g. from a browser textarea or an uploaded file) to `\r` before calling it, and drops blank lines.
- `hl7.parse()` has **no MSH-boundary awareness at all** - a real HL7v2 file can be a batch (multiple MSH-led messages concatenated back to back, with no `BHS`/`BTS` wrapper this app recognizes), and the library happily parses every segment from every concatenated message into one single `Message` object. This is a genuine correctness hazard, not just a batching inconvenience: `optional_segments`/`group_segments_by_leader` (used for OBX/NTE/AIP/AIL/AIG) would silently pull matching segments from *every* message in the batch into one Bundle, with no way for a caller to tell the result apart from a single message that just happens to have an unusually large number of repeating segments. `app/hl7/parser.py::_truncate_to_first_message()` detects a second `MSH` in the normalized text and truncates to only the first message's segments before `hl7.parse()` ever runs - mirroring this app's own established "process only the first, disclosed rather than silent" precedent for batched input (`app/edi/parser.py::first_transaction_set`'s identical scope limit for X12). Caught by a follow-up multi-agent code review, not the original test suite - see `tests/test_hl7_parser.py::test_parse_message_truncates_to_first_message_when_multiple_msh_present`.
- When a field/repetition has no component separator (`^`), the library collapses it to a bare Python `str` instead of a nested `[component]` list. Naively indexing a second level (`field[0][0]`) on such a field does **character** indexing, not component indexing, and silently returns the wrong (truncated) value. `app/hl7/parser.py::component_str()` guards against this and is the only sanctioned way to pull a component out of a field/repetition — always use it (or `field_str()`, which wraps it) instead of raw indexing when adding a new mapper.
- The library splits on `^` **purely syntactically, with no awareness of HL7 data types** — it splits a field the same way whether the field is genuinely composite (XCN, CWE, PL, ...) or an unstructured free-text type (`ST`/`FT`/`TX`) where a literal `^` is just a character a user typed, not a component separator. `field_str()`'s `component=1` default is correct for the former but silently **truncates** the latter at the first `^`. `app/hl7/parser.py::raw_field_str(segment, field_num, repetition=0)` returns the field's full original text in both cases (it's a bare string already when the library didn't split it, and gets rejoined with `^` via `str()` when it did) — use this, not `field_str()`, for any `ST`/`FT`/`TX`-typed field (e.g. `OBX-5` when `OBX-2` is one of those types, `NTE-3`, `TXA-25`). This exact truncation bug shipped once in both `app/mappings/oru.py`'s `_build_observation_value` and `app/mappings/mdm.py`'s `_build_binary_from_obx` (both read free-text `OBX-5` via `field_str`) and was caught by code review, not the original test suite — see `tests/test_hl7_parser.py::test_raw_field_str_preserves_a_caret_that_field_str_would_truncate` and the matching regression tests in `test_oru_mapping.py`/`test_mdm_mapping.py`.

### `fhir.resources` library notes

- Resources are imported from the `R4B` subpackage (`fhir.resources.R4B.*`), not the root package — as of `fhir.resources` v7+, the root package defaults to FHIR R5. R4B did not change `Patient`/`Encounter`/`Bundle`/`Appointment`/`Practitioner`/`Location`/`Device`/`DiagnosticReport`/`Observation`, so it's a safe practical stand-in for R4 here.
- `Encounter.class` is a required field exposed as the Python attribute `class_fhir` (since `class` is a reserved word) — it must be passed as a constructor kwarg (`Encounter(..., class_fhir=Coding(...))`), not set as an attribute after construction, because required fields are validated eagerly on `__init__`. `Appointment` has no such reserved-word field and can be built incrementally (construct with just `id`/`status`/`participant`/`extension`, then set the rest via attribute assignment).
- Bundles use `Bundle.type = "collection"` (not `"transaction"`) since there's no FHIR-server interaction in this app.
- Before using a resource sub-object you haven't used before (e.g. `EncounterHospitalization`, `AppointmentParticipant`, `DeviceDeviceName`, `ObservationReferenceRange`), inspect its real `model_fields` rather than guessing field names/shapes — this was done for `dischargeDisposition` when adding A03 discharge mapping, for `Appointment`/`AppointmentParticipant` when adding SIU, and for `Practitioner`/`Location`/`Device`/`DiagnosticReport`/`Observation` when adding resource materialization and ORU. Also don't assume the library enforces FHIR's own cardinality/binding rules: `fhir.resources.R4B.Appointment` doesn't actually require `status` at construction time (only `participant`) even though the FHIR spec calls status 1..1, and it does **not** validate that status/participant-status strings are real codes from the spec's value sets — getting the *values* right (not just the field names) is entirely on the mapper. Confirm real code values against the FHIR spec pages (e.g. `valueset-appointmentstatus.html`), not memory. `Practitioner`/`Location`/`Device` have **no required fields at all** (unlike `Encounter`/`Appointment`/`DiagnosticReport`/`Observation`, which each require at least one) - they can be built incrementally with nothing but an `id`.
- `Quantity.value` (used for `Observation.valueQuantity`, e.g. from OBX-5/6) deserializes as `decimal.Decimal`, not `float` - `Decimal('7.2') == 7.2` is `False` in Python, so comparisons in tests need `float(obs.valueQuantity.value) == 7.2` or a `Decimal` literal, not a bare float equality check.
- **`model_fields` alone understates real required-at-construction fields for several resources this app builds** — confirmed by direct construction, not assumption, each time: `MedicationRequest.intent`, `Immunization.status`/`occurrence[x]`, `Observation.status`, `DiagnosticReport.status`, `Procedure.status` (the last three confirmed while adding the Vital Signs/Results/Procedures C-CDA sections), `CoverageEligibilityRequest.created`/`purpose`/`status` (only `patient`/`insurer` show as required in `model_fields`), `CoverageEligibilityResponse.created`/`outcome`/`purpose`/`status` (only `patient`/`insurer`/`request` show), `Coverage.status` (only `beneficiary`/`payor` show), `Task.status`/`.intent` (zero fields show as required in `model_fields` at all), `Claim.created`/`.status`/`.use` / `ClaimResponse.created`/`.outcome`/`.status`/`.use` (only `Claim`'s `insurance`/`patient`/`priority`/`provider`/`type` and `ClaimResponse`'s `insurer`/`patient`/`type` show), `PaymentReconciliation.created`/`.paymentDate`/`.status` (only `paymentAmount` shows), and `ClaimItem.sequence`/`ClaimDiagnosis.sequence` (`model_fields` shows only `ClaimItem.productOrService` and nothing at all for `ClaimDiagnosis` - both `.sequence` fields are eagerly required at construction regardless). `Task.for` is exposed as the Python attribute `for_fhir` (reserved word, same pattern as `Encounter.class_fhir`). `PaymentReconciliation.created` is a plain `dateTime` (has a date-only form) while `Bundle.timestamp` is an `instant` (does not) - the same field-name-looks-similar-but-type-differs trap `remittance_835.py` was built to avoid deliberately rather than rediscover, see that module's own bullet. Always construct a resource type directly the first time a mapper uses it, rather than trusting `model_fields.is_required()`.

### HL7 SCH/SIU-shaped facts worth remembering

- The `TQ` composite data type (used in the legacy `SCH-11` field) has **component 4 = start date/time, component 5 = end date/time** — not components 1/2 as might be assumed from a generic "timing" field. `TQ1` (the segment that superseded embedding TQ in SCH-11) is much simpler: TQ1-7 = start, TQ1-8 = end, both plain `DTM` fields. `app/mappings/siu.py::resolve_appointment_timing()` prefers TQ1, falls back to SCH-11 — resolved **per-field** (start and end independently), not all-or-nothing: a TQ1 segment that supplies only a start (no end) still lets a usable SCH-11 end value through, rather than leaving `Appointment.end` blank just because TQ1 supplied *something*. Get this wrong (checking `if start or end` instead of resolving each independently) and a partially-populated TQ1 silently blocks a complete SCH-11 fallback — this exact bug shipped once and was caught by code review, not by the original test suite (see `tests/test_siu_s12_mapping.py::test_partial_tq1_falls_back_to_sch11_per_field`).
- `_resolve_minutes_duration` prefers **TQ1-6 over SCH-9/10** (matching `resolve_appointment_timing`'s TQ1-over-SCH11 preference) specifically so a reschedule (S13) with a stale SCH-9 duration but a fresh TQ1-derived start/end doesn't produce a self-contradictory Appointment where `minutesDuration` doesn't match `end - start`. The SCH-10 unit check is lenient (`startswith("MIN")`) rather than an exact match, to tolerate spellings like `"MINUTES"`.
- `parse_hl7_datetime` (`app/fhir_models/builders.py`) preserves a trailing HL7 timezone offset (`+/-ZZZZ`) rather than dropping it and mislabeling the result `Z` (UTC) — silently wrong-by-hours timing is a real scheduling error, not a cosmetic issue, once this helper feeds `Appointment.start`/`end`/`created`.
- `RGS` (Resource Group Segment) is purely structural (sequencing/action-code only, no clinical content) — SIU's `AIS`/`AIG`/`AIL`/`AIP` segments are read directly via `optional_segments()` without tracking which `RGS` group they belong to, since FHIR's `Appointment.participant` is a flat list with no group-nesting concept to preserve anyway.
- `Appointment.participant.type`'s recommended value set (`encounter-participant-type`, Extensible binding) has no code for "patient" or for a location/equipment role — only practitioner-ish roles like `ATND`. Don't force a non-fitting code in just to fill the field; omit `type` when nothing in the binding actually fits (see `app/mappings/siu.py::_build_participants`).
- **AIP/AIL/AIG participants are materialized as real resources, not display text** - and each participant `Reference` carries both `reference` (the real resource, by `urn:uuid`) *and* `display` (human-readable text), per FHIR's own guidance that `display` SHOULD be populated even when `reference` is present, for consumers that render a participant list without resolving the whole Bundle. Per the official v2-to-FHIR ConceptMaps, `AIP-3` → `Appointment.participant.actor` = `Reference(Practitioner)` and `AIL-3` → `Reference(Location)` are fixed targets; both use the shared `build_practitioner_from_xcn`/`build_location_from_pl` from `common.py` for the resource, and `person_display`/`location_display` for the matching `Reference.display` text. `AIG` ("general resource") has **no single fixed target** in the official mapping - the real resource type depends on what `AIG-4` (Resource Type, a local/user-defined table) says the resource actually is. `app/mappings/siu.py::_build_aig_resource` branches on it: a location-ish `AIG-4` code (`LOCATION`/`ROOM`) builds a `Location`, anything else (the common case) builds a `Device` whose `.type` preserves the AIG-4 category (not just used to pick the branch and then discarded). Unlike AIP/AIL, this is built **directly** from AIG-3/4's components rather than routed through `build_location_from_pl` - AIG-3/4 is CWE-shaped, not PL, and the two only coincidentally look similar (both have two leading components); reusing the PL-scoped helper here worked by accident the first time this was written, not by design, and was fixed once caught by review. This is a disclosed interpretation, not something the spec hands you directly - if a real-world sender uses a different `AIG-4` vocabulary, `_AIG_LOCATION_TYPE_CODES` is the place to extend it.
- **`Appointment.comment` concatenates every `NTE` in the message**, not just the first one (`build_appointment_core` in `app/mappings/siu.py`). This replaced an earlier, buggier version that took only `nte_segments[0]` regardless of which segment it actually trailed, which could pick an AIS/AIG/AIL/AIP-scoped note over a more relevant SCH-level one just because it happened to appear first. **Known, disclosed limitation that remains:** every NTE is treated as appointment-scoped and folded into one comment (joined with `\n`) with no group-scoping - an SCH-level note and an AIP-scoped personnel note end up indistinguishable in the output, since `Appointment.comment` is a single field with no place to preserve which segment each note trailed, and no separate field exists for per-participant notes. Fixing *that* properly would require positionally tracking which segment each NTE follows (the same kind of group-tracking `app/hl7/parser.py::group_segments_by_leader` provides for ORU's OBR/OBX) and then deciding what to do with a non-SCH-scoped note, which has no home in FHIR's `Appointment` shape - a real scope decision, not a one-line fix. NTE-3 is read via `raw_field_str`, not `field_str` (see the `hl7` library gotcha above) - it's an `FT` free-text field, so a literal `^` in a clinical note must not get truncated at component 1. The join separator is `\n` rather than `"; "` specifically because a semicolon is a much more plausible substring of real clinical-note text than a newline, though neither separator fully eliminates the ambiguity of folding multiple notes into one field with no boundary markers.

### HL7 ORU/OBR/OBX facts worth remembering

- **OBR/OBX grouping is not optional, unlike SIU's RGS.** An ORU message can carry multiple `OBR` (one per ordered panel/report), each followed by its own run of `OBX` result segments. Which `OBX` belongs to which `OBR` is semantically load-bearing: `DiagnosticReport.result` must reference only the `Observation`s built from *its own* group's `OBX` segments, not every `OBX` in the message. This is exactly what `group_segments_by_leader(message, "OBR", ["OBX"])` is for - see `app/mappings/oru.py::BaseOruMapper.to_bundle`.
- **OBX-2 (Value Type) drives which `Observation.value[x]` choice is populated from OBX-5**: `NM` → `valueQuantity` (with OBX-6 as `.unit`), `ST`/`FT`/`TX` → `valueString`, `CE`/`CWE`/`CNE`/`IS` → `valueCodeableConcept`, `DT`/`DTM` → `valueDateTime`. Other value types (`SN`, `NA`, `ED`, ...) are left unset rather than guessed at - see `app/mappings/oru.py::_build_observation_value`.
- **OBX-11 (Result Status) / OBR-25 (Result Status) → `Observation.status` / `DiagnosticReport.status`** both draw from the same core HL7 status codes (table 0085/0123): `F`→`final`, `P`→`preliminary`, `C`→`corrected`, `A`→`amended`, `X`→`cancelled`, `D`/`W`→`entered-in-error`. Codes with no FHIR equivalent (`B`, `I`, `N`, `O`, `R`, `S`, `U`, `V`, ...) fall back to `"unknown"` (a real `Observation`/`DiagnosticReport` status code) rather than raising or guessing - see `app/mappings/oru.py::_RESULT_STATUS_MAP`.
- **`Encounter.status` for ORU's optional PV1-derived Encounter is honestly `"unknown"`**, not inferred the way ADT's `AdtA08Mapper` infers it - ORU's PV1 gives result-reporting context, not an admit/discharge lifecycle trigger, so there's no signal to infer a real status from.
- **OBX-16 (Responsible Observer) Practitioners are deduped within a message**, keyed by the XCN's id component (component 1), via a `performer_cache: dict[str, Practitioner]` created once per `to_bundle()` call and threaded through every `build_observation()` call for that message (see `app/mappings/oru.py::_resolve_performer`). A report panel commonly has every result verified by the same physician; without this, an N-result panel would produce N near-identical `Practitioner` resources referencing one real person instead of one resource referenced N times. An OBX-16 with no id component (family/given only) still gets its own fresh `Practitioner` each time, since there's no reliable key to dedupe on.
- **OBR-4 → `DiagnosticReport.code` and OBX-3 → `Observation.code` are both FHIR-required** (`fhir.resources.R4B` enforces this at construction). If either is genuinely empty in malformed input, resource construction raises `pydantic.ValidationError` naturally - already handled by the existing "FHIR validation error" (422) category in `app/routes/convert.py`, no special-casing needed.
- **ORU's free-text `OBX-5` values (`ST`/`FT`/`TX`) are read via `raw_field_str`, not `field_str`** — see the `hl7` library gotcha above.

### HL7 MDM/TXA facts worth remembering

- **The v2-to-FHIR IG ships exactly one MDM ConceptMap** (`MDM_T02` → `Bundle`) and treats the `TXA` segment map as trigger-agnostic — confirmed via `build.fhir.org/ig/HL7/v2-to-fhir`'s `artifacts.html`. There's no IG-published guidance distinguishing T02/T04/T06/T08/T10/T11's field-level handling, which is why `app/mappings/mdm.py::BaseMdmMapper` is non-trigger-polymorphic like ORU, not like ADT/SIU.
- **TXA → DocumentReference field map** (verified against the real IG ConceptMap page, not memory): TXA-2 Document Type → `type`, TXA-3 Content Presentation → `content.attachment.contentType` (1..1 in the IG), TXA-6 Origination Date/Time → `date`, TXA-9 Originator → `author` (Practitioner), TXA-10 Assigned Authenticator → `authenticator` (Practitioner), TXA-12 Unique Document Number → `masterIdentifier`, TXA-16 Unique Document File Name → `identifier`, TXA-18 Confidentiality Status → `securityLabel`, TXA-19 Availability Status → `status`, TXA-25 Document Title → `description`. TXA-17 (Completion Status → `docStatus`) is deliberately **not** mapped — no verified code crosswalk from TXA-17's table values to FHIR's 4-code `CompositionStatus` value set was found, and passing an unverified raw code through risked emitting a non-compliant value; omitted rather than guessed, same philosophy as ORU's OBX-11 status map falling back to `"unknown"` rather than inventing a mapping.
- **TXA-19 → `DocumentReference.status` only has one verified mapping** (`"AV"` → `"current"`); every other/absent value also defaults to `"current"` (matching the IG's own stated default) rather than guessing at a fuller crosswalk - see `app/mappings/mdm.py::_resolve_status`.
- **Document *content* is carried by `OBX` segments following `TXA`, not by `TXA` itself** — the IG doesn't show a worked content-transfer example, so this app's approach (every `TX`/`FT`-typed `OBX-5` value concatenated into a single plaintext body, base64-encoded into a separate `Binary` resource referenced via `DocumentReference.content.attachment.url = urn:uuid:...`) is a disclosed extension of the IG's intent, not something the IG hands you directly. A message with no usable OBX content still converts successfully - it just gets no `Binary` and an `Attachment` with no `url` (valid FHIR - `Attachment` has no required fields). OBX-5 is read via `raw_field_str`, not `field_str` - see the `hl7` library gotcha above.
- **TXA-3 (Content Presentation, HL7 table 0191) → a real MIME type has no IG-published crosswalk** - `app/mappings/mdm.py::_CONTENT_PRESENTATION_TO_MIME_TYPE` is a disclosed, local judgment call (same category as SIU's `_AIG_LOCATION_TYPE_CODES`) covering the most common real-world codes (`TEXT`/`FORMATTED`/`HTML`/`XML`/`RTF`/`PDF`/`JPEG`); anything unrecognized falls back to `text/plain` rather than leaving `contentType` unset, since it's a required-by-the-IG 1..1 target field.
- **TXA-9 (Originator) and TXA-10 (Assigned Authenticator) are deduped when they identify the same real person** (matching XCN id component), reusing one materialized `Practitioner` referenced from both `DocumentReference.author` and `.authenticator` rather than building two near-identical resources - same rationale as ORU's OBX-16 `performer_cache`, see `app/mappings/mdm.py::build_document_reference`.
- **`fhir.resources.R4B.DocumentReference` requires `content` at construction** (unlike `Appointment`, which doesn't enforce its spec-required `status`) - confirmed by inspecting `model_fields` and constructing directly, not assumed. `Attachment` and `Binary` have **no required fields at all** (same "no required fields" pattern as `Practitioner`/`Location`/`Device`). `Binary.data` and `Attachment.data` both accept a base64-encoded `str` at construction and store it decoded as raw `bytes` (`pydantic`'s `Base64Binary` type handles the encode/decode automatically) - don't re-`base64.b64decode()` a constructed instance's `.data`, it's already raw bytes.

## Testing

`tests/fixtures/*.hl7` are synthetic, non-PHI HL7v2 messages. They were generated by building each segment as a list of positional fields joined with the correct field index (see git history of `tests/fixtures/` if regenerating) rather than hand-typing pipe-delimited strings — it's easy to miscount field positions (e.g. PV1-19 vs PV1-18) by hand. If adding a new fixture, verify field positions by parsing it back with `hl7.parse()` and checking each field you intend to rely on.

`tests/test_generate_adt.py` / `tests/test_generate_siu.py` / `tests/test_generate_oru.py` / `tests/test_generate_mdm.py` are property-based/fuzz tests over the generators (fixed seed ranges, so failures are reproducible) - they check: the message parses and carries the right MSH-9 trigger; fields documented as "required" above are non-empty across many seeds; fields documented as "optional" are genuinely both present *and* absent across enough seeds (this is the test that would catch a `maybe()` call accidentally hardcoded to always-true/always-false); and, most valuably, that `convert_hl7_to_bundle()` succeeds on every generated message across 20+ fixed seeds per trigger - this is real fuzz coverage of the mappers using far more field-value combinations than the static fixtures alone exercise, and is exactly why the required/optional policy above guarantees convertibility rather than leaving it to chance. `test_generate_oru.py` additionally fuzzes the OBR/OBX grouping guarantee itself (every `DiagnosticReport.result` reference resolves to a real `Observation`, and every generated `Observation` is referenced by exactly one report) - the kind of correctness property that's easy to get right on a hand-built fixture and wrong on a differently-shaped one. `test_generate_mdm.py` similarly fuzzes whether OBX document content varies both present and absent, exercising the with-`Binary`/without-`Binary` mapper paths. Each of the four files also has a `test_generated_message_has_no_validation_errors` case - `validate_hl7()` must report `is_valid=True` (zero **error**-severity findings, not zero findings of any severity) across the same seed ranges; `test_generate_oru.py`'s version is the one place this distinction actually matters, since the ORU generator deliberately produces `OBX-5` values outside their `OBX-7` reference range ~30% of the time, which is a legitimate `info`-severity finding, not a bug.

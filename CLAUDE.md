# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`hl7-tools` is a Python/FastAPI web app for converting HL7v2 messages to FHIR R4 Bundles. The long-term goal (see README.md) covers transformation, validation, deduplication, test-data generation, and mapping across HL7v2/FHIR/CDA/C-CDA. Currently implemented:
- ADT — **A01 Admit, A02 Transfer, A03 Discharge, A04 Register, A08 Update** — each converting to a FHIR Bundle (Patient + Encounter).
- SIU — **S12 New booking, S13 Reschedule, S14 Modify, S15 Cancel** — each converting to a FHIR Bundle (Patient + Appointment + real Practitioner/Location/Device resources for the appointment's AIP/AIL/AIG participants, referenced by `urn:uuid`, not left as display-only text).
- ORU — **R01 Observation result, R30/R40 point-of-care result** — each converting to a FHIR Bundle (Patient + optional Encounter + one DiagnosticReport per OBR + one Observation per OBX, correctly grouped so each report only references its own results).
- A synthetic HL7 message generator (`app/generators/`) covering all 12 combinations above, with realistic field-level randomization, selectable from a UI dropdown or `/api/generate`.

Remaining trigger events for any of these message types (ADT A05/A11/A13, SIU S17/S26, ORU R32/etc.) can follow the same pattern as their siblings. MDM is planned next (TXA → DocumentReference, content referenced via a Binary resource rather than inlined).

## Architecture

**Request flow:** `app/routes/convert.py` (FastAPI routes for `/`, `/convert`, `/api/convert`, `/api/generate`, `/healthz`) calls the single pipeline entrypoint `app/hl7/pipeline.py::convert_hl7_to_bundle(raw_text) -> Bundle`. That function: parses raw text via `app/hl7/parser.py`, reads MSH-9 to get the message type/trigger event, looks up a mapper in `app/mappings/registry.py`, and calls `mapper.to_bundle(message)`. `/api/generate?message_type=&trigger_event=&seed=` runs the mirror-image path through `app/generators/registry.py::generate()` and returns raw HL7 text instead of a Bundle - the UI's message-type dropdown (populated from `app/generators/registry.py::list_supported_types()`) and "Generate sample" button call it to fill the textarea.

**Extension point for new message types:** `app/mappings/base.py` defines the `MessageMapper` interface (`to_bundle(message) -> Bundle`). Each HL7 message *type* gets its own module (`app/mappings/adt.py`, `app/mappings/siu.py`, `app/mappings/oru.py`) implementing that interface, registered in `app/mappings/registry.py` as `{(message_type, trigger_event): mapper_instance}` — no changes to routes, the parser, or templates. Cross-message-type shared logic lives in `app/mappings/common.py`:
- `build_patient(pid) -> Patient` — PID is mapped identically no matter the message type.
- `assemble_bundle(msh, patient, *resources) -> Bundle` — MSH-derived Bundle metadata + entries, generic over however many additional resources a message type produces.
- `resolve_encounter_class(pv1) -> Coding` / `build_visit_identifier(pv1) -> Identifier | None` — PV1-2 (patient class) → `Encounter.class` and PV1-19 (visit number) → an `Identifier`, used by both `adt.py`'s `build_encounter_core` and `oru.py`'s `_build_minimal_encounter`. These two independently hand-rolled the same `{"I":"IMP","O":"AMB",...}` mapping before it was extracted here - if you're building a third PV1-derived Encounter somewhere, use these rather than a third copy.
- `location_display(segment, field_num)` / `person_display(segment, field_num)` — PL/XCN-shaped **display-string** formatting, for when a field only needs to read as text (e.g. `Encounter.location`/`Encounter.participant` display in `adt.py`, which doesn't materialize separate Location/Practitioner resources). `person_display` falls back to the XCN id (component 1) when family/given are both empty — it must stay in sync with `build_practitioner_from_xcn`'s presence check ("id or family or given") below, since anywhere both are paired into one `Reference` (as `siu.py`'s AIP participants do), a field with only an id and no name would otherwise materialize a real Practitioner but produce `Reference(display="")`, which FHIR rejects (`display` must be a non-empty string when present). This exact crash shipped once (an id-only AIP, e.g. `AIP|1||5678||||`) and was caught by code review, not the original test suite — see `tests/test_siu_s12_mapping.py::test_aip_with_id_only_materializes_with_id_as_display`. `siu.py`'s `add_participant` also has its own defensive layer for the same failure mode: it omits `display` entirely (rather than passing `""`) whenever the resolved display string is empty, so any *future* display-string helper with a similar gap fails safe instead of crashing.
- `build_location_from_pl(segment, field_num) -> Location | None` / `build_practitioner_from_xcn(segment, field_num) -> Practitioner | None` — the same PL/XCN field shapes, but building a **real, separately-referenceable resource** instead of just a string. Used by `siu.py` (AIL→Location, AIP→Practitioner) and `oru.py` (OBX-16→Practitioner performer). Prefer these over the display-only pair whenever the target field is an `actor`/`performer`/similar `Reference` rather than a plain string, since a real resource is more useful to any downstream consumer (they can look up the practitioner's identifier, not just read a name). These are PL/XCN-scoped specifically - don't reuse them for a differently-shaped field (e.g. CWE) just because two of its components happen to look similar; build that shape's resource directly instead (see the AIG note below for a case where this was gotten wrong once).

Generic, reusable *field-level* FHIR-fragment builders (name/address/datetime/gender parsing, `build_codeable_concept_from_cwe` for CWE-typed fields) live in `app/fhir_models/builders.py`, shared across all message types; message-type-specific field logic stays in that type's module.

**Extension point for trigger events within one message type:** `app/mappings/adt.py` and `app/mappings/siu.py` follow the same shape — a `Base*Mapper(MessageMapper)` whose `to_bundle()` does the parts identical across every trigger event for that message type (require the message type's core segments, read any optional repeating segments, build the Patient via the shared `build_patient`, delegate to an abstract per-trigger build method, assemble the Bundle via the shared `assemble_bundle`), with concrete trigger subclasses implementing only the part that actually varies:
- `app/mappings/adt.py`: `BaseAdtMapper.build_encounter(pv1, evn, patient_id) -> Encounter`. Most subclasses (`AdtA01Mapper`, `AdtA04Mapper`) just call the shared `build_encounter_core(pv1, evn, patient_id, status=...)`; `AdtA02Mapper` additionally layers in PV1-6 prior-location history; `AdtA03Mapper` requires a resolvable discharge time (PV1-45 or EVN-2 fallback) and maps PV1-36 discharge disposition; `AdtA08Mapper` infers status from whether a discharge time is present.
- `app/mappings/siu.py`: `BaseSiuMapper.build_appointment(sch, tq1_segments, nte_segments, ais_segments, participants) -> Appointment`. `participants` is built once by `to_bundle` (via `_build_participants`, which also returns the Practitioner/Location/Device resources materialized for AIP/AIL/AIG so `to_bundle` can add them to the Bundle) since it's identical regardless of trigger event - only `status`/`start`/`end` vary, so those are the only things each subclass supplies. `SiuS12Mapper`/`SiuS13Mapper`/`SiuS14Mapper` all inherit the private `_BookedSiuMapper`, which resolves timing via `resolve_appointment_timing()` and requires a start time (raises `MappingError` otherwise) — these three are deliberately identical apart from which `trigger_event` string ends up in the `Appointment.extension` marker, since this converter has no persisted state to make a "new booking" vs. "reschedule" vs. "modify" distinguishable in the output. `SiuS15Mapper` (cancel) resolves timing but does not require it.
- `app/mappings/oru.py`: **not** trigger-polymorphic — `BaseOruMapper` handles R01/R30/R40 identically (they differ only in upstream ordering-workflow semantics this converter doesn't model), so the three concrete classes are just `trigger_event = "R01"/"R30"/"R40"` with no overrides. This is the degenerate case of the same pattern, not a different one.

When adding a new trigger event for an already-supported message type, add a subclass in that type's module rather than a new file — only add a new file for a genuinely different HL7 message type.

**Extension point for repeating leader/member segment groups:** `app/hl7/parser.py::group_segments_by_leader(message, leader_name, member_names)` walks a message's segments in order and associates each run of member segments with the leader segment that immediately precedes it (e.g. ORU's `OBR` leading its `OBX` results). Use this - not the flat `optional_segments()` - whenever which-segment-belongs-to-which matters for correctness, not just presence/absence. It's deliberately generic (any leader/member name pair), so a future message type with a similar repeating-group shape (e.g. an order message's `ORC` leading `OBR`) can reuse it directly rather than re-deriving the same positional-walk logic.

**Synthetic message generation (`app/generators/`)** is the mirror image of `app/mappings/` - HL7 text out instead of in. `app/generators/registry.py::generate(message_type, trigger_event, seed=None) -> str` looks up a plain generator function per `(message_type, trigger_event)` (not a class hierarchy like the mappers - generation doesn't need per-trigger polymorphism, just per-trigger field-population rules) and threads a `random.Random(seed)` instance through it; same seed always reproduces the same message byte-for-byte, `seed=None` gives real randomness for the UI's "fresh one" use case. `app/generators/base.py` holds shared primitives every generator uses: `maybe(rng, p=0.6) -> bool` (the one place "should this optional field be included" is decided), small pools of obviously-synthetic sample data (names/addresses/reason codes/lab tests/etc.), `generate_msh_segment()`, `generate_pid_segment()` (used by all three message types' generators), `build_minimal_pv1_fields(rng, patient_class) -> dict` (used by `adt.py` and `oru.py` - the two message types whose generators build a PV1; this exists because those two independently duplicated the same PV1-1/2/7/19 field logic once, and had already silently diverged - ORU's copy was missing the physician field ADT's had - before being unified here), and shape-level helpers (`random_location_field()` for PL-shaped fields, `random_physician_xcn()` for XCN-shaped fields) reused across `adt.py`/`siu.py`/`oru.py` as needed.

Required/optional policy (the field-level randomization rule the generators implement): a field is treated as required - always populated - when either the HL7 standard calls it required, *or* this app's own mapper needs it to avoid raising `MappingError`/`MissingSegmentError` for that specific trigger (e.g. `PV1-6` prior location is required only for A02; `PV1-44`/`PV1-45` are both required only for A03, since `AdtA03Mapper` raises without a discharge time; SIU S12/S13/S14 always get resolvable timing - via a randomized ~75/25 split between `TQ1` and legacy `SCH-11`, deliberately exercising both of `resolve_appointment_timing()`'s paths - while S15 leaves timing fully optional). Every other field is optional at a fixed ~50-60% inclusion rate via `maybe()`. The one deliberate exception is A08's discharge time, held at exactly 50% *by design* (not just "the general optional rate") specifically to exercise `AdtA08Mapper`'s finished-vs-in-progress status inference in both directions. This policy guarantees every generated message converts successfully through the existing pipeline - the generator's test suite leans on this heavily (see Testing below).

**Error taxonomy:** three custom exceptions in `app/hl7/errors.py` — `Hl7ParseError` (unparseable text), `MissingSegmentError` (required segment absent), `MappingError` (no mapper registered for a message type) — plus `pydantic.ValidationError` from FHIR resource construction. `app/routes/convert.py` translates each to an HTTP status + category label, and both the JSON API and the server-rendered form path route through the same `_run_conversion()` helper so error handling only lives in one place. The UI never shows a raw traceback.

### `hl7` library gotcha (important)

The `hl7` package (PyPI: `hl7`, i.e. python-hl7) is used for HL7v2 parsing:
- `hl7.parse()` **always** splits segments on `\r`, regardless of input. `app/hl7/parser.py::parse_message()` normalizes `\n`/`\r\n` input (e.g. from a browser textarea or an uploaded file) to `\r` before calling it, and drops blank lines.
- When a field/repetition has no component separator (`^`), the library collapses it to a bare Python `str` instead of a nested `[component]` list. Naively indexing a second level (`field[0][0]`) on such a field does **character** indexing, not component indexing, and silently returns the wrong (truncated) value. `app/hl7/parser.py::component_str()` guards against this and is the only sanctioned way to pull a component out of a field/repetition — always use it (or `field_str()`, which wraps it) instead of raw indexing when adding a new mapper.

### `fhir.resources` library notes

- Resources are imported from the `R4B` subpackage (`fhir.resources.R4B.*`), not the root package — as of `fhir.resources` v7+, the root package defaults to FHIR R5. R4B did not change `Patient`/`Encounter`/`Bundle`/`Appointment`/`Practitioner`/`Location`/`Device`/`DiagnosticReport`/`Observation`, so it's a safe practical stand-in for R4 here.
- `Encounter.class` is a required field exposed as the Python attribute `class_fhir` (since `class` is a reserved word) — it must be passed as a constructor kwarg (`Encounter(..., class_fhir=Coding(...))`), not set as an attribute after construction, because required fields are validated eagerly on `__init__`. `Appointment` has no such reserved-word field and can be built incrementally (construct with just `id`/`status`/`participant`/`extension`, then set the rest via attribute assignment).
- Bundles use `Bundle.type = "collection"` (not `"transaction"`) since there's no FHIR-server interaction in this app.
- Before using a resource sub-object you haven't used before (e.g. `EncounterHospitalization`, `AppointmentParticipant`, `DeviceDeviceName`, `ObservationReferenceRange`), inspect its real `model_fields` rather than guessing field names/shapes — this was done for `dischargeDisposition` when adding A03 discharge mapping, for `Appointment`/`AppointmentParticipant` when adding SIU, and for `Practitioner`/`Location`/`Device`/`DiagnosticReport`/`Observation` when adding resource materialization and ORU. Also don't assume the library enforces FHIR's own cardinality/binding rules: `fhir.resources.R4B.Appointment` doesn't actually require `status` at construction time (only `participant`) even though the FHIR spec calls status 1..1, and it does **not** validate that status/participant-status strings are real codes from the spec's value sets — getting the *values* right (not just the field names) is entirely on the mapper. Confirm real code values against the FHIR spec pages (e.g. `valueset-appointmentstatus.html`), not memory. `Practitioner`/`Location`/`Device` have **no required fields at all** (unlike `Encounter`/`Appointment`/`DiagnosticReport`/`Observation`, which each require at least one) - they can be built incrementally with nothing but an `id`.
- `Quantity.value` (used for `Observation.valueQuantity`, e.g. from OBX-5/6) deserializes as `decimal.Decimal`, not `float` - `Decimal('7.2') == 7.2` is `False` in Python, so comparisons in tests need `float(obs.valueQuantity.value) == 7.2` or a `Decimal` literal, not a bare float equality check.

### HL7 SCH/SIU-shaped facts worth remembering

- The `TQ` composite data type (used in the legacy `SCH-11` field) has **component 4 = start date/time, component 5 = end date/time** — not components 1/2 as might be assumed from a generic "timing" field. `TQ1` (the segment that superseded embedding TQ in SCH-11) is much simpler: TQ1-7 = start, TQ1-8 = end, both plain `DTM` fields. `app/mappings/siu.py::resolve_appointment_timing()` prefers TQ1, falls back to SCH-11 — resolved **per-field** (start and end independently), not all-or-nothing: a TQ1 segment that supplies only a start (no end) still lets a usable SCH-11 end value through, rather than leaving `Appointment.end` blank just because TQ1 supplied *something*. Get this wrong (checking `if start or end` instead of resolving each independently) and a partially-populated TQ1 silently blocks a complete SCH-11 fallback — this exact bug shipped once and was caught by code review, not by the original test suite (see `tests/test_siu_s12_mapping.py::test_partial_tq1_falls_back_to_sch11_per_field`).
- `_resolve_minutes_duration` prefers **TQ1-6 over SCH-9/10** (matching `resolve_appointment_timing`'s TQ1-over-SCH11 preference) specifically so a reschedule (S13) with a stale SCH-9 duration but a fresh TQ1-derived start/end doesn't produce a self-contradictory Appointment where `minutesDuration` doesn't match `end - start`. The SCH-10 unit check is lenient (`startswith("MIN")`) rather than an exact match, to tolerate spellings like `"MINUTES"`.
- `parse_hl7_datetime` (`app/fhir_models/builders.py`) preserves a trailing HL7 timezone offset (`+/-ZZZZ`) rather than dropping it and mislabeling the result `Z` (UTC) — silently wrong-by-hours timing is a real scheduling error, not a cosmetic issue, once this helper feeds `Appointment.start`/`end`/`created`.
- `RGS` (Resource Group Segment) is purely structural (sequencing/action-code only, no clinical content) — SIU's `AIS`/`AIG`/`AIL`/`AIP` segments are read directly via `optional_segments()` without tracking which `RGS` group they belong to, since FHIR's `Appointment.participant` is a flat list with no group-nesting concept to preserve anyway.
- `Appointment.participant.type`'s recommended value set (`encounter-participant-type`, Extensible binding) has no code for "patient" or for a location/equipment role — only practitioner-ish roles like `ATND`. Don't force a non-fitting code in just to fill the field; omit `type` when nothing in the binding actually fits (see `app/mappings/siu.py::_build_participants`).
- **AIP/AIL/AIG participants are materialized as real resources, not display text** - and each participant `Reference` carries both `reference` (the real resource, by `urn:uuid`) *and* `display` (human-readable text), per FHIR's own guidance that `display` SHOULD be populated even when `reference` is present, for consumers that render a participant list without resolving the whole Bundle. Per the official v2-to-FHIR ConceptMaps, `AIP-3` → `Appointment.participant.actor` = `Reference(Practitioner)` and `AIL-3` → `Reference(Location)` are fixed targets; both use the shared `build_practitioner_from_xcn`/`build_location_from_pl` from `common.py` for the resource, and `person_display`/`location_display` for the matching `Reference.display` text. `AIG` ("general resource") has **no single fixed target** in the official mapping - the real resource type depends on what `AIG-4` (Resource Type, a local/user-defined table) says the resource actually is. `app/mappings/siu.py::_build_aig_resource` branches on it: a location-ish `AIG-4` code (`LOCATION`/`ROOM`) builds a `Location`, anything else (the common case) builds a `Device` whose `.type` preserves the AIG-4 category (not just used to pick the branch and then discarded). Unlike AIP/AIL, this is built **directly** from AIG-3/4's components rather than routed through `build_location_from_pl` - AIG-3/4 is CWE-shaped, not PL, and the two only coincidentally look similar (both have two leading components); reusing the PL-scoped helper here worked by accident the first time this was written, not by design, and was fixed once caught by review. This is a disclosed interpretation, not something the spec hands you directly - if a real-world sender uses a different `AIG-4` vocabulary, `_AIG_LOCATION_TYPE_CODES` is the place to extend it.
- **Known, disclosed limitation:** `Appointment.comment` is taken from the first `NTE` segment found anywhere in the message (`nte_segments[0]`), with no awareness of which group that NTE trails (an SCH-level note vs. one scoped to a specific AIS/AIG/AIL/AIP occurrence). A message with multiple NTEs in different groups can have the wrong one — or a more relevant later one — end up as the appointment-level comment. Fixing this properly requires positionally tracking which segment each NTE follows (the same kind of group-tracking that `app/hl7/parser.py::group_segments_by_leader` now provides and that ORU relies on) - unlike when this was first written, that machinery now exists in the codebase, so revisiting this is a smaller lift than it used to be, but it's still a real scope decision (which segment is the NTE's "leader" isn't as clean-cut as OBR/OBX), not a one-line fix.

### HL7 ORU/OBR/OBX facts worth remembering

- **OBR/OBX grouping is not optional, unlike SIU's RGS.** An ORU message can carry multiple `OBR` (one per ordered panel/report), each followed by its own run of `OBX` result segments. Which `OBX` belongs to which `OBR` is semantically load-bearing: `DiagnosticReport.result` must reference only the `Observation`s built from *its own* group's `OBX` segments, not every `OBX` in the message. This is exactly what `group_segments_by_leader(message, "OBR", ["OBX"])` is for - see `app/mappings/oru.py::BaseOruMapper.to_bundle`.
- **OBX-2 (Value Type) drives which `Observation.value[x]` choice is populated from OBX-5**: `NM` → `valueQuantity` (with OBX-6 as `.unit`), `ST`/`FT`/`TX` → `valueString`, `CE`/`CWE`/`CNE`/`IS` → `valueCodeableConcept`, `DT`/`DTM` → `valueDateTime`. Other value types (`SN`, `NA`, `ED`, ...) are left unset rather than guessed at - see `app/mappings/oru.py::_build_observation_value`.
- **OBX-11 (Result Status) / OBR-25 (Result Status) → `Observation.status` / `DiagnosticReport.status`** both draw from the same core HL7 status codes (table 0085/0123): `F`→`final`, `P`→`preliminary`, `C`→`corrected`, `A`→`amended`, `X`→`cancelled`, `D`/`W`→`entered-in-error`. Codes with no FHIR equivalent (`B`, `I`, `N`, `O`, `R`, `S`, `U`, `V`, ...) fall back to `"unknown"` (a real `Observation`/`DiagnosticReport` status code) rather than raising or guessing - see `app/mappings/oru.py::_RESULT_STATUS_MAP`.
- **`Encounter.status` for ORU's optional PV1-derived Encounter is honestly `"unknown"`**, not inferred the way ADT's `AdtA08Mapper` infers it - ORU's PV1 gives result-reporting context, not an admit/discharge lifecycle trigger, so there's no signal to infer a real status from.
- **OBX-16 (Responsible Observer) Practitioners are deduped within a message**, keyed by the XCN's id component (component 1), via a `performer_cache: dict[str, Practitioner]` created once per `to_bundle()` call and threaded through every `build_observation()` call for that message (see `app/mappings/oru.py::_resolve_performer`). A report panel commonly has every result verified by the same physician; without this, an N-result panel would produce N near-identical `Practitioner` resources referencing one real person instead of one resource referenced N times. An OBX-16 with no id component (family/given only) still gets its own fresh `Practitioner` each time, since there's no reliable key to dedupe on.
- **OBR-4 → `DiagnosticReport.code` and OBX-3 → `Observation.code` are both FHIR-required** (`fhir.resources.R4B` enforces this at construction). If either is genuinely empty in malformed input, resource construction raises `pydantic.ValidationError` naturally - already handled by the existing "FHIR validation error" (422) category in `app/routes/convert.py`, no special-casing needed.

## Testing

`tests/fixtures/*.hl7` are synthetic, non-PHI HL7v2 messages. They were generated by building each segment as a list of positional fields joined with the correct field index (see git history of `tests/fixtures/` if regenerating) rather than hand-typing pipe-delimited strings — it's easy to miscount field positions (e.g. PV1-19 vs PV1-18) by hand. If adding a new fixture, verify field positions by parsing it back with `hl7.parse()` and checking each field you intend to rely on.

`tests/test_generate_adt.py` / `tests/test_generate_siu.py` / `tests/test_generate_oru.py` are property-based/fuzz tests over the generators (fixed seed ranges, so failures are reproducible) - they check: the message parses and carries the right MSH-9 trigger; fields documented as "required" above are non-empty across many seeds; fields documented as "optional" are genuinely both present *and* absent across enough seeds (this is the test that would catch a `maybe()` call accidentally hardcoded to always-true/always-false); and, most valuably, that `convert_hl7_to_bundle()` succeeds on every generated message across 20 fixed seeds per trigger - this is real fuzz coverage of the mappers using far more field-value combinations than the static fixtures alone exercise, and is exactly why the required/optional policy above guarantees convertibility rather than leaving it to chance. `test_generate_oru.py` additionally fuzzes the OBR/OBX grouping guarantee itself (every `DiagnosticReport.result` reference resolves to a real `Observation`, and every generated `Observation` is referenced by exactly one report) - the kind of correctness property that's easy to get right on a hand-built fixture and wrong on a differently-shaped one.

`tests/test_hl7_parser.py` has direct (non-fuzz) unit tests for `group_segments_by_leader` itself - correct grouping, no-leader-present, and members-before-the-first-leader-are-dropped - independent of any specific mapper, since it's meant to be reused by future message types.
